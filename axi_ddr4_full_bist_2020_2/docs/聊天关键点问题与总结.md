# DDR4 工作聊天关键点、问题与总结

更新时间：2026-09-11。此文件作为当前聊天工作的滚动摘要，后续变更应同步追加状态和新问题。

## 1. 目标演进

1. 最初讨论把 DDR 后端接入同一块自研 KU040 板的 PCIE-CPU 工程，保留 64-bit PCIe/Aurora 架构。
2. 在集成前先独立验证板上 DDR，选择 AXI 最小工程作为底座，而不是第 32 章 Native APP Demo。
3. 原 `axi_ddr4_min_2020_2` 保持不变，在远端新建 `axi_ddr4_full_bist_2020_2`。
4. 验证目标从 32 KiB 冒烟扩展为数据线、WSTRB、地址线、边界、全 4 GB、March、保持和 PRBS。
5. 当前用户明确收缩执行范围：不做综合，只做工程生成、编译、Elaborate 和基本冒烟。

## 2. 已确认硬件事实

- 板卡不是通用开发板，而是组内把 KU040 FPGA、四颗 DDR、PCIe、Aurora、以太网集成到同一单板。
- FPGA：`xcku040-ffva1156-2-i`。
- DDR：GDQ3BFAM-WJ，单颗 8 Gb/x16，四颗组成 x64、4 GB。
- DDR 差分参考时钟使用 AK17 对；外部低有效复位为 AC34；LED 为 T22/T23。
- 同事按第 32 章 Demo 已上板通过，Demo 的管脚约束具有可复用依据。

## 3. 关键技术判断

- AXI 接口比 Native APP 更适合后续 PCIe/Aurora 集成和可移植验证。
- 原最小工程 32 KiB 冒烟可用，但单拍且不能证明全 4 GB。
- 全空间结束判定必须使用 33-bit，否则 `0xFFFF_FFF8` 后会回绕到 0。
- 正式访问采用 16-beat、64-bit INCR；burst 基址按 128 B 对齐，禁止跨 4 KiB。
- Micron 别名/CL16 只保留为 Demo 兼容条件；GD 正式版使用 CL17/CWL12 和规格书 2400 参数。
- MIG 自定义颗粒在 Vivado 2020.2 可生成综合配置，但官方器件模型对自定义颗粒仿真存在限制，因此仿真用 AXI RAM 做全模式，MIG 器件模型只适合小范围/兼容配置。
- ILA/VIO 不能替代 BIST；必须有可综合事务发生器、比较器和错误现场寄存器。

## 5. 遇到的问题与处理

| 问题                         | 原因                       | 处理/结论                                  |
| -------------------------- | ------------------------ | -------------------------------------- |
| 远端一度不可连接                   | 网络未开启                    | 网络恢复后继续，仅在远端执行 Vivado                  |
| GD CustomParts 初次生成失败      | 未先置 `DDR4_isCustom=true` | 调整 Tcl 顺序后 gd2400 XPR 生成 PASS          |
| 自定义颗粒 MIG 仿真受限             | Vivado 2020.2 官方模型限制     | 全模式使用 AXI RAM；硬件做全 4 GB                |
| 旧 `pipeline.status` 与日志不一致 | 旧工程状态文件陈旧                | 新工程只以日志 PASS marker 为准                 |
| 33-bit 全空间和 10 分钟计数        | 32-bit 会回绕/溢出            | 地址上界和 HOLD\_CYCLES 均扩展为足够位宽            |
| 误启动一次综合                    | 执行范围随后被再次明确为“不做综合”       | 立即停止进程、删除 `.runs`，无 bitstream；保留中断日志说明 |
| 冒烟后遗留 xelab                | 工具子进程未自动退出               | 已终止，确认 vivado/xelab/xsim 均为 0          |
| 临时生成物和参考副本冗余               | 开发审计过程产生                 | 从交付目录移除，保留必要 XPR/XCI/日志/WDB/文档         |

## 7. 后续入口

### 7.1 2026-09-15 Hardware Manager 崩溃恢复

Hardware Manager Auto Connect 触发电脑重启后，XPR 无法打开。根因不是 XPR，而是 `prj\compat\axi_ddr4_full_bist_compat.hw\axi_ddr4_full_bist_compat.lpr` 被写成全零文件，Vivado 报 XML character encoding not supported。已保留原目录为 `axi_ddr4_full_bist_compat.hw_recovered_20260915`，让 Vivado 重建 `.hw` 状态目录；恢复后 XPR、synth\_1、impl\_1 均可读。体检脚本为 `tcl\check_project_recovery.tcl`，日志为 `logs\project_recovery_check_final.log`。

只有用户以后明确允许综合，才可运行带 `ALLOW_SYNTH=1` 防误触开关的 `tcl/future_build_bitstream_NOT_RUN.tcl`。完成综合、实现、时序、DRC 和 bitstream 后，再按 `KU040_DDR4上板测试操作指南.md` 执行分层上板验收。

### 7.2 2026-09-15 AL321 上板连接

之前 Hardware Manager Auto Connect 崩溃的直接诱因之一是使用紫光 AL232 线缆；当前已改用 Xilinx 兼容 AL321，截图显示 `xcku040_0=Programmed`、`MIG_1=CAL PASS`、VIO 输出为 Reset、ILA 为 Idle。上板操作必须先下载匹配 bit/ltx，确认 CAL PASS，再运行 VIO。一个测试完成后不需要重新上电或重新校准，下一个 mode 使用 `restart` 0→1→0 脉冲重新锁存并启动；`start` 只适用于 IDLE，`repeat_enable` 在启动时锁存，不能在运行中靠改电平停止循环。具体 probe 位定义与逐项顺序维护在 `KU040_DDR4上板测试操作指南.md`。
