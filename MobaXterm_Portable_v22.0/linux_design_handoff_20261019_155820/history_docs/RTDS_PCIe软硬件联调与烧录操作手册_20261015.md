# RTDS PCIe 软硬件联调与烧录操作手册

版本：V3.0；核对日期：2026-10-15；工具：Vivado 2020.2；FPGA：xcku040-ffva1156-2-i；PCIe 对端：RK3588 / Linux。

本手册从“PCIe 和现有访问工具已经调通”开始，按一次共同操作流程组织，不划分驱动与应用章节。软件同事使用现有工具执行文中的 `read32`、`write32`、H2C、C2H；这些名称是操作示意，不是未经确认的现成命令。

当前用户已确认按加快 Flash 配置的工序完成 PCIe 联通。寄存器、数据比对、通知、GPIO 和长期稳定性的条目仍需逐项记录实测，不自动标为通过。本次只整理文档、证据清单及调试辅助脚本，不重跑综合/实现，不改 RTL、BD、IP 或管脚，不执行现场烧写和 VIO 输出。

## 1. 先看这一页：本轮固定顺序

| 步骤 | 共同操作 | Vivado 此时做什么 | 达到什么条件再继续 |
|---|---|---|---|
| 1 | 确认使用主工程冷启动文件；若已固化且正常，直接进入步骤 3 | 查看文件名/哈希；不重新 Program | 文件身份已记录 |
| 2 | 需要固化时，用配置存储器编程写 MCS，勾选 Erase、Program、Verify；完成后整机断电再上电 | 编程会暂时加载 SPI 辅助设计；此时不用找 VIO/ILA | Program/Verify successful；冷启动重新建链 |
| 3 | 保持冷启动现场，连接 JTAG、关联匹配 LTX | **只 Refresh Device，不再 Program Device** | 看到两组 VIO、四组 ILA、MIG 和 PCIe 内部 JTAG 调试核 |
| 4 | 记录启动状态，间隔 1 秒再读一次 | 刷新两组 VIO；三个输出保持 0；**不点 Trigger、不清历史** | 新 VIO link/DDR/时钟正常；旧 VIO status 低两位为 3，无 fault |
| 5 | 读固定寄存器和状态，读写回验配置寄存器 | VIO 只刷新；BAR 检查不要求 ILA 触发 | 版本、DDR 状态、配置读回正确 |
| 6 | 用 16Byte 数据完成 H2C 写 DDR、C2H 回读 | PCIe ILA 先布防，再执行对应 DMA；旧 VIO start 仍为 0 | 全部 16Byte 一致；DMA 无错误；无新丢字/DDR 错误 |
| 7 | 软件先准备轮询 `0x30`，再产生一个上行测试块 | FDMA ILA **Run Trigger** 等待后，旧 VIO `rx_test_start` 提交 0→1 | 一块 8Byte；读清通知不释放；C2H 完成且比对后一次归还 |
| 8 | 重复单块、多块、用户通知检查 | 每轮先布防再触发；新 VIO 保持观察 | 每块一次确认，队列可排空，计数稳定 |
| 9 | 有实际 10G/1G 对端时做下行发送和 GPIO/同步帧验证 | 下行 FDMA ILA 先 Run Trigger，再写 `0x20=1`；GPIO 用示波器/逻辑分析仪 | 对端内容及 I/O 实测正确 |
| 10 | 连续运行和冷启动复测，归档证据 | 保存 VIO、寄存器、CSV/WDB 和文件身份 | 按第 12 节条目记录通过/失败/未执行 |

“▶ Run Trigger”用于先等待指定事件，“▶▶ Run Trigger Immediate”用于立即查看当前短窗口。具体图标以鼠标悬停显示的文字为准。VIO 观察不需要点击 Trigger；VIO 输出必须真正提交到硬件，不能只修改编辑框。

```text
上行：VIO固定字 → 原block writer → FDMA → AXI → DDR → XDMA C2H → CPU
下行：CPU H2C → DDR → 原下行业务 → 10G Aurora
```

该编译模式隔离真实 Aurora RX/FIFO 上行输入。VIO start=0 也不会恢复真实上行。以后接实际子机上行时，必须将 `RX_VIO_TEST_ENABLE=0` 并重新综合、实现、生成和固化另一套产物；这属于逻辑模式变化，不能只重新生成 bit，也不是本次文档整理会执行的操作。

## 3. 软件访问地址与全部业务寄存器

### 3.1 四种地址分别使用

| 地址类型 | 例子 | 用在哪里 |
|---|---|---|
| CPU 侧用户 BAR 映射基址 | 由现场枚举与工具给出 | `read32(USER_BAR_BASE+offset)`，手册简写为 `read32(offset)` |
| 用户 BAR 相对偏移 | `0x00`、`0x24`、`0x30` | INFO_EXCH 业务寄存器，32bit、小端、按 4Byte 对齐 |
| FPGA 内部 AXI-Lite 地址 | `0x40000000+offset` | BD 内部地址；XDMA 的用户 BAR 已配置相应地址翻译，**软件不要再次加 0x40000000** |
| 卡端 DDR 字节地址 | 下行 `0x8000`；上行由 `0x18` 返回 | 传给 H2C/C2H 的卡端地址；不是 CPU 缓冲区地址，也不是用户 BAR 偏移 |

CPU 的 DMA 缓冲区由现有访问工具分配/映射，另有自己的 CPU/总线地址，不可拿 DDR 卡端地址代替。当前用户 AXI-Lite 为用户 BAR0，XDMA 控制为 BAR1；实际使用的工具入口必须是用户业务 BAR。最可靠的初验是偏移 0 返回 `0x00002001`，不能只凭“读出了非零”判断 BAR 正确。

### 3.2 完整寄存器表

| 偏移 | 名称 | 访问 | 复位值/固定值 | 使用方法 |
|---|---|---|---|---|
| `0x00` | VERSION | RO | `0x00002001` | 接口版本；未随诊断版升级，不能单独识别 bit 身份 |
| `0x04` | PROG_TIME | RO | `0x20260914` | BD 常量；不是本次 bit 生成日期 |
| `0x08` | BUF_LEN_MAX | RO | `0x00040000` | 一个上行块最大 256KiB |
| `0x0C` | FPGA_TEMP | RO | 当前状态 | `[15:0]` SYSMON 原始码，bit16 为 TEMP_RD 周期提示，`[31:17]=0`；不是直接摄氏度 |
| `0x10` | INT_STATE | 读清通知/相关错误 | 当前通知，主要使用 bit0 | 先保存 `0x2C`，再读一次；读取不释放块，不能用其是否为 0 判断队列空 |
| `0x14` | CPU_REC_STATE | 写 bit0=1 产生一次确认；读通常 0 | 0 | 每完成一块 C2H 后写 1 一次；不需要再写 0；不凭读回判断确认完成 |
| `0x18` | FPGA_CPU_START_ADDR | RO | 队列空时 0 | 当前最老待取块的 DDR 字节地址 |
| `0x1C` | FPGA_CPU_LEN | RO | 队列空时 0 | 队头有效字节数，4Byte 整数倍 |
| `0x20` | CPU_WR_DONE | 空闲时写 1 启动；读 bit0 忙 | 0 | 下行任务结束/拒绝/中止后硬件清 0；不是成功结果码 |
| `0x24` | CPU_FPGA_START_ADDR | RW，忙时忽略写 | `0x00008000` | 下行起始 DDR 地址，16Byte 对齐 |
| `0x28` | CPU_FPGA_LEN | RW，忙时忽略写 | `0x00008000` | 下行总字节数；当前 RTL 复位为 32KiB，联调主动写 `0x10` |
| `0x2C` | DDR_STATUS | RO 当前位及粘滞位 | 当前状态 | bit0 DDR_READY；bit1 校准完成；bit2 AXI 响应错误；bit3 RX 溢出；bit4 DDR/FDMA 超时；其余 0 |
| `0x30` | UP_READY_BLOCK_CNT | RO | 0 | 已完成且未归还块数，0～8；轮询的主要依据 |
| `0x34` | UP_BLOCK_SEQ | RO | 空时 0，第一块编号也可为 0 | 队头块顺序号，32bit 自然回绕；不用它判断空队列 |
| `0x38` | UP_DROP_WORD_CNT | RO，复位清零 | 0 | 累计丢失的 32bit 字数，饱和于 `0xFFFFFFFF`；读 `0x10` 不清它 |

未实现偏移读回 0，但不作为可用接口，不试写保留偏移。旧 V2.0 Word 表中 `0x28` 出现的 `0x10` 是联调示例值；当前 RTL 的真实复位值为 `0x8000`，本手册按源码修正。

健康 DDR 条件为 `(DDR_STATUS & 3)==3`；初测期望 `DDR_STATUS & 0x1C == 0`。先保存原始值，再读 `0x10` 清通知和可清错误，复查是否重新出现。清错不会修复正在发生的故障，也不会清累计丢字、VIO 注入 fault 或诊断历史。

### 3.3 不带副作用的第一次读取顺序

```text
读 0x00 → 0x04 → 0x08 → 0x0C → 0x20 → 0x24 → 0x28
→ 0x2C → 0x30 → 0x18 → 0x1C → 0x34 → 0x38
保存以上结果后，确实需要清通知时才单独读 0x10
```

不要在自动“全寄存器刷新”中无条件包含 `0x10`。后台自动读清会使通知看起来始终为 0，并破坏清前错误证据。已有工具若自动处理了通知，需在本轮日志注明；队列判断仍看 `0x30`。

## 4. 完整烧录、固化、冷启动和连接顺序

### 4.1 当前文件已经生成且身份匹配：直接使用

已有 bit/MCS 无需再生成，更不需要重新综合/实现。先记录第 2 节文件哈希；确认 Flash 型号与实际板卡一致。当前 GUI 使用 `mt25ql128-spi-x1_x2_x4`，容量 128Mbit = 16MiB；Flash 型号以该板器件和已验证选择为准。

1. 在主工程 Vivado 打开 Hardware Manager → Open Target → Auto Connect，选择 `xcku040_0`。保留一个 GUI 连接当前 JTAG target。
2. 右键 FPGA → Add Configuration Memory Device；已有该器件则直接使用，不重复添加。选择匹配的 `mt25ql128-spi-x1_x2_x4`。
3. 右键配置存储器 → Program Configuration Memory Device。Configuration file 选 `TOP_main_spi4_50.mcs`；若要求 PRM，选同目录、同次生成的 `.prm`。
4. 地址范围使用配置文件指定范围（use_file），勾选 Erase、Program、Verify。LTX 不填入 Flash 配置文件栏；不要把 `spi_xcku040_pullnone.bit` 当成业务 bit。
5. 点击 Program，等日志明确出现擦除成功及 `Program/Verify Operation successful`。此步骤会暂时将 FPGA 配置为 SPI 编程辅助设计，业务和原 VIO/ILA 会消失；辅助阶段的 missing probes 不能当成业务逻辑已坏。
6. 编程完成后结束当前业务访问，按现有整机操作断电，确认各电源轨已放电，再按实际使用方式上电。这里不规定未经测量的“必须断电几秒”。
7. 观察 FPGA 配置完成、LED16 心跳、LED17 灭和现有软件连接状态。不要再点 Program Device，否则会改成 JTAG 重配置现场，失去这次冷启动证据。
8. 在 Hardware Manager 重新连接 target，关联 `TOP_main_spi4_50.ltx` 后 Refresh Device，按第 5 节观察。软件按现有工具重新建立设备访问、BAR 映射和 DMA 缓冲区。

`Boot from Configuration Memory / boot_hw_device` 用于按模式管脚重新启动配置，不会把所选 bit 写入 Flash；不能代替 Program Configuration Memory Device，也不能代替整机断电上电。GUI 的 PROGRAM.FILE 只是电脑侧属性，不证明 Flash 当前内容。

2026-10-14 已见过两次测试 bit 的 JTAG Program 成功，随后 Boot/Refresh 才出现 Xicom 50-38 和 Labtools 27-3176；不能将这种混合过程记为同一个 bit 的冷启动失败。

### 4.2 仅需要重新导出启动配置时

只修改四项启动配置、逻辑和已实现布线均未变化时，复用现有 routed design，重新导出 bit/LTX/MCS 即可。**前置动作必须先打开已实现设计**。在主工程 GUI 的 Tcl Console 先执行：

```tcl
open_run impl_pcie_diag_20261014
current_design
```

等加载完成，`current_design` 返回 `TOP` 后才执行下面的代码。使用带时间戳的新目录，避免覆盖已确认成功的交付文件：

```tcl
set_property CONFIG_MODE SPIx4 [current_design]
set_property BITSTREAM.CONFIG.SPI_BUSWIDTH 4 [current_design]
set_property BITSTREAM.CONFIG.CONFIGRATE 50 [current_design]
set_property BITSTREAM.CONFIG.SPI_FALL_EDGE Yes [current_design]

set boot_out C:/project/RTDS/pcie_cold_boot_audit_20261014/main_spi4_50_[clock format [clock seconds] -format %Y%m%d_%H%M%S]
file mkdir $boot_out
write_bitstream $boot_out/TOP_main_spi4_50.bit
write_debug_probes $boot_out/TOP_main_spi4_50.ltx
write_cfgmem -format mcs -size 16 -interface SPIx4 \
    -loadbit [list up 0x0 $boot_out/TOP_main_spi4_50.bit] \
    -file $boot_out/TOP_main_spi4_50.mcs
```

四项配置已经保存在主工程 `RTDS_test_DDR4_64bit.srcs/constrs_1/new/DDR4_PIN.xdc`。注意旧 routed checkpoint 可能保留旧属性，所以复用旧实现结果时仍应在当前打开的 design 上明确设置并确认。无需为了文档复核重新运行上述导出命令。

如改过 RTL、BD、IP、参数、管脚或诊断探针，不能照搬“不重跑综合/实现”的结论；必须使用对应的新实现产物。当前启动版与原诊断版的配置帧数据哈希一致，仅启动相关命令改变，核对记录为 `candidate_bitstream_verification.json`。

### 4.3 仅 JTAG 临时下载

右键 FPGA → Program Device，Bitstream file 选 `.bit`，Debug probes file 选同版 `.ltx`，Program 成功后 Refresh。JTAG 下载不持久化 Flash，断电后从 Flash 加载的仍是原内容。

该动作会重置 FPGA 业务、清空诊断累计历史，并造成 PCIe 端点消失后重现。当前 CPU 的固化软件不保证会重新初始化链路；因此日常联调优先保留已成功冷启动的板内程序，不能把 JTAG 下载当成每轮测试的必需步骤。恢复现场时按已验证的整机冷启动流程重新建立连接。

### 4.4 冷启动后只关联 LTX，不重下载

可在 GUI 的 Device Properties 中设置 Probes file。界面不易找到时，在已连接 target 的 Tcl Console 执行：

```tcl
set dev [get_hw_devices xcku040_0]
current_hw_device $dev
set_property PROBES.FILE {C:/project/RTDS/pcie_cold_boot_audit_20261014/main_spi4_50_gui/TOP_main_spi4_50.ltx} $dev
set_property FULL_PROBES.FILE {C:/project/RTDS/pcie_cold_boot_audit_20261014/main_spi4_50_gui/TOP_main_spi4_50.ltx} $dev
refresh_hw_device $dev
```

这段不执行 `program_hw_devices` 或 `boot_hw_device`。探针 UUID 不匹配时先核对板内程序与 LTX 身份，不强行忽略警告。首次空白波形面板先点“+”添加探针，不能把“没添加信号”当成采样时钟停止。

## 5. 上电后默认观察：不需要 Trigger 或 VIO 启动

### 5.1 先保存，再考虑清除

1. 在 Dashboard Options 勾选两组 VIO；面板为空时用“+”添加全部信号。
2. 确认旧 VIO `rx_test_start=0`，新 VIO `clear_vio=0`、`capture_axi_vio=0`。上电默认均为 0；已是 0 无需反复提交。
3. 点击 Refresh Inputs 或启用自动刷新，保存第一次读数，再间隔约 1 秒保存第二次，必要时 10 秒保存第三次。此时不清诊断历史、不发注入、不启动 DMA。
4. 依次看新 VIO `live_vio`：bit7=1、bit6=0、bit0=1、bit1=1、bit2=1、bit3=1、bit4=1、bit5=1。无业务 IRQ 时常见 `0x00BF`，有 IRQ 时可为 `0x01BF`；不能只死比整字数值。
5. 看 `uptime_vio` 增加、`seq_vio` 持续更新、`age_vio` 不持续累加；然后看 `history_vio[3]=1`、掉链/PLL/复位计数是否增加。初始 `ups_vio` 不一定精确为 1，链路可能在观察器稳定前已经建立。
6. 旧 VIO 应为 busy=0、fault=0、status[1:0]=3；若队列为空、无通知，常见 status=3。`rx_test_status_r=1` 仍表示只有 DDR ready，PCIe 未就绪。
7. 软件读取第 3.3 节的无副作用寄存器清单；保存 `0x2C` 和 `0x38` 基线。

`live_vio[2]=1` 只证明 PCIe 时钟心跳被观察到，不代表 PCIe link up；建链看 bit3，AXI 复位释放看 bit4。`first_link_vio=0xFFFFFFFF` 表示本次观测范围内未见 link；其他值为本次 FPGA 业务复位后的相对毫秒，不是 CPU 开机时间。

监测从 FPGA 配置完成且相关时钟开始后才工作，不能记录 bit 尚未装入时的电气过程。重新 Program、整机掉电或板级复位会改变/清掉历史。不要为“开始观察”先点清零。

### 5.2 三种操作互不替代

| 动作 | 实际作用 | 不能替代什么 |
|---|---|---|
| 新 VIO `clear_vio` 0→1 | 清诊断历史/计数；不驱动 PCIe 或 DDR 复位 | 不清业务通知、丢字、注入 fault，不是重新训练 PCIe |
| 软件读 `0x10` | 清业务通知及可清错误标志 | 不归还上行块，不清诊断历史，不清累计丢字 |
| 软件写 `0x14=1` | 归还一个最老待取块 | 不是清通知，不是启动接收，不能在 DMA 完成前执行 |

确需分段统计时，先保存旧 VIO/寄存器日志，再将新 VIO clear 提交 0→1，确认刷新后提交回 0。PCIe 时钟停止时，原生域清除会等时钟恢复；不连续抖动 clear。清除后，当前已经为真的“曾经”位会很快再次置位；当前 link 已高时不一定重新产生一次 0→1 计数。

## 6. 寄存器与控制接口联调：不要求先做 DMA

| 编号 | 软件动作 | Vivado/VIO 动作 | 预期结果 |
|---|---|---|---|
| R01 | 连续读取 `0x00/0x04/0x08` 各 100 次，记录错误/不一致次数 | 两组 VIO 只刷新；不用 Trigger | 固定为 `2001/20260914/40000`；无访问错误 |
| R02 | 读 `0x2C/0x30/0x38`，记录基线 | 确认 link、DDR 为 1，rx_start=0 | DDR 低两位为 3；块数 0～8；无新丢字 |
| R03 | 等 `0x20=0`；保存 `0x24/0x28`；写 `0x24=0x8000`、`0x28=0x10`，分别读回 | 不操作 VIO，不要求 ILA 触发 | 读回匹配，单独写地址/长度不会启动业务 |
| R04 | 在仍空闲且无并行业务时，写另一组合法配置 `0x24=0x8010`、`0x28=0x20` 并读回；然后恢复 `0x8000/0x10` | 保持 start=0 | 配置可重复写回；不写 `0x20=1`，此项不发 Aurora |
| R05 | 第 8 节注入一块后，保存 `0x2C/0x38`，读一次 `0x10`；再次读取 `0x30/0x18/0x1C/0x34` | 新 VIO看 IRQ 位，旧 VIO看通知位/块数 | 通知清除，但块数和队头不变；无其他清通知者时首次通知应可见 |

只有寄存器访问能力时，先执行 R01～R04。R05 可看状态变化，但**不要为了清空测试块而直接写 `0x14`**；后续仍应读完有效数据再归还。当前硬件已能看见 VIO/寄存器相关状态，不代表每一次 BAR AR/AW 都能在现有 ILA 中看见。

软件拥有写寄存器能力后可以继续后面的控制验证；H2C/C2H 尚未接入时，将数据比对项目标为待测，不用“寄存器能读”替代数据通路结论。测试名不区分软件实现在哪一层。

## 7. 先验证 DDR 搬运：16Byte H2C → C2H

固定数据：

```text
卡端地址：0x00008000
请求长度：0x00000010（16Byte）
TX：00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
RX初值：A5 A5 A5 A5 A5 A5 A5 A5 A5 A5 A5 A5 A5 A5 A5 A5
```

1. 确认 DDR、PCIe 就绪，旧 VIO start=0，`0x20=0`。本项不要求 10G 建链。
2. 需要 ILA 时，打开 `u_pcie/U_PCIE_LINK_DEBUG/ila`，按第 10 节设正常连续采样；本次先布防 H2C 写地址握手触发。**先 Run Trigger，再执行 H2C**。
3. 执行 `H2C(0x8000,TX,16)`，等待现有工具返回完成，检查错误及实际完成字节数。不要只固定睡眠后假定完成。
4. 保存这一轮 PCIe ILA。随后为 C2H 单独重新布防读地址握手触发；**先 Run Trigger，再执行 C2H**。
5. 执行 `C2H(0x8000,RX,16)`，等待完成及所需 CPU 缓存同步。
6. 比较全部 16Byte。小端 32bit 字应为 `03020100、07060504、0B0A0908、0F0E0D0C`。
7. 保存 `0x2C/0x38`、新 VIO 掉链/PLL/复位计数、DMA 错误与完成字节数。`0x2C[4:2]` 无新置位、`0x38` 不增加。

不需要点 VIO start，不需要写 `0x20=1`。当前 FDMA ILA 只看业务 adapter，CPU 直接 H2C/C2H 不经过该业务接口，所以它没有触发是正常可能情况。PCIe ILA 看 XDMA M_AXI，可验证 VALID/READY 握手及数据，但最终成功仍以完整 CPU 缓冲区比对为准。

扩展数据：全 0、全 FF、AA55 交替、递增字节、带固定种子的伪随机；扩展长度 16、32、256、4096、32768Byte，均保持本次下行窗边界与工具对齐要求。先串行完成，再考虑并发；每次实际回读前先把 RX 填成与期望不同的图样。

## 8. 上行固定数据闭环：先 ILA，后 VIO，最后归还

### 8.1 单块操作表

| 顺序 | 软件与检查 | Vivado 操作 | 预期/下一步条件 |
|---|---|---|---|
| U1 | 读 `0x30`，首次要求为空；保存 `0x24/0x28/0x2C/0x38` | 旧 VIO start 先提交 0；busy=0、status[1:0]=3、fault=0 | 如有旧块，先按正常流程读完/归还，不盲确认 |
| U2 | 先准备轮询 `0x30`（建议 1ms 间隔、首次等 500ms） | FDMA ILA 添加 `fdma_wareq` 为唯一条件 `==1`，点击 **Run Trigger** | 显示等待触发；不要点 Immediate |
| U3 | 开始等待块数增加；不循环读 `0x10` | 旧 VIO `rx_test_start` 提交为 1；新 VIO输出保持 0 | 发生器只响应这一次 0→1 |
| U4 | 等 `0x30=1`，读取 `0x18/0x1C/0x34` | 旧 VIO accepted=2，busy 最终=0，fault=0，blocks=1 | 有效长度 8Byte；正常首次地址 `0x100000`，以后用返回地址 |
| U5 | 保存 `0x2C/0x38`，单独读一次 `0x10`；复读队头 | 保存 FDMA 波形，旧 VIO观察通知变化 | 读清通知不释放；块数、地址、长度、序号稳定 |
| U6 | `C2H(返回地址,RX,8)`，等完成及缓存同步，逐字节比对 | 如需观察 C2H，先单独给 PCIe ILA 布防读握手 | 有效数据 `11 00 00 00 22 00 00 00` |
| U7 | 成功后写 `0x14=1` **一次** | 不点 VIO start | 一次归还一个最老块；不需要再写 0 |
| U8 | 没有新触发时，复查 `0x30=0`、`0x18/0x1C=0`，`0x24/0x28` 未被上行改变 | 旧 VIO blocks=0，busy=0；start 可保持 1 | 丢字不增加，无新 DDR 错误 |
| U9 | 开始下一轮时重复 U1～U8 | busy=0 后提交 start=0，再提交 1；采波形则先重新 Run Trigger | 每次一个独立测试块 |

预期 FDMA 写请求：`fdma_wsize=1`，`fdma_wdata=64'h00000022_00000011`，正常写状态 0→1→2→3→0。两个输入 32bit 字拼成一个 64bit 写拍；不是两个 DDR 拍。

writer 周期为 250MHz / 25,000,000 拍 = 100ms。发生器先等当前周期结束再送字，还要等下一次块登记，正常从触发到块可读约 100～200ms 加事务处理时间。busy 的短中间变化可能被面板刷新漏掉，不能因未看见 busy=1 判失败；最终 accepted、fault、块状态和数据结果必须核对。

`accepted=2` 只说明两个输入字被接受，不等于 DDR 写成功。busy 回 0 也可能是异常退出，需 fault=0、块已登记且 C2H 数据一致。注入 fault 在本次设计中保持到全局复位；新 VIO clear 和读 `0x10` 都不清它。

若现有工具只支持 16Byte DMA，可在确认工具支持后从同一基址读 16Byte，只比对前 8Byte。后 8Byte 没有规定值，日志分别写“有效 8Byte/请求 16Byte”，不要改动 `0x1C` 的含义。

### 8.2 不归还时的稳定性与多块

先形成一块且不写 `0x14`，在 1 秒内多次读 `0x18/0x1C/0x34`，应保持相同；读清通知也不应改变它们。之后完成 C2H 和一次归还。

多块测试从空队列开始，逐次 start=0→1，每次等 busy=0 且块数增加后再产生下一次。先积 2 块，再可扩展至 8 块；不得在 busy=1 时快速连续点 start。每次形成一个 8Byte 块；队头不因后续入队改变。

读取流程：读 `0x30` 得 N → 重复 N 次“重新读队头地址/长度/序号 → C2H 完成并比对 → 写 `0x14=1` 一次” → 再读 `0x30`，继续至 0。第一次序号可为 0；第 8 块之后的环形地址必须使用返回值，不在软件中自行加地址。

VIO 发生器在队列满 8 块时会拒绝新启动，不能用“第九次点击无响应”证明真实 Aurora 流的溢出策略。真实流过载、连续接收、接收 FIFO 及 CDC 要在正式接收模式下另测。

### 8.3 用户通知测试

轮询闭环通过后，先排空队列，使能现有工具的 XDMA 用户通知并开始等待 → FDMA ILA Run Trigger → 旧 VIO start=0→1 → 保存通知日志及 `0x2C` → 单独读 `0x10` 清通知 → 按 `0x30` 把队列读完并归还。

中断次数不是块数。已有待取块时再次入队不保证每块一次新通知；读清后队列仍非空时不能只等下一次通知。保留 `0x30` 轮询兜底；只有一个流程负责清通知和归还，防止双重确认。用户通知与 DMA 完成是不同事件，不能为避免自动清通知而整体关闭 DMA 完成所需的机制。

## 9. 下行业务、GPIO 与 1G 周期帧

### 9.1 10G 下行发送

1. 第 7 节 DDR 写后回读先通过；确认实际 10G 对端能够接收。当前 VIO 上行模式不妨碍下行；但当前 VIO/ILA 不直接提供 10G channel_up 探针，需要对端/板级现有手段确认。
2. 等 `0x20=0`。H2C 将第 7 节 16Byte 数据写到 `0x8000`，等待完成；写 `0x24=0x8000`、`0x28=0x10`，读回。
3. FDMA ILA 用 `fdma_rareq==1` 为唯一条件，**先 Run Trigger**；再由软件写 `0x20=1` 一次。
4. 轮询 `0x20.bit0` 到 0；不要求一定采到中间的 1。FDMA 期望 `raddr=0x8000`、`rsize=2`，在两次 `fdma_rvalid=1` 的有效拍看到 `0706050403020100`、`0F0E0D0C0B0A0908`。
5. 对端核对收到一个完整 16Byte 帧及全部内容；保存 `0x2C/0x38` 和诊断计数。

仅 `0x20` 回 0 不足以判成功：非法参数、链路未就绪或中止也可回 0。FDMA 看见两拍仅证明业务读接口活动，不证明 Aurora 对端已经接收。没有对端时，只把 DDR 搬运和启动返回记录为对应的局部检查。

合法下行地址范围 `0x8000～0xFFFF`，起始地址 16Byte 对齐；长度大于 0 且为 16Byte 整倍数，最大 32768Byte，地址+长度不超过 `0x10000`。业务忙时，写 `0x24/0x28` 和重复启动会被忽略。

### 9.2 1G 首次配置与外部观察

当前设计在下行业务首个有效读拍提取 Byte1（`fdma_rdata[15:8]`），首次合法编号 1～10 用于锁定 duty/Vin。仅 H2C 写 DDR 不会触发配置，必须实际开始并接受该下行业务读拍。第 7 节数据 Byte1=1，适合作为首次配置。

编号 1：duty=3000（`0x0BB8`）、Vin=`0x00500000`。预期 1G 完整 16Byte 帧：

```text
B8 0B 00 00 50 00 F0 00 00 00 00 00 00 00 00 00
```

1G 用户接口按先发字节放高位的四个 32bit 拍观察，应为 `B80B0000、5000F000、00000000、00000000`。Byte6=`F0` 是同步标识，不要把 10G 下行原始 16Byte 帧与查表产生的 1G 帧混成同一数据格式。

配置保持到主机全局复位；第二次提交不同合法编号不覆盖第一次配置。要测试全部编号，需逐次以可识别的新复位/冷启动现场开始，重新做启动检查。当前 1G configured、configured_id、tx_valid/ready/data、skipped_periods 没有进入已实现的 VIO/ILA 或 BAR，不能在 GUI“+”中凭名称添加；用对端验帧或外部设备结果记录。

1G 发送尝试由 250MHz 的每 500 拍源事件产生，间隔 2µs。跨到 31.25MHz 用户域后发送四拍；反压或正在发送会跳过周期，不保证对端每 2µs 都收到一帧。50µs GPIO 每周期含 25 个 2µs 源事件，和源时间基准相关，但不能据此承诺 CPU 收到 GPIO 与子机完整帧到达完全同时。

外部接线依据当前 XDC：1G RX AH2/AH1、TX AH6/AH5、参考 AB6/AB5；10G RX Y2/Y1、TX AA4/AA3、参考 V6/V5。只供核对已知接线，不在本轮修改这些管脚。

## 10. ILA 设置与触发方法

### 10.1 实例选择、按钮和窗口

`hw_ila_1` 等编号可能变化，始终按实例路径选核。当前四组为 PCIe 原生、FDMA、温度、PHY，全部探针见附录 B。

第一轮统一用 `CONTROL.CAPTURE_MODE=ALWAYS`，即每个采样时钟连续存储；Trigger Mode 为 BASIC_ONLY；单窗口，FDMA/温度 1024 点、PCIe/PHY 2048 点；触发位置可先用 128。GUI 中找不到 Capture Mode 时用本手册附带 helper 设置，不必在 Settings 面板反复查找。

VIO/FDMA/温度/PHY 观察使用板载 250MHz，4ns/点；1024 点约 4.096µs，2048 点约 8.192µs。PCIe 原生 ILA 使用 XDMA `axi_aclk`，不同于板载业务时钟，即使请求配置名义为 250MHz，也应按实际时钟周期换算，不能套用所有板载窗口。100ms 块周期无法用一屏连续 ILA 覆盖；FDMA 抓单次写，VIO/寄存器看块登记。

| 目的 | 核 | 触发条件 | 先后顺序 |
|---|---|---|---|
| 看当前 link/LTSSM | PCIe 原生 | Immediate | 点击 ▶▶，无需软件或 VIO 操作 |
| 上行注入写入 | FDMA | `fdma_wareq==1` | 先 ▶ 等待，再旧 VIO start=0→1 |
| 下行业务读出 | FDMA | `fdma_rareq==1` | 先 ▶ 等待，再软件写 `0x20=1` |
| CPU H2C 写入 DDR | PCIe 原生 | `ila_axi[1:0]==2'b11`，其余位 X | 先 ▶ 等待，再 H2C |
| CPU C2H 读取 DDR | PCIe 原生 | `ila_axi[7:6]==2'b11`，其余位 X | 先 ▶ 等待，再 C2H |
| 观察掉链 | PCIe 原生 | link probe1 的下降沿；或已建立后比较等于 0 | 先布防，再等待真实事件；不以复位 CPU 制造本轮故障 |
| 独立看 GT/复位 | PHY | Immediate | 点击 ▶▶；不需要发业务 |
| 温度 DRP | 温度 | `den_in==1` | 先 ▶，等约 1ms 周期，无需发业务 |

PCIe 原生 ILA 的 probe1 在 GUI 叫 `ila_flags_1`，probe2 叫 `ila_flags_2`，probe3/4 为 `_3/_4`；无数字后缀的 `ila_flags` 是 **capture_event**，不要误当 link。以 LTX/附录映射为准。

本轮 helper 只采用普通连续采集，不启用稀疏事件存储。旧事件 CSV 曾出现 event 全 0 且 ticks 步长 1，不能作为跨毫秒稀疏历史。将来启用 BASIC 事件存储后，需确认保留样点事件位有效并用 ticks 差值还原间隔；不能把点序号直接当连续时钟。

### 10.3 保存失败现场

出现超时、数据不一致、fault、掉链或新 DDR 错误：停止产生新业务 → 保存软件日志及无副作用寄存器 → `snapshot` 保存 VIO → 保存已完成 ILA → 需要时再读一次 `0x10` 并注明该读清动作。DMA 失败时不写 `0x14`；不要先 clear、Program 或重启后才取证。

PCIe 不能建链时，现有只读内部调试脚本仍可作为补充：

```tcl
source C:/project/RTDS/DDR/RTDS_test_DDR4_64bit_batch_dev/debug/pcie_diag_20261014/read_pcie_receiver_detect.tcl
```

它访问 PCIe 核内调试地址，不访问业务 BAR/DDR。确认签名 `ABCD` 和 lane 数 2；Receiver Detect 的 PHYSTATUS=1 且 RXSTATUS=011 表示检测到远端接收器，000 表示该记录未检测到。该检测看 FPGA TX→CPU RX 终端，不等于 RX 数据收发正常。前几槽为早期记录，末槽会更新，不能把四槽当当前同一轮连续采样。

## 11. 故障现象与下一步

| 现象 | 先看什么 | 下一步 |
|---|---|---|
| LED17 灭，固定寄存器错误/全 FF | bit/LTX/MCS 身份、软件所用用户 BAR、访问错误码、live bit3/4 | 先核对映射和访问宽度，不因 LED 灭直接判数据接口通过 |
| BAR 能读，PCIe ILA 没触发 | 当前操作是否只是 BAR；ILA 是否布防了 DMA AXI | BAR 不在该 ILA，改以寄存器结果验证；做 H2C/C2H 时再采 |
| H2C/C2H 通过，FDMA ILA没触发 | 是否只做了直接 DDR 搬运 | 属于不同接口，按第 9 节提交业务后再抓 FDMA |
| start=1，busy/块数不变 | start 是否真的提交 0→1、busy、fault、就绪、blocks 是否已满 | 先满足条件；忙时/未就绪时的边沿被丢弃，不自动排队 |
| accepted=2，块迟迟不就绪 | 是否已等 100～200ms、fault、DDR_STATUS、FDMA 状态 | 保存现场；不将“两个字已接受”当写成功 |
| `0x10=0`，`0x30>0` | 是否有后台读清或先前已清通知 | 仍需按队列取块；不要只等待新通知 |
| 读清后块还在 | `0x30/0x18/0x1C` | 正常；C2H 完成比对后才写 `0x14` |
| `0x20` 很快回 0 | 对端是否就绪、FDMA数据、实际对端结果 | 可能正常结束也可能拒绝/中止，没有独立成功结果码 |
| `live[2]=1` 但 link=0 | live[0/1/3/4]、history、LTSSM、PHY | 时钟存在不代表 link；保留冷启动配置与Receiver Detect证据 |
| PCIe VIO 快照不更新 | uptime、seq、age、clock_alive | age 增长且时钟活性低时原生快照是旧值，不继续解读旧 speed/width |
| PHY 某个 CPLLLOCK=0 | QPLL1LOCK及当前 plltype | 当前使用 QPLL1，CPLL 未使用，不能要求十位全部为 1 |
| Xicom 50-38/调试链读取错误 | 是否仍处于 SPI 辅助设计、LTX是否匹配、JTAG状态 | 固化结束后冷启动重新识别；必要时降低JTAG频率并重连，保留日志；不据此直接判PCIe失败 |
| GUI波形为空但核可见 | 是否添加探针、是否已有采集、ILA时钟是否运行 | 先“+”添加信号，再按本章触发；不自动重建工程 |
