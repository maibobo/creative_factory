# RTDS 主机单机 VIO 上行激励设计方案

版本：V1.0　核对日期：2026-10-13

适用工程：RTDS_test_DDR4_64bit_batch_dev。以远程当前 RTL、XPR、VIO IP、TOP.ltx 和当日验证记录为依据，并结合 E:\codex_history_md\PCIE-CPU 今天更新的记录。

## 1. 设计目标与当前结论

主机暂时没有子机参与，真实 Aurora 上行没有数据来源。本方案由 Vivado 的 VIO 输出一次启动电平，驱动可综合固定数据发生器，在原接收 FIFO 之后向真实 block writer 注入两个 32bit 有效字。数据随后经过原 FDMA、AXI、backend 和 DDR 通路，形成真实可读块，再由原寄存器和用户中断通知软件。

VIO 只负责触发和观察，不直接写 DDR，不伪造块数量或中断，也不新增 BAR 寄存器。驱动可先观察动态 BAR 状态与清通知，再接入 C2H DMA 完成数据读取和单块归还。

当前方案已经实现。RTL 默认 RX_VIO_TEST_ENABLE=0；远程当前工程 generic 为 1，选择测试源。2026-10-13 10:44 已生成包含 VIO 的新版 bit/ltx；当次 routed 报告满足已指定时序约束。四项快速冒烟及完整 TOP RTL elaboration 已通过，模型与板级边界见第 8 节。

本方案验证的是接收 FIFO 之后的上行存储和软件交互。Aurora 接收、接收 FIFO 与其跨域不在这次注入覆盖范围内。无子机时，上行 VIO 测试与下行 DDR 写后回读可以独立执行；完整下行 Aurora 发送仍要求实际链路条件成立。

## 2. 注入位置与模块职责

正式路径：Aurora RX → 接收 FIFO／跨域 → block writer → CONV_DMA → 共享 AXI 通路 → backend／Clock Converter／MIG → DDR4。

测试路径：JTAG／VIO start → RTDS_RX_VIO_STIM → 原 block writer → 原 CONV_DMA／AXI／backend／MIG → DDR4 → XDMA C2H → RK3588。

完成反馈：原 writer 的成功非空块登记事件 → 发生器等待结束；同一 writer 维护可读块队列，并通过 INFO_EXCH 和 XDMA 用户中断通知 CPU。

## 3. 触发原理与发生器状态机

VIO 的 probe_out0 是 start，默认 0。发生器使用同一个 250MHz 业务时钟，先采样为 start_r，再保存上一拍为 start_d，以 start_r && !start_d 检测上升沿。保持 start=1 不重复触发；再次测试需要提交 0，再提交 1。

启动只在 IDLE 接受，条件同时包括：start_edge、上一拍寄存的就绪／空块判断 can_start_r、当前 store_ready，以及 fault=0。其中 store_ready 沿用原 DDR 就绪与已同步 PCIe 建链条件，can_start_r 还要求可读块数小于 8。无需 Aurora 建链，但仍需要真实 DDR 与 PCIe 就绪。

忙时或未就绪时的 start 上升沿被忽略，不排队。若在未就绪时已经把 start 拉高，后来就绪不会自动启动，必须重新操作 0→1。

| 状态／编码 | 输出和动作 | 转移条件 | 设计目的 |
| --- | --- | --- | --- |
| IDLE／0 | valid=0、busy=0；合法触发时计数清 0，预置首字 0x11 | 满足启动条件 → WAIT_TICK | 一次触发对应一次任务 |
| WAIT_TICK／1 | busy=1，暂不提供数据 | 收到寄存后的原周期事件 tick_r → SEND_FIRST | 避开触发恰在周期末造成的拆块风险 |
| SEND_FIRST／2 | valid=1，数据为 00000000_00000011；反压时保持 | valid && ready → 计数为 1，换为第二字，进入 SEND_LAST | 第一个字确实被 writer 接受后才前进 |
| SEND_LAST／3 | valid=1，数据为 00000000_00000022；反压时保持 | valid && ready → 计数为 2，撤销 valid，进入 WAIT_BLOCK | 两个字按固定顺序发送 |
| WAIT_BLOCK／4 | valid=0、busy=1，accepted_words 保持 2 | 原成功块登记事件的寄存副本 committed_r → IDLE | 等真实块可读，不把输入接受当成写成功 |

正常状态序列：IDLE → WAIT_TICK → SEND_FIRST → SEND_LAST → WAIT_BLOCK → IDLE。

### 3.1 为什么数据和 valid 要寄存

frame_data 和 frame_valid 都由时序逻辑输出。writer 未接受时状态不前进，数据和 valid 保持；第一字被接受后才切换第二字。VIO 控制不直接组合驱动 64bit 数据或 FDMA 请求，控制路径与数据输出之间有寄存器边界。

发生器的 frame_data 接口为 64bit，但 writer 每次只取低 32bit。因此这里“两拍”是两个 writer 输入字，不是两个 DDR 64bit 写拍，也不是两个 Aurora 帧。

### 3.2 异常退出

处于 busy 时，如果 store_ready 失效，或出现 fdma_wdone && fdma_werror，发生器撤销 valid、返回 IDLE，并置 fault=1。非法状态也置 fault。fault 保持到全局复位，不提供 VIO 清 fault 或软件清 fault 命令。

fault 是本次测试源的失败锁定，不是原 DDR_STATUS 的粘滞错误位。读 0x10 可以清原通知和相关业务异常，但不会清这个 fault。异常后 busy=0 不代表成功；应结合 fault、块数、原 DDR 状态和数据结果判断。

发生器停止并不擦除 DDR，也不清除 writer 的半字、旧队列或已接受事务。通过 fault 禁止再次注入，避免把异常残留数据与下一次固定数据混合；保留诊断后用全局复位重新开始。

## 4. 周期对齐、DDR 写成功与块可读

### 4.1 为什么触发后不立即发送

writer 的生产周期为 250MHz × 25,000,000 拍，即 100ms。周期计数独立运行，不由 VIO start 重新计时。如果在周期末立即注入，第一字可能作为尾字单独封存，第二字落入下一周期。

发生器先等待原 debug_period_tick，事件经 tick_r 寄存后才提供数据。writer 在封存过程中会撤销 frame_ready；发生器保持首字，直到 writer 完成当前周期封存并重新允许输入。正常就绪、短反压下，两个字在新周期内完成。

从触发到块可读，通常包括“等当前周期结束”和“等新周期结束”两段，约 100～200ms，再加写响应、封存及观察延迟。这是正常条件下的预估，不是硬件保证的截止时间。软件初测可每 1ms 轮询，500ms 超时后保存现场。

### 4.2 数据如何从两个字变成 8Byte 块

| 阶段 | 数据或事件 | 结果含义 |
| --- | --- | --- |
| 接受第一字 | frame_data[31:0]=0x00000011 | writer 保存待配对半字，尚未证明写入 DDR |
| 接受第二字 | frame_data[31:0]=0x00000022 | 组成 64bit 写拍 00000022_00000011 |
| 提交 FDMA | wsize=1，正常完整拍 wstrb=0xFF | 经 CONV_DMA 生成原 AXI 写事务 |
| 最终写响应 | fdma_wdone=1 且 fdma_werror=0 | writer 才增加成功有效长度 8Byte |
| 周期封存 | 等在途写响应及必要尾字处理完成 | 成功长度非零才登记块 |
| 成功块登记 | debug_block_committed=push_block | 可读块数增加；发生器随后清 busy |
| CPU 读取完成 | C2H DMA 完成并比对 | 数据已交付 CPU，尚未释放块 |
| CPU 归还 | 向 0x14.bit0 写一次 1 | 原 writer 释放一个最老块 |

CPU 小端期望字节：11 00 00 00 22 00 00 00。首次复位后队列为空时，首块地址为 0x00100000，有效长度为 8Byte；后续以 0x18 返回的队头地址为准。

accepted_words=2 只证明两个输入字被接受。busy 清零是“发生器已看到原块登记”的成功路径表现，也可能由异常退出造成；真正的数据结果仍需块状态与 DMA 比对共同确认。

### 4.3 通知和归还保持原协议

空队列登记首块时拉起通知；已有队列再加入新块不保证产生一次新通知。读取 0x10 清通知，不释放块；CPU 写 0x14 才归还最老块。归还后仍有块，通知会重新置位。中断次数不能当作块数量，软件仍应以 0x30 排空队列。

VIO 不访问下行配置。上行注入、通知、C2H 读取和归还期间，0x24／0x28 保持软件原配置。没有新增启动 BAR，也没有改成 BAR 简化版。

## 5. VIO 与内部接口定义

VIO 核路径：u_pcie/G_RX_VIO.U_VIO_RX_START。发生器路径：u_pcie/u_pcie_fdma_aurora_brg_adapter/G_RX_TEST_SOURCE.U_RX_STIM。

所有以下控制、发生器和观察寄存器均使用业务时钟 clk_250m（PCIe 内名 i_sys_clk，adapter 内名 fdma_clk），周期 4ns。它们不是 MIG UI 域或 Aurora 用户域。JTAG 更新由官方 VIO 核输出到此业务时钟域；start_r／start_d 用于采样和边沿检测，不被描述为新增的异步 CDC 同步器。

### 5.1 VIO 全部五个端口

方向以 VIO 核为参考：OUT 为 VIO 驱动业务，IN 为业务状态送入 VIO。

| VIO 端口 | LTX 对应信号 | 位宽／方向 | 含义 |
| --- | --- | --- | --- |
| probe_out0 | u_pcie/rx_test_start | 1bit／OUT | 唯一操作入口；0→1 触发一次，初始化为 0 |
| probe_in0 | u_pcie/rx_test_busy_r | 1bit／IN | 寄存后的 busy，覆盖等待周期、两字发送和等待块登记 |
| probe_in1 | u_pcie/rx_test_accepted_r | 2bit／IN | 寄存后的本次已接受字数，0、1、2；空闲成功后保持 2，直到下次合法启动或复位 |
| probe_in2 | u_pcie/rx_test_status_r | 4bit／IN | bit0 DDR_READY；bit1 已同步 PCIe link；bit2 测试 fault；bit3 原上行通知请求 |
| probe_in3 | u_pcie/rx_test_blocks_r | 4bit／IN | 寄存后的原可读块数，0～8；不是发送字数 |

状态例子：0x1 表示 DDR 就绪、PCIe 未就绪，不能触发；0x3 表示 DDR／PCIe 就绪且没有 fault／通知；正常首块通知后可见 0xB。即使状态低两位为 3，仍要检查 fault=0、busy=0、块数小于 8。

观察量在 PCIe.v 中额外寄存一拍，减轻业务信号直接连接调试核的负载。因此面板状态相对业务事件至少晚一个业务拍，再叠加 JTAG 刷新时间；VIO 适合看保持状态，不能靠面板刷新捕捉一拍事件。

### 5.2 发生器的关键输入和状态

| 信号 | 位宽 | 来源或规则 | 作用 |
| --- | --- | --- | --- |
| rst_n | 1 | fdma_rstn | 全局清状态、数据、valid、计数与 fault |
| store_ready | 1 | ddr_ready && pcie_link_up_fdma | 保留原业务存储允许条件 |
| ready_blocks | 32 | 原 writer 队列数量 | 启动前要求小于 8 |
| period_tick／tick_r | 1／1 | 原 tick，寄存一拍 | 等待周期边界后再发送 |
| block_committed／committed_r | 1／1 | 原 push_block，寄存一拍 | 等待真实成功非空块登记 |
| write_error | 1 | fdma_wdone && fdma_werror | 最终写失败时锁定 fault |
| frame_data／frame_valid／frame_ready | 64／1／1 | 数据与 valid 寄存输出；ready 为原 writer 接受条件 | 以 valid && ready 接受一个低 32bit 字 |

### 5.3 与原 ILA 的配合

原 FDMA ILA 不新增探针。上行以 fdma_wareq==1 触发，可见低 32bit 写地址、wsize=1、wdata=00000022_00000011、写源 valid，以及 writer 的 0→1→2→3→0 状态。

fdma_w_source_valid 不是接受脉冲，原 ILA 也没有 wstrb、wdone、werror、B 响应或发生器 state。故 ILA 看见写请求不等于写成功，VIO accepted=2 不等于块完成，必须结合原寄存器和数据比对。

## 7. 主机单机联调执行顺序

### 7.1 FPGA／Vivado 操作

1. 使用与 RX_VIO_TEST_ENABLE=1 对应的同版 bit／ltx，刷新器件后确认上述 VIO 核存在。版本寄存器常量未因本修改更新，不能仅凭 0x00 读值识别是否加载 VIO bit。
2. 打开 VIO Dashboard，确认 busy=0、fault=0、可读块数小于 8，status 的 DDR／PCIe 位均为 1。建议先清空旧队列。
3. 在原 FDMA ILA 设置 fdma_wareq==1，点击 Run Trigger 并确认等待触发。
4. VIO 将 start 提交为 0，再提交为 1；提交的是实际输出更新，不只是编辑显示值。
5. 观察 busy 变 1。等原周期边界后 ILA 触发；accepted_words 变 2 后仍可能 busy=1，继续等块登记。
6. 成功后 busy 回 0、可读块数增加。保持 start=1 不再次发送；下次测试要重新提交 0→1。

### 7.2 驱动／软件操作

| 顺序 | 操作 | 判据或注意事项 |
| --- | --- | --- |
| 1 | 映射用户 AXI-Lite BAR，32bit 小端访问，确认 0x00／0x04／0x08 | 期望 00002001／20260914／00040000 |
| 2 | 确认 0x2C 低两位为 3，保存 0x38 和 0x24／0x28 | 上行测试不写 0x20／0x24／0x28 |
| 3 | 如有旧块，按正常 C2H 流程读取并归还；随后等待 FPGA 操作 | 初测最好 0x30=0 |
| 4 | VIO 触发后轮询 0x30 | 一次成功触发预期增加一个 8Byte 块；初测可 1ms 轮询、500ms 后记超时 |
| 5 | 读取 0x18／0x1C；先保存 0x2C，再读 0x10 清通知 | 期望长度 8；清通知不减少块数 |
| 6 | C2H 从队头地址读取实际长度，等待 DMA 完成并比对 | 期望 11 00 00 00 22 00 00 00 |
| 7 | 向 0x14.bit0 写 1 一次，最低字节写使能有效 | 只归还当前一块；无需再写 0，不靠读回值判完成 |
| 8 | 再读队列、异常和丢字状态 | 无新触发时队列为空，地址／长度为 0，丢字不增加，0x24／0x28 不变 |

若第一阶段只调 BAR，可先观察块数、地址／长度、通知清除，不做 C2H；未读块保留。若诊断时直接归还，则必须记录为丢弃测试数据，不能记录为读取比对通过。

中断专项需驱动先注册、启用并等待 XDMA 用户中断，再由 VIO 触发。收到通知后仍按 0x30 取块到空；清通知由一方统一负责。真实 MSI 是否送达 RK3588 必须有驱动现场证据。

| routed timing／新版 bit 与 LTX | 已满足指定时序；LTX 含 VIO | 2026-10-13 实现报告及产物 | 不能证明上板数据和真实 MSI 已通过 |

VIO 集成冒烟使用 RX_PERIOD_CYCLES=2000，在 250MHz 下为 8µs；FDMA／backend 超时参数为 256 拍。生产 TOP 保留 RX_PERIOD_CYCLES=25000000，即 100ms。缩时冒烟证明握手和功能顺序，不证明生产周期的实测间隔。

### 8.2 本方案应如何判成功

一次正常任务必须同时看到：两个输入字被接受；没有 fault；最终写成功；原块登记；可读块有效长度 8Byte；CPU 数据比对正确；归还后数量和队头正确；异常记录与丢字计数不增加。只看到 VIO／ILA 有活动、accepted=2 或中断回调，均不足以代替这些结果。

截至本次资料核对，历史记录已说明板上识别到 VIO，但未提供本次固定数据在 RK3588 C2H 读回及真实 MSI 的完整通过证据。本次工作只生成设计方案，不进行上板触发、烧写或新仿真。

## 9. 设计限制与后续检查

1. 测试模式替换原 FIFO 输出，因此不覆盖 Aurora RX、接收 FIFO 和该跨域；恢复正式模式仍需真实对端验证。
2. 所有启动仍保留 DDR／PCIe 门控。status=0x1 时仅 DDR 就绪，不能通过 VIO 绕过 PCIe 建链要求。
3. WAIT_TICK 提供一个新周期的正常发送余量，但没有对超长反压设置专门截止时间；若阻塞跨过完整生产周期，不能宣称两个字必然同块。正常初测按一个 8Byte 块检查，跨周期阻塞需另做专项。
4. committed_r 观察原块登记事件，没有独立任务 ID 或专用块号关联；正确使用依赖测试源独占、单次任务和先清旧队列。最简发生器不承担通用多源／多任务调度。
5. 发生器没有自己的等待超时计数。若 frame_ready 或块登记始终不出现，busy 可持续为 1；原 backend 超时记录也不等于强制结束发生器。软件超时后应保留状态，检查故障与原通路。
6. 写失败分支、队列满拒绝和超长反压等有 RTL 规则，但本次四项冒烟不代表这些场景均已有直接执行证据。测试数据固定，仅覆盖最小功能闭环，不代替容量、吞吐和随机压力验证。
7. 观察寄存器和 JTAG 刷新有延迟；VIO 用于状态查看，短事件和精确先后仍需 ILA 或仿真。当前 ILA 未导出 backend recovery、写响应及掩码。
