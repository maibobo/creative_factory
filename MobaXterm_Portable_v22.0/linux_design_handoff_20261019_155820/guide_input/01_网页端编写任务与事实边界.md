# 后续网页端编写任务

请结合本包、用户另行提供的最近约1小时对话以及同仓库历史资料，输出“当前ARM Linux与主机FPGA板内联调设计指南”。先读事实摘要，再读代码，不要只拼接旧版文档。本包近期讨论文件是要点整理，不是完整逐字聊天导出；网页端不会自动继承本地会话。

## 必须回答

- 区分ARM用户态应用、ARM内核XDMA驱动、FPGA XDMA IP、FPGA业务FDMA。逐项列出运行位置、源码位置、设备节点、调用接口、依赖及当前缺失代码。
- 解释Python主入口、C helper main、open/lseek/read/write如何联系；普通文件fd与XDMA字符设备fd如何不同；DMA地址与BAR寄存器地址、CPU虚拟缓冲区地址如何不同。
- 下行先H2C把CPU数据送入FPGA DDR，再配置业务地址/长度并触发；上午只验证DDR往返和配置回读，未写0x20启动真实对端业务。
- 上行VIO源→业务FDMA写DDR→队头寄存器→C2H读取→比较/处理→ACK归还；通知读清与归还独立；所有权、超时、短传输、失败不归还。
- 列明部署、编译、环境依赖、基本运行、日志、监视器、ILA/VIO关联；本地或远程PC只是控制入口，实际DMA都在ARM执行。
- 给出应用同事接入方式：调用helper进程，或抽取C函数接入已有main；不要求重写驱动，不把两个main拼在一起。
- 单列已验证、未验证和后续验收。每项硬件通过结论引用具体run_id或波形证据。

## 文档证据优先级

现场结果与对应源码 > 20261019更正/说明 > 20261016实验手册 > 20261015/13旧操作说明 > 更早的寄存器协议说明。旧文档中“当前实现”等字样指其编写时点，不自动代表今天。若仍冲突，明确标为待核实，不自行改RTL或臆造驱动源码。

本轮目标是单主机ARM CPU↔FPGA，真实子机、Aurora外部对端待后续；不要把VIO替代源的测试说成真实Aurora已经通过。基础DMA通过也不等于全部RTL、全部Linux应用功能通过。

保留RX_VIO_TEST_ENABLE=1、有效8Byte/请求16Byte的区别；helper限制16Byte对齐和32KiB最大值是本测试程序策略，不能扩写为所有XDMA硬件固有限制。

本轮boot_mode记录unknown；接受用户已验证reboot修复，但本轮没有进行reboot专项或区分Flash/JTAG两种启动的独立回归。应用文件保存在ARM持久根分区，断电保留，不自动开机运行。
