## 实际调用

```text
rtds_lab.py (Python main/用例)
  → subprocess启动 rtds_dma (C main)
  → open(H2C或C2H字符设备)
  → lseek(dev, card_addr, SEEK_SET)
  → write(dev, CPU缓冲区, size) 或 read(dev, CPU缓冲区, size)
  → Linux内核中已有xdma驱动
  → PCIe / FPGA XDMA / FPGA DDR
  → 返回完成字节数
  → C保存C2H文件并返回；Python核对长度、数据和寄存器，最后才ACK
```

不用把C main与驱动main链接；内核驱动本来也不是用户态main程序。应用通过系统调用和设备节点访问驱动，不需要本helper链接libxdma或直接使用驱动私有头文件。DMA页映射/描述符/引擎提交由已有驱动负责；未对现场驱动内部实现逐行核对。

H2C时先把输入文件完整读入CPU缓冲区；对XDMA设备的write才发DMA。C2H时对XDMA设备read得到数据，再写入普通输出文件。不能因代码里都有read/write，就把普通文件读写与DMA混为一谈。JSON的completed等于requested且进程退出0，才能算本次helper完整成功；内容正确另由Python逐字节比较。

## 三种地址与控制/数据两条路径

- BAR0物理基址当前0xf0200000；io访问寄存器0x30用0xf0200030。程序从PCI资源表发现基址，不再次叠加FPGA内部AXI地址。
- 卡内DDR地址0x8000或队头返回的0x100000等，通过lseek传给XDMA，不是BAR地址。
- buf是CPU用户态虚拟内存，由posix_memalign分配；不等于FPGA地址，也不保证物理连续，不能直接把buf数值写到业务寄存器0x24。
- 0x24/0x28是FPGA业务使用的DDR地址/字节长度；数据不通过这两个寄存器逐字写入。0x20是业务启动/忙，不是H2C/C2H通道的必需开关。

上行每块重新读0x18地址、0x1C有效长度、0x34序号、0x30数量；C2H后比较有效数据才写0x14=1。读0x10仅清通知，不取数据、不弹队头。2/8/2表示分别积累排空三批，最后队列为0。

## 构建和依赖边界

ARM包根目录执行sh arm/build.sh，用cc -std=c11 -O2 -Wall -Wextra -Werror生成helper。Python核心实验/监视器不依赖Paramiko，Windows远程编排才需要它。ARM需要现有io、设备访问权限、Linux sysfs/procfs与已有XDMA驱动。本包不带ARM二进制、第三方wheel、驱动安装包、密码或私钥；优先在目标ARM重编译。

已有lab_remote.py保留历史默认Windows依赖搜索路径~/.cache/rtds-lab-hostdeps，也可在运行它的Python环境安装Paramiko5.0.0；脚本内现有主机别名vivado-srv需配置OpenSSH，ARM与远程Windows的host key需事先核验。自动脚本不等于通用新环境一键安装器，移植时检查实际路径/别名及Python版本。

仅离线检查可在包内hardware_joint_lab_20261016执行python -m unittest discover -s tests -p 'test_*.py'；Tcl模拟测试另需Python tkinter/Tcl。真实DMA/VIO用例必须按手册独占硬件，不能作为普通离线单元测试运行。
