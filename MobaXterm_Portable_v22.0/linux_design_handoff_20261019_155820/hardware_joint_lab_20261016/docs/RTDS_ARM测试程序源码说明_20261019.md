# RTDS ARM 测试程序源码说明

日期：2026-10-19

## 1. 程序定位

`arm/rtds_lab.py`、`arm/rtds_dma.c` 和 `arm/build.sh` 是运行在 ARM Linux 用户态的联调测试程序。它们依赖系统已经加载并绑定好的 XDMA 内核驱动，通过 `/dev/xdma*_h2c_0`、`/dev/xdma*_c2h_0` 字符设备传输数据，通过 `io` 工具访问 PCIe BAR0 寄存器。

这些文件不是内核驱动，也不会自动完成 FPGA 编程、复位、驱动装卸、用户中断注册或业务程序启停。运行带写操作的实验前，操作者必须确认其他业务程序已经停止，并显式传入 `--exclusive`。

三份文件分工如下：

- `rtds_lab.py`：发现并核对 PCIe/XDMA 设备，读取或写入受限寄存器，编排 DMA 和 VIO/ILA 控制握手，校验数据并保存运行证据。
- `rtds_dma.c`：一次进程只向一个 XDMA 字符设备提交一次同步 `read` 或 `write`，输出机器可读的 JSON 结果。
- `build.sh`：在 ARM Linux 上用系统 C 编译器生成 `rtds_dma`，编译成功后才替换旧二进制。

## 2. 总体数据与控制路径

下行 DDR 闭环的数据路径是：

```text
ARM 数据文件 -> rtds_dma -> xdma*_h2c_0 -> FPGA/DDR 地址 0x8000
ARM 结果文件 <- rtds_dma <- xdma*_c2h_0 <- FPGA/DDR 地址 0x8000
```

上行 VIO 测试的数据路径是：

```text
Vivado VIO 注入测试块
    -> FPGA 上行环形队列
    -> BAR0 队头地址/有效长度/序号
    -> xdma*_c2h_0 读取
    -> ARM 校验前 8 Byte
    -> BAR0 0x14 写 1，归还已验证块
```

Vivado 控制面有两种方式：

1. ARM 直接手动运行时不传 `--control-dir`。Python 在终端逐步提示操作者到 Vivado Tcl Console 执行 `::rtds_lab::inspect`、`::rtds_joint::arm ...`、`::rtds_lab::inject`、`::rtds_lab::save ...` 或 `::rtds_joint::snapshot`，看到动作完成后回到 ARM 终端输入 `PASS`。
2. 现有 GUI 联动时传 `--control-dir`。Python 写入带唯一 ID 的 `request.json` 并等待同 ID 的 `response.json`；PC 侧 `lab_remote.py` 将请求转给已经连接硬件的 Vivado GUI bridge。该方式仍使用用户现有 GUI，不新开 Vivado、不重新连接或编程器件。

两种方式都采用明确的请求—完成握手，不靠固定延时盲目触发。没有收到明确完成响应就停止，不自动重复动作。

## 3. `rtds_lab.py` 结构

### 3.1 参数和运行互斥

测试用例为 `env`、`regs`、`config`、`ddr`、`single`、`multi`。其中 `env` 和 `regs` 只读；其余用例会写寄存器或发起 DMA，必须传 `--exclusive`。

主程序对 `/run/lock/rtds_joint_lab.lock` 持有非阻塞独占锁，覆盖整个实验周期。这样第二个测试实例不能同时消费或确认同一块数据。它还扫描 `/proc/*/fd`；若其他进程已打开本次选中的 XDMA 字符设备，实验会在写操作和 DMA 之前退出。

### 3.2 PCIe 端点与 XDMA 节点核对

程序从 `/sys/bus/pci/devices` 中查找 `vendor=0x10ee`、`device=0x8032` 的端点。找到多个端点时必须用 `--bdf` 明确选择。随后检查：

- BAR0 物理基址非零、覆盖至少 `0x00..0x38`，并且是内存资源；
- PCIe 功能已经绑定到名为 `xdma` 的驱动；
- `xdmaN_user`、`xdmaN_h2c_0`、`xdmaN_c2h_0` 都是字符设备；
- 字符设备的主/次设备号经 `/sys/dev/char` 反查后属于同一个 BDF，避免误用另一张卡的相同编号节点。

虽然检查了 `xdmaN_user`，当前寄存器读写实际使用 `io -4 -r/-w BAR0物理地址`。DMA 使用 H2C/C2H 字符设备。

### 3.3 BAR0 寄存器

下表只描述当前源码实际检查或使用的语义。`0x0c` 虽在安全读取白名单中，但当前程序只记录其快照，不对其字段作判定。

| 偏移 | 访问 | 当前程序中的含义与约束 |
|---|---|---|
| `0x00` | 读 | 身份标识，健康检查期望 `0x2001` |
| `0x04` | 读 | 版本/日期标识，期望 `0x20260914` |
| `0x08` | 读 | 设计能力参数，期望 `0x40000` |
| `0x0c` | 读 | 纳入普通快照，当前程序不解释字段 |
| `0x10` | 读后清除 | 通知状态；仅在通知测试中显式读取一次，要求 bit 0 为 1 |
| `0x14` | 写 | 队列消费确认；数据和状态全部验证后写 `1`，每块恰好一次 |
| `0x18` | 读 | 当前上行队头的卡内地址；空队列结束时应清零 |
| `0x1c` | 读 | 当前上行块有效长度；测试块期望 8 Byte，空队列结束时应清零 |
| `0x20` | 读 | 下行忙状态，健康状态要求为 0 |
| `0x24` | 读/写 | 下行 DMA 配置地址；写操作仅在 `--exclusive` 下允许 |
| `0x28` | 读/写 | 下行 DMA 配置长度；写操作仅在 `--exclusive` 下允许 |
| `0x2c` | 读 | 就绪/错误状态；低两位必须同时为 1，`0x1c` 掩码覆盖的错误位必须为 0 |
| `0x30` | 读 | 上行队列中待消费块数 |
| `0x34` | 读 | 当前块序号；相邻块要求按 32 bit 回绕连续递增 |
| `0x38` | 读 | 丢字计数器；实验期间不能相对基线变化，且基线不能为 `0xffffffff` |

普通 `snapshot()` 不读取 `0x10`，因为读取本身会清通知。程序把“清通知”和“归还队列块”视为两件独立操作：读 `0x10` 后会再次确认队头和计数未变，只有完成 DMA 和数据校验后才写 `0x14`。

### 3.4 DMA 约束

Python 层进一步把 DMA 限制在实验区域：

- H2C 只允许地址 `0x8000`、长度 16 Byte；
- C2H 允许 DDR 地址 `0x8000`，或上行环形区 `0x100000 + N * 0x40000`，其中 `N=0..7`；
- 每次调用 `rtds_dma` 都有超时，超时、非零退出码或完成长度不等于请求长度都立即失败。

上行测试块的有效数据为 8 Byte：

```text
11 00 00 00 22 00 00 00
```

本实验的 DMA helper 主动限制地址和长度按 16 Byte 对齐，因此 Python 对有效 8 Byte 的上行块发起 16 Byte C2H 请求；这不是对所有 XDMA 模式的统一最小长度声明。结果文件保存完整 16 Byte，但只将前 `effective=8` Byte 与期望数据比较；后 8 Byte 是对齐带出的尾部，不作为有效载荷判据。报告会同时记录 `effective=8`、`requested=16` 和 helper 返回的 `completed`。

### 3.5 “失败不归还”原则

消费上行块的顺序固定为：

1. 核对队列计数；
2. 读取并验证队头地址、有效长度和序号；
3. 必要时验证通知清除不会改变队头；
4. 发起一次 16 Byte C2H；
5. 校验前 8 Byte 有效数据；
6. 再做健康快照并确认队头未变化；
7. 记录 `ack_intent`；
8. 向 `0x14` 写一次 `1`；
9. 等待 `0x30` 队列计数减一，再记录 `ack_confirmed`。

在第 8 步之前发生任何失败，代码都不会归还该块。`0x14` 写操作若报错，软件无法确定硬件是否已经接收，因此也不会重试。DMA 超时、DMA 错误或短传输同样不会重新提交，更不会执行 ACK。这样可以避免重复 DMA 或重复释放导致队列所有权混乱。

失败处理只记录 `FAILURE` 和安全寄存器快照，不自动复位、清错、清通知或清队列。`config` 用例是一个有意的例外：其 `finally` 会在硬件仍健康且空闲时恢复测试前的 `0x24/0x28` 配置。

### 3.6 各测试用例

| 用例 | 行为 |
|---|---|
| `env` | 完成设备、驱动、节点、占用情况和基础健康检查，记录 Python 与 `io` 环境 |
| `regs` | 保存基线与最终安全寄存器快照，不写寄存器 |
| `config` | 依次写入并回读 `(0x8000, 0x10)`、`(0x8010, 0x20)`，最后恢复原配置 |
| `ddr` | 把 `00..0f` 共 16 Byte 写入 `0x8000`，再读回逐字节比较；可配合 ILA |
| `single` | 注入并消费 1 个上行测试块，验证通知、队头稳定、8 Byte 有效数据和一次性 ACK |
| `multi` | 分别执行 2、8、2 块批次，共 12 块；验证序号连续、队头不被新入队块覆盖、8 个环形槽均被使用并发生回绕 |

VIO 注入是 FPGA 内部测试源，不能据此声明真实 Aurora RX 链路已验证。

### 3.7 证据文件

每次运行创建独立的 `results/<run_id>/`，若目录已存在则拒绝覆盖。主要文件为：

- `run.log`：每一步的追加式 JSON 事件；
- `result.json`：原子更新的完整运行状态；
- `summary.csv`：最终用例、状态、耗时和错误摘要；
- `ddr_tx.bin`、`ddr_rx.bin` 或 `up_*.bin`：实际发送/接收的数据；
- `program_sha256`：运行时 `rtds_lab.py`、`rtds_dma.c`、`rtds_dma` 的 SHA-256，便于追溯版本。

ARM 墙上时间可能不可信，因此超时和耗时使用单调时钟；PC 时间可通过 `--pc-time` 写入报告。

## 4. `rtds_dma.c` 原理

命令格式为：

```sh
./arm/rtds_dma h2c|c2h DEVICE CARD_ADDR SIZE FILE
```

地址和长度必须 16 Byte 对齐，长度范围为 16..32768 Byte。程序用 `posix_memalign` 分配 4096 Byte 对齐的缓冲区，并预填 `0xa5`。H2C 会在打开 XDMA 节点前先把输入文件完整读入；输入文件不存在或不足 `SIZE` 时不会提交 DMA。

打开 XDMA 节点后，`lseek` 设置卡内 AXI-MM 地址。随后只有一条关键调用：H2C 使用一次 `write`，C2H 使用一次 `read`。普通数据文件的短读/短写可以循环补齐，但 XDMA 的短返回绝不循环补交，因为第一次返回后硬件状态可能已经不确定。

标准输出是一行 JSON，包含方向、卡地址、请求长度、完成长度、单调时钟耗时和错误码。返回码含义如下：

| 返回码 | 含义 |
|---|---|
| 0 | DMA 完整成功；C2H 结果文件也已写入并 `fsync` |
| 2 | 参数、对齐、长度或地址范围错误 |
| 3 | 缓冲区、普通文件或设备打开/定位/结果保存错误 |
| 4 | XDMA `read/write` 返回错误 |
| 5 | XDMA 完成长度小于请求长度；未重试 |

C2H 使用 `O_EXCL` 创建结果文件，避免覆盖已有证据。

## 5. 编译

在 ARM Linux 的包根目录执行：

```sh
sh arm/build.sh
```

脚本实际执行 `cc -std=c11 -O2 -Wall -Wextra -Werror`，先生成 `arm/rtds_dma.new`，编译成功后再用 `mv` 替换 `arm/rtds_dma`。因此编译失败不会主动覆盖现有 helper。输出的架构字符串用于确认构建发生在预期目标机上。

## 6. ARM 手动运行入口

以下命令均在已经部署好的 ARM 包根目录运行。当前部署目录为 `/root/rtds_joint_lab_20261016`；部署状态及源码/二进制哈希以 `validation/deployment_*.json` 为准，直接编辑 Windows 副本不会自动同步 ARM。

只读检查：

```sh
cd /root/rtds_joint_lab_20261016
python3 arm/rtds_lab.py env
python3 arm/rtds_lab.py regs
```

配置与不使用 JTAG 的 DDR 闭环：

```sh
python3 arm/rtds_lab.py config --exclusive
python3 arm/rtds_lab.py ddr --exclusive --no-jtag
```

需要当前 Vivado GUI 人工配合的运行：

```sh
python3 arm/rtds_lab.py ddr --exclusive --capture
python3 arm/rtds_lab.py single --exclusive --capture
python3 arm/rtds_lab.py multi --exclusive
```

这类命令不传 `--control-dir`，ARM 终端会逐步给出 Tcl 操作提示。操作者应在已经连接到正确器件、加载匹配 LTX 且已 source 实验 Tcl 的 Vivado Tcl Console 中执行提示的命令，确认其完成后才回到 ARM 输入 `PASS`。输入其他内容或遇到 EOF 都会使实验失败。运行期间不要另行注入、重新 arm ILA 或让业务程序访问相同 XDMA 节点。

常用可选项：

```text
--bdf 0000:xx:yy.z       多个 10ee:8032 端点时明确选择
--device-index N         选择 xdmaN_*，默认 0
--run-id NAME            指定唯一结果目录名
--output DIR             指定结果根目录
--state-timeout SEC      寄存器状态等待，默认 2 秒
--dma-timeout SEC        单次 helper 超时，默认 10 秒
--control-timeout SEC    人工/文件控制等待，默认 600 秒
--boot-mode MODE         flash、jtag 或 unknown，仅作为报告元数据
--artifacts-manifest P   把 FPGA 工件清单写入结果
```

## 7. 现有 GUI 联动入口及其差别

现有 GUI 联动由 PC 侧程序管理，适合串行执行全部用例并自动回收 ARM 证据。典型流程是：

1. 在已经连接目标板的 Vivado GUI Tcl Console 中 source `vivado/gui_bridge.tcl`；加载脚本本身不执行硬件动作。
2. 在同一 Tcl Console 执行 `::rtds_gui::start`。它先检查当前器件与 VIO 状态，然后创建唯一 jobs 目录并每秒轮询一次请求。
3. PC 侧运行 `pc/verify_gui.py`，或用 `pc/lab_remote.py run ... --jobs <GUI_BRIDGE_READY 输出的 jobs>` 执行选定用例。
4. bridge 对每条请求先改名为 `.working` 表示已经领取，再执行白名单动作，最后写响应；状态不确定的请求不会重新入队。

两种入口的主要差别如下：

| 项目 | ARM 手动入口 | 现有 GUI 联动入口 |
|---|---|---|
| 启动位置 | ARM 终端直接运行 `rtds_lab.py` | PC 侧 `verify_gui.py`/`lab_remote.py` 通过 SSH 启动 ARM 用例 |
| `--control-dir` | 不传 | PC launcher 自动传入唯一目录 |
| Vivado 动作 | 操作者按 ARM 提示手工执行 Tcl，再输入 `PASS` | GUI bridge 从 jobs 目录领取白名单请求并自动执行 |
| 同步依据 | 人工确认 | 请求 ID 和响应 ID 必须一致 |
| 证据回收 | 结果留在 ARM，操作者自行保留 | PC launcher 在成功或失败后尝试下载本次结果目录 |
| GUI 行为 | 操作者直接观察并操作当前 GUI | 复用当前 GUI；bridge 不新开 GUI、不连接硬件、不更换 LTX、不编程或复位 |
| 适用场景 | 单步排查、现场人工控制 | 既有 GUI 下的重复联调和统一证据收集 |

`pc/verify_gui.py` 的既定序列是 `env`、`regs`，等待 GUI bridge，就绪后执行 `config`、`ddr`、`single`、`multi`；其中 `ddr` 和 `single` 开启采集，`multi` 不额外创建大量波形页。这个入口属于 PC 侧联动，不等同于把 GUI 或控制逻辑部署到 ARM。

## 8. 边界与故障处理

- 程序只认可一个匹配端点；设备、BDF、驱动或节点对应关系不明确时退出。
- 寄存器写仅允许 `0x14`、`0x24`、`0x28`，并要求 `--exclusive`。
- DMA 地址和长度由 Python 与 C 两层约束，不能作为通用任意地址读写工具。
- 所有超时必须为正数；超时后保留现场，不做自动重试、复位或 ACK。
- `--no-jtag` 只能用于不依赖 VIO 的路径，不能与 `--capture`、`single` 或 `multi` 组合。
- VIO 测试证明的是内部测试源到 DDR/C2H/队列协议的联调路径，不覆盖真实 Aurora 对端、真实 RX 流量或系统级业务并发。
- 当前程序捕获常见受控错误并写失败报告；断电、内核崩溃或进程被强制终止仍可能只留下此前已经原子落盘的证据。
