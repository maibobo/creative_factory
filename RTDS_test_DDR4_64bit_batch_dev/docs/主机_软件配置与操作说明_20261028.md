# RTDS 软件配置与操作说明

适用当前业务接口 `VERSION=0x00002001`。驱动同事通过现有调试程序完成寄存器访问和 DMA，无需业务应用参与。上、下行可独立测试。

## 1. 软件配置

| 项目 | 推荐值／要求 |
|---|---|
| 寄存器访问 | 用户 AXI-Lite BAR，32bit 小端 MMIO；表内地址均为 BAR 相对偏移 |
| 下行卡端地址 | `0x00008000` |
| 下行写入、回读长度 | 均为 `0x00000010`，即16Byte |
| 上行地址、有效长度 | 每块分别读取 `0x18`、`0x1C`，不能自行递增或硬编码 |
| 初测通知方式 | 轮询 `0x30`；自动测试可用1ms／500ms；**人工观察单独等待确认，超时停止** |
| DMA完成 | 使用驱动完成接口，检查错误和完成字节数；缓存同步、缓冲区对齐及MMIO顺序由驱动保证 |
| 并发 | **同一时刻只允许一条流程执行上行读取与归还**；清通知统一由一方处理 |

**BAR地址、卡端DDR地址、CPU DMA缓冲区是三种不同地址。** 本文 `H2C/C2H` 的地址参数为卡端DDR字节地址，不是BAR地址。下面的函数名是操作示意，应替换为实际驱动接口。

## 2. 初始化

1. 确认PCIe设备枚举、驱动绑定及用户BAR映射成功。
2. 读取并保存：`0x00=0x00002001`、`0x04=0x20260914`、`0x08=0x00040000`。
3. 读取 `0x2C`，业务操作前要求 **`(value & 0x3)==0x3`**。
4. 保存 `0x2C/0x38`。若 **`(read32(0x2C) & 0x1C) != 0`**，**先停止业务并留存现场**；**需要验证读清时才读一次 `0x10`**，复查异常后再决定是否继续。
5. 软件每轮保存丢字基线；测试中 `0x38` 增加即记录丢字。读取 `0x10` 不会清除该累计计数。

### 软件怎样检查DDR状态

**先读取偏移 `0x2C` 的32bit状态值，再对读回值做按位与。** 下列 `read32` 是驱动寄存器读接口的示意名称，应替换成现有接口：

```c
uint32_t status = read32(0x2C);
bool ready = (status & 0x03) == 0x03;
bool has_error = (status & 0x1C) != 0;
```

**这里 `0x1C` 是错误位掩码，二进制为 `0001 1100`，用于检查bit4、bit3、bit2；不是读取偏移 `0x1C` 的上行有效长度，也不是把地址常量 `0x2C` 直接拿来计算。**

| 状态位 | 软件解释 | 判定方式 |
|---|---|---|
| bit0、bit1 | DDR已就绪、校准已完成 | `(status & 0x03) == 0x03` 才满足DDR操作条件 |
| bit2，掩码 `0x04` | DDR访问发生过响应错误 | 非零时保存状态、DMA返回及数据日志 |
| bit3，掩码 `0x08` | 接收发生过溢出 | 非零时同时保存 `0x38` 丢字计数及基线 |
| bit4，掩码 `0x10` | DDR访问或FDMA处理发生过超时 | 非零时停止当前业务，保留超时和状态记录 |

例如读回 `status=0x03` 时， `status & 0x1C` 为0；读回 `0x07` 时，结果为 `0x04`，说明DDR就绪但有响应错误记录。**非零是异常条件，不是通过条件；这些位会保留错误记录，也可能反映之前的异常。** 软件先保存原值、运行阶段及相关日志，再按明确的排查步骤处理，不能一看到非零就自动读 `0x10` 清掉。DDR就绪和错误位是两项独立检查。

## 3. 下行：16Byte写入后回读

### 配置与数据

```text
card_addr = 0x00008000
len       = 0x00000010
tx_buf    = 00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
rx_buf    = A5 A5 A5 A5 A5 A5 A5 A5 A5 A5 A5 A5 A5 A5 A5 A5
```

### 必做步骤

| 顺序 | 软件操作 | 检查结果 |
|---:|---|---|
| D1 | 轮询 `0x20.bit0`，等于0才继续 | 下行空闲 |
| D2 | 写 `0x24=0x8000`、`0x28=0x10`，分别读回 | 地址、长度与写值一致；**配置不会自动启动任务** |
| D3 | 分配符合驱动要求的两个DMA缓冲区，填入上述数据 | 两个缓冲区各至少16Byte，写、读缓冲区分开 |
| D4 | `H2C(card_addr, tx_buf, len)`，等待完成 | 无错误，完成字节数为16 |
| D5 | `C2H(card_addr, rx_buf, len)`，等待完成及缓存同步 | 无错误，完成字节数为16 |
| D6 | 比较全部16Byte，失败时打印偏移、期望值和实际值 | **逐字节一致**；小端32bit读值为 `03020100、07060504、0B0A0908、0F0E0D0C` |
| D7 | 保存 `0x20/0x24/0x28/0x2C` | 忙位为0，配置仍为 `0x8000/0x10`，无新异常 |

本流程通过记录为：**BAR配置、H2C写DDR、C2H回读16Byte及数据比对通过。** 不将其记录为完整下行发送通过。

### 可选：提交命令检查

当前单机测试如果需要覆盖启动寄存器，在D6比对通过后：再次确认 `0x20=0`、地址和长度正确 → 写 `0x20=1`一次 → 轮询直到bit0返回0 → 保存状态及驱动日志。无需先写0，也不要求软件一定采到中间的1。

`0x20`回0只表示任务结束，拒绝、中止也可能回0，不能单凭它判定数据发送成功。忙时不得改 `0x24/0x28` 或重复启动。

有效下行限制：地址16Byte对齐、长度为正且16Byte整倍数、最大32KiB，地址范围 `0x8000～0xFFFF`，地址加长度不超过 `0x10000`。

## 4. 上行：等待数据、读取、比对、归还

**上行不通过写 `0x20` 启动，也不写 `0x24/0x28`。**运行接收流程后等待可读数据即可；无数据超时不能记录为通过。

**上行主机软件不需要构造并通过H2C写入测试载荷**；软件负责准备**C2H接收缓冲区及校验依据**。当前VIO模式由FPGA内部固定源生成数据，PC脚本经Vivado触发注入，ARM软件读取；有效长度8Byte，期望值为 `11 00 00 00 22 00 00 00`。本环境不接子机，上行只使用测试源；真实子机接收属于后续联调，不能套用固定8Byte模式。**接收缓冲区预填A5只是初始化，不是上行载荷**；主机预写DDR再读回只能验证DDR往返，不能据此判定上行接收通过。

| 顺序 | 软件操作 | 检查结果 |
|---:|---|---|
| U1 | 保存 `0x24/0x28`、`0x2C/0x38` 基线，轮询 `0x30` | 数量为0继续等待；超时保存日志，不写归还命令 |
| U2 | `0x30>0` 后，记录本批数量N；读取 `0x18/0x1C`，可选读 `0x34` 作顺序日志 | 数量在1～8；地址为上行块合法基址，有效长度为正、4Byte整倍数且不超过256KiB；本轮单块期望8Byte |
| U3 | 保存 `0x2C/0x38`，再读一次 `0x10` 保存通知并清通知 | **清通知不释放块**，地址、长度仍保持；`0x10=0`不能判定队列空 |
| U4 | 分配并初始化读缓冲区，从返回地址执行C2H，等待完成及缓存同步 | 驱动无错误，完成请求字节数；**本轮演示读取16Byte，仅比较有效8Byte** |
| U5 | 比较全部有效数据 | 本轮为 `11 00 00 00 22 00 00 00`；**数据错误时保存日志，不继续归还** |
| U6 | DMA完成且比对通过后，向 `0x14` 写32bit值1 **一次**，最低字节写使能有效 | **只归还当前最老的一块**；无需再写0，不通过读回 `0x14` 判定成功 |
| U7 | 继续处理本批剩余块，再读 `0x30`，非零继续，直至0 | 每块重新读地址和长度，每块完成后仅确认一次 |
| U8 | 保存 `0x30/0x18/0x1C/0x2C/0x38`，复查 `0x24/0x28` | 无新数据时数量、地址、长度为0；`0x2C` 错误位无新增、`0x38` 未增加，下行配置不变 |

上行合法块基址：`0x100000 + k × 0x40000`，`k=0～7`。软件只校验并使用返回地址，不自行维护块号；复位后首块为 `0x100000`，后续不固定。`0x34=0`不能用来判断没有数据。

若现有工具仅支持16Byte读取，先确认驱动长度与对齐规则；本轮固定8Byte测试可从同一卡端地址读取16Byte，只比对前8Byte，**后8Byte无规定值**。日志区分“有效长度8”和“DMA请求长度16”，不改变 `0x1C` 的含义。

处理顺序示意：

```text
N = read32(0x30)
while N > 0:
    重复N次:
        addr      = read32(0x18)
        valid_len = read32(0x1C)
        C2H(addr, rx_buf, 请求长度)
        等DMA完成并同步缓冲区
        比对valid_len个有效字节
        write32(0x14, 1)       // 本块一次确认
    N = read32(0x30)
```

**DMA失败、比对失败或超时立即退出当前流程并保存日志，不继续执行确认。**

## 5. 中断方式：轮询通过后另测

1. 驱动注册并使能XDMA用户通知中断，先检查 `0x30`；已有数据直接处理，不只等下一次中断。
2. 收到用户通知后，先保存 `0x2C`，再读 `0x10` 清通知，唤醒取数流程。
3. 取数流程仍按第4节处理 `0x30`，逐块DMA、比对、确认，直到队列为空。
4. 保留 `0x30` 轮询兜底；**中断次数不是块数**，读清后队列仍非空时，新数据到达也可能没有新通知。
5. 用户通知与DMA完成事件分别处理。清通知和归还不由多个线程或驱动、应用重复执行；不要整体禁用DMA完成所需的中断。

## 6. 最少日志与通过结论

保存：设备和驱动标识、固定寄存器读值、BAR偏移、DMA卡端地址、有效长度、请求／完成字节数、期望／实际数据、确认次数、`0x2C/0x38` 及错误日志。中断专项另记实际用户通知次数。

- 下行：16Byte写入、回读、全部数据一致，地址／长度配置正确，无新异常。
- 上行：实际读到有效数据并比对，读清不释放块，每块DMA完成后一次归还，队列处理至空，无丢字，下行配置不变。
- 只有寄存器读写或状态变化时，记录为BAR检查通过，不替代DMA数据通路通过。


## 7. 分步操作与实时记录

确认 **`0x24=0x8000` 为卡端地址、`0x28=0x10` 为16Byte长度**；先前将 `0x28` 写成 `0x8000` 属误写。

人工演示按“准备本步→执行一次操作→检查返回与日志→操作者确认→下一步”推进。**数据比较通过后、归还之前也应设置确认点**。当前自动演示只在入队和归还后停留约2秒；提示窗口只读，完整的逐步确认尚未实现。等待操作者不冻结硬件或1G周期发送。

软件观察以寄存器监视终端、测试程序输出及独立提示窗口为主。持续监视不轮询读清寄存器 `0x10`；正式验证通知时才读取一次。轮询可能漏瞬态，应结合本轮事件记录；不能要求0.5秒刷新捕获每次快速队列变化。

## 9. 两个Python程序的职责

工作区启动脚本实际打开的两个Python文件是 `pc/demo_runner.py` 和 `arm/rtds_lab.py`。前者在Windows组织实验，后者部署到ARM Linux执行。它们是用户态联调程序，不是内核驱动；DMA仍依赖已有XDMA驱动和 `rtds_dma` C辅助程序。

### Windows调度程序 demo_runner.py

`demo_runner.py` 建立到 `192.168.50.10` 的连接，组织只读基线、DDR往返、慢速8槽和连续8槽实验。它把阶段和ARM回传事件写入JSONL，供独立提示窗口显示。**它不生成VIO上行载荷，也不产生2µs发送节拍**。

| 函数或类 | 软件职责 | 输出或失败行为 |
|---|---|---|
| `EventLog.__init__/emit/arm_event` | 创建事件输出，记录PC时间和运行编号，转发ARM事件 | JSONL及终端打印；不做DMA |
| `connect_arm` | 使用已保存的主机密钥认证ARM连接 | SSH连接；未知主机密钥或认证失败则退出 |
| `run` | 顺序组织环境、寄存器、DDR及两轮8槽实验 | 每个实验关联运行编号；任何阶段失败即停止 |
| `main` | 解析桥接目录、日志路径、独占声明及密码输入 | 调用调度入口；密码不写入命令参数或日志 |

### ARM执行程序 rtds_lab.py

`rtds_lab.py` 校验设备和BAR，访问业务寄存器，调用C辅助程序完成真实DMA，比较数据并执行队列归还。**DDR往返的 `00～0F` 是Python生成的发送数据；上行的 `UP_DATA` 只是软件比较期望，不经H2C写入上行槽。**

| 函数或类 | 软件职责 | 输出或失败行为 |
|---|---|---|
| `atomic_json/parse_io/compare_bytes` | 原子保存状态、解析目标地址读值、逐字节比较 | 解析有歧义、长度不同或数据不同即失败 |
| `Report` | 保存运行编号、源码哈希、事件和结论 | `run.log/result.json/summary.csv`；保留旧结果 |
| `Hardware.__init__/reject_external_users` | 核对PCIe端点、驱动、BAR、设备节点及其他消费者 | 目标不匹配或设备被占用时停止 |
| `Hardware.rd/wr/snapshot/wait` | 受限寄存器访问、基线采样及状态等待 | 显式控制读清；超时或不确定写入不重试 |
| `Hardware.dma` | 传入方向、卡端地址、长度和数据文件，调用C辅助程序 | 检查实际完成长度；错误或短传输不进入归还 |
| `Control.call` | 请求测试源触发或辅助采证，等待人工或PC控制器响应 | 请求编号必须匹配；不是上行数据传输接口 |
| `Experiments.ddr/config` | DDR16Byte往返；下行地址/长度回读及恢复 | 只构造DDR测试数据；不自动写 `0x20` 启动业务 |
| `Experiments.inject/up/consume` | 一次触发一块，累计队列，再读取、比较并逐块归还 | 检查地址、有效长度、序号和一次归还；失败保留块 |
| `Experiments.health/preflight/run` | 检查身份、DDR状态、丢字基线和空队列，分发实验 | 健康或所有权检查不通过即留证退出 |
| `demo_hold/arguments/main` | 演示停留、参数约束、进程锁及异常收尾 | 固定停留不等人工确认；不自动复位、清错或重发 |

辅助依赖中， `lab_remote.py` 负责远程执行与控制请求转发， `notice_window.py` 只显示事件， `rtds_regs_watch.py` 负责实时寄存器监视。**两个主程序目前均未实现1G到CPU的周期接收专项；现有寄存器写白名单不允许写 `0x20`。**

## 10. 1G到真实CPU的2µs接收实验计划

本项应加入软件操作说明，因为它覆盖之前DDR与VIO实验没有覆盖的CPU接收链路。沿用主机FPGA、真实CPU和CPU侧配套接收模块，不连接子机。这里的1G是现场配套的Aurora链路，**接收程序使用配套模块实际提供的驱动接口，不假定为普通网卡或UDP套接字**。

本节是待执行计划。本次仅增加源码注释及文档，没有发送配置、启动接收或改变在板状态。开始前需确认CPU接收模块对应的设备入口、现有接收程序、缓存容量、原始帧保存方式、计数及硬件时间戳能力；目前不虚构设备节点或可运行收包命令。

### 软件步骤与检查条件

| 顺序 | 软件操作 | 检查结果 |
|---|---|---|
| S1 | 停止其他业务消费者，记录设备、版本、DDR状态、下行空闲、错误及接收模块基线 | 复用此前环境；已有配置及运行中的周期流先记录，不盲目复位或改编号 |
| S2 | 先准备CPU接收程序和日志，确认配套模块能够提供完整原始帧 | 保存帧内容、长度、接收总数、模块错误及溢出；软件单调时间用于过程记录 |
| S3 | 选择首次配置编号，例如Byte1=`0x01`；如已有首次配置，沿用并核实其实际编号 | **首次合法配置保持，后续写入不能当成参数已更新**；换编号须另安排受控复位和复测 |
| S4 | 准备16Byte配置帧，例如 `00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F`；H2C写 `0x8000`，必要时回读比较；确认 `0x24=0x8000/0x28=0x10` | 软件在本项需要构造下行配置数据；**H2C写DDR完成本身不等于1G配置完成** |
| S5 | 在当前链路和驱动满足已有下行启动条件时，通过独立受控流程写一次 `0x20=1`，记录状态及错误 | 现有两个Python程序没有此专项。`0x20` 回0只表示任务结束；若条件不满足，停止并保存现场，不连续重发 |
| S6 | 核对CPU接收模块实际收到的16Byte帧；编号1的预期见下方 | 每帧长度、内容、接收模块状态正确；不能拿VIO上行8Byte模式作本项比较期望 |
| S7 | 在约定观察区间累计帧数、模块溢出/错误及时间信息，比较有无丢收或停顿 | **2µs应由接收模块硬件时间戳或硬件计数证据验证**；Linux打印、轮询及线程唤醒间隔不能证明2µs |

编号1对应的1G接收载荷期望为：

```text
B8 0B 00 00 50 00 F0 00 00 00 00 00 00 00 00 00
```

软件按字节流顺序比较：Byte0～1为duty的低、高字节，编号1对应3000；Byte2～5为Vin `0x00500000` 的低字节在前表示；Byte6固定 `F0`，Byte7～15为0。**CPU实际读取接口若按字或批量返回，应先恢复协议字节顺序再比较。**

2µs是周期发送机会，接收端反压、链路中断等会使实际接收间隔改变；应记录接收模块及发送侧辅助证据。当前固定帧没有逐帧业务序号，不能沿用上行队列寄存器 `0x34` 作为1G收包序号；相同载荷本身也不能证明无丢帧或重复。

通过结论分两层：收到并比较正确帧，可记录“1G到CPU基本收包通过”；具备可靠硬件计时/计数且持续接收无错误后，才记录相应条件下的周期验证结果。**1G的2µs数据流与50µs CPU GPIO同步分别记录。** FPGA辅助调试见同目录 `FPGA_1G到CPU_2us补充调试说明_20261028.md`。
