# RTDS 主机 FPGA 波形功能与设计说明



# 阅读目的与设计边界



本说明围绕主机 FPGA 的实际业务链路解释波形。阅读时先确定数据属于哪个模块、在哪个时钟域被接受，再检查完成事件和状态更新。信号变化反映接口推进过程，数据正确性、数量和异常处理结果由同次运行中的检查共同判断。

主机下行经过寄存器、协议适配器、FDMA、DDR4 后端和 10G 发送桥；上行经过接收 FIFO、有效字提取、FDMA 写入和可读块管理。1G 参数发送从下行真实接受拍提取 Byte1，再通过配置跨域和同源计时形成四拍帧。它与 10G 载荷发送共享参数来源，分别按各自接口推进。

当前活动工程选择 RX_VIO_TEST_ENABLE=1。本次同时保留该模式及 RX_VIO_TEST_ENABLE=0 的检查，分别说明测试数据源和正式接收通路。DDR4 采用接口存储模型，Aurora 物理核采用接口模型；真实 MIG、GT、PCIe Root Port 及板上通信时延不由这些波形判定。

信号表使用从 TOP 开始的真实主机实例层次。独立模块仿真在相同业务模块上观察信号，表中给出它在主机中的对应位置；原始测试台路径单独保存在信号索引。测试环境的参考值和计数器明确归入环境，避免把它们当成 DUT 内部状态。



# 1 adapter 下行控制：把一次软件命令变成受控的数据发送



adapter 连接软件命令、存储读取和异步发送链路。其核心职责是保存本次任务的地址和帧数、决定何时可以读取、统计真正完成的帧，并在失效后把旧事务与后续命令隔开。软件侧结束、FDMA 侧结束、用户侧停止确认分别具有独立条件。



## 1.1 命令检查与任务参数保存



一次任务由 rd_start 提交。起始字节地址需要 16 Byte 对齐，长度需要大于零、为 16 Byte 的整数倍且不超过 32 KiB，请求整体位于 0x00008000～0x0000FFFF。结束地址采用 33 bit 运算检查，保留进位，防止较大的地址与长度相加后回绕成一个看似合法的小地址。

合法命令接受后，tx_base_addr_lo 保存基址，tx_target_frames 保存 LEN/16。后续读取使用已保存的参数；每帧的偏移由发送桥推进。将命令参数与正在执行的读取分开保存，使 CPU 后续的总线操作不会改变在途任务的数据位置。

未就绪或非法命令仍需要结束软件启动状态，同时记录相应错误，并确保没有形成 DDR 读请求。波形应同时观察启动、检查结果、任务有效和 FDMA 请求，才能区分“命令已结束”与“完成了正常发送”。

本轮 adapter_story 检查了未就绪命令结束且无 DDR 访问、32 Byte 合法任务、未对齐拒绝等行为；tx_boundaries 另检查零长度、非整帧长度、越界、超长、32 KiB 最大任务及地址范围末端任务。

## 1.2 读请求、两拍载荷与 Byte1 提取



每个 16 Byte 帧由两个 64 bit 读拍组成。读请求被接受后，FDMA 返回的每拍数据在 fdma_rvalid 与 fdma_rready 同时有效的采样沿进入后续处理。状态跳转或 busy 变化本身不能代替数据接受。

config_read_beat 标识每帧的首个读拍。只有该拍真实接受且属于当前有效任务，才从 fdma_rdata[15:8] 取得 Byte1，并产生 cfg_byte_valid。反压会延长等待，但不会把同一个保持拍重复解释为多次配置。

Byte1 支路只观察数据，不改写两个 64 bit 载荷。1G 模块可以在整个 10G 批次完成前锁定参数。adapter 每帧给出编号事件，1G 参数模块再按“首次合法配置”规则决定是否保存，这两个接受层次需要分别阅读。

## 1.3 发送完成为何以末拍接受为准



用户域只有在 EOF 所在的第二个 64 bit 拍被接受后，才形成一帧完成事件。FDMA 读完说明数据已经从存储侧交出，FIFO 中仍可能存在未发送数据；将任务结束绑定到末帧接受，可以让软件完成状态对应本地发送接口的实际进度。

完成事件通过翻转位进入 250 MHz 域，再恢复为单周期事件并增加 tx_completed_frames。翻转位跨域适合传递这种离散事件，能够避免直接采样窄脉冲造成丢失；连续事件之间仍需满足同步链能够分辨的间隔。

完成帧数达到保存的目标值后结束任务。图中应将用户域 EOF 接受、源侧完成事件、目的域计数、软件结束分别排列，跨域传播时间体现为自然延迟。这个完成只表示主机本地发送，不包含子机计算或执行回执。

## 1.4 正常结束后的停止确认与连续八拍检查



软件命令结束后进入清理过程。adapter 等待 FDMA 旧读空闲、用户域发送桥确认停止，并检查没有迟到的帧完成事件。tx_quiet_count 在这些条件连续满足时计数，到八个 FDMA 时钟后解除 tx_recovering。

这段检查处理的是异步链路两侧对“已经停止”的认识差异。用户域看到任务失效和发送桥复位后，才产生 tx_user_quiet；250 MHz 域等待同步回来的确认，而不是按一个固定延时推断另一时钟域已经处理完成。

当用户时钟停止，确认也无法继续传播。保持恢复隔离使旧完成事件和旧 FIFO 状态不会被下一任务计入。波形中需要同时看到任务有效下降、用户侧确认、旧 busy 和安静计数，单看软件忙位不足以判断下一任务何时能进入。

## 1.5 正常清理期间保存一条新命令



正常完成后的清理期间，软件启动状态已经结束，发送侧仍在等待停止确认。实现允许在该阶段保存一条新的合法命令：tx_deferred_base 和 tx_deferred_frames 保存参数，tx_restart_pending 记录等待启动。

清理完成后才使用保存的参数建立新任务，避免新基址与旧读偏移混用。该结构只有一个等待位置，容量需要按一个命令理解；它不会把任意次数的软件写入扩展为一个任务队列。

异常中止时 tx_recovery_aborted 有效，新命令不会按这条正常完成通路被保存。将两种结束原因分开处理，使错误恢复期间的软件行为有明确结果。暂存命令用例核对保存地址、帧数、新数据、帧完成次数和最终完成事件。

## 1.6 就绪失效后的旧读排空与新任务隔离



PCIe、DDR、Aurora channel 或 lane 的同步就绪条件失效后，adapter 结束当前软件任务并停止新的读请求。该任务后续返回的数据不再进入发送 FIFO，也不再产生 Byte1 配置事件。

已被下游接受的读请求需要把响应取完。fdma_rbusy 仍有效时，适配器继续允许旧读接受，使 CONV_DMA 可以结束在途事务；存储无法给出剩余数据时，后端按事务记录提供错误响应。这使“停止业务发送”和“结束总线事务”可以分别完成。

旧读空闲后仍要等待用户域停止确认。用例先停止用户时钟再触发链路失效，证明等待条件依赖实际跨域确认。时钟恢复并完成清理后，新任务的数据、Byte1 和完成计数重新开始，不把旧事务结果归给新任务。

## 1.7 状态清除、丢字统计和无进展超时



用户域错误状态与软件清除不在同一个时钟域。清除事件使用翻转位传递；250 MHz 域以 user_status_clear_hold 等待旧错误电平下降，再恢复后续错误捕获。这样可以避免软件刚清除的旧高电平经过同步延迟后立即重新置位。

FIFO 丢字和写入器丢字使用 33 bit 中间和汇总，输出为 32 bit 饱和值。统计单位为有效的 32 bit 业务字。满缓存、无存储条件及写响应失败造成的损失需按各自计数来源理解，不能直接按完整光链路帧数解释。

FDMA 监视器在存在等待且没有实际进展时累计计数。默认阈值 65,535 个 250 MHz 时钟约为 262.14 µs；接受请求、数据接受和写完成等进展使相关等待计数重新开始。超时状态用于诊断，旧存储事务仍由后端的恢复逻辑收尾。

本轮波形能够观察清除事件、正常计数和相应恢复过程。32 bit 累计值到达饱和上限的极长运行采用实现核对说明，不把有限仿真中的普通数值变化描述成已经覆盖全部计数边界。

# 2 DDR4 backend：保持接口承诺并结束失效前的事务



backend 位于业务 AXI 接口和存储侧之间，承接的是已被 AXI 接受的请求。DDR 就绪失效后，它仍需要履行这些请求的响应数量和标识约束。事务记录与响应寄存器共同决定恢复过程，存储恢复和业务恢复因此具有不同的条件。



## 2.1 存储可用与业务就绪的两层含义



storage_ready 表示存储接口的同步可用条件。ddr_ready 还要考虑业务侧是否存在未完成的异常收尾。校准或复位已经恢复时，旧 R/B 仍可能因上游反压而等待接受；此时继续保持业务不就绪，可以防止新请求与旧事务交错。

后端分别保存读、写事务的在途信息。读写两个方向独立推进，失效处理也分别跟踪。观察 ready 时，应连同 pending、abort 和已接受事务数量阅读，明确阻止新请求的具体原因。

实际硬件还包含异步 AXI 转换与各时钟域的复位释放过程。接口保持复位并连续满足本域释放条件后才重新工作，不能用单个校准位代替整条接口可用性。模型波形用于解释业务协议收尾，不能证明物理 DDR 初始化时间。

## 2.2 AR/AW 接受时记录原始事务



ARVALID 与 ARREADY 同时有效时，后端保存读 ID 和 LEN+1 拍数；写地址同样在 AW 接受时保存。这些记录来自已经接受的接口事实，恢复时可以继续使用原 ID、剩余拍数和最后一拍位置。

如果只记录存储侧是否“忙”，故障后就无法判断该向上游返回多少拍，也无法区分旧请求和后来重新提交的请求。保留事务信息使剩余响应有确定的数量和身份，CONV_DMA 可以按原来的协议顺序结束。

WVALID 可以先于 AW 接受出现，AW 与 W 分别按各自条件推进。测试驱动持续展示自己的 valid，不把“等待 AW 完成后才允许展示 W”作为唯一驱动方式，以覆盖接口之间的合法等待关系。

## 2.3 已展示的 R/B 响应为什么必须保持



返回数据先进入业务侧响应寄存器。RVALID=1 且 RREADY=0 时，数据、ID、响应码和 RLAST 都属于已经向上游展示的同一拍，需一直保持到接受；B 通道的 BID 与 BRESP 采用相同规则。

存储失效只能改变尚未展示的后续响应。若在反压期间把一个已展示的 OKAY 改成 SLVERR，同一个有效拍就会在等待时改变含义，破坏上游按 valid/ready 保持的协议约束。响应寄存器把这一级接口承诺与后端存储状态分开。

图中应先定位首次展示，再定位故障生效和最终接受。持有期间即使 storage_ready 下降，当前响应仍保持原值。随后产生的错误响应再依据事务剩余量组成。

backend_story 中首个待接受读响应在 226 ns 展示；外部 DDR 复位于 228 ns 拉低，存储就绪在 230 ns 下降。该已展示的成功响应保持，之后尚未返回的读拍使用 SLVERR。成功 B 响应在 458 ns 已展示，随后复位变化同样不能修改它的成功含义。

## 2.4 读中断后的错误响应补齐



失效后无法由存储完成的剩余读拍由后端按原 ID 返回，数据填零，响应为 SLVERR，最后一拍给出 RLAST。剩余数量只在真实接受时减少；RREADY 反压期间保持正在展示的错误拍。

已经展示的成功拍仍先交付，它也占原事务的一个拍数。错误起点需要依据故障实际生效时已经展示了哪些数据来确定，不能把所有故障附近的拍都统一改成错误。

这种补齐策略的目的，是让上游明确收到该事务的结束边界并报告错误。它并不恢复本次读请求的业务载荷；软件重试应等待恢复完成，并按业务要求重新准备或确认存储内容。

## 2.5 写中断后的剩余 W 与唯一 B 响应



AW 已接受后，写端对剩余数据拍仍负有接口责任。发生失效时，后端继续接收并丢弃该事务尚未结束的 W 拍，不把它们交给失效的存储接口。接收完原事务要求的数据后，再给出一次对应的错误 B 响应。

如果故障时直接撤掉 WREADY，上游可能持续展示原 WVALID 并等待；如果过早给出 B，又可能让一个尚未结束的数据序列与新事务混在一起。记录剩余拍数并先结束数据阶段，能够维持写地址、数据和响应之间的对应关系。

错误 B 在反压下保持，接受后才完成旧写事务。若成功 B 在失效前已经展示，则保持原成功响应，避免为同一个 AW 再返回第二个错误 B。

## 2.6 同拍故障、超时与 clear_status

无进展超时记录接口长期等待。backend_story 使用 64 拍、即 256 ns 的测试阈值，让 RREADY 保持低电平，观察超时标志，然后清除诊断。clear_status 不撤销已接受的 AR，也不删除已经展示的 R；放开 RREADY 后原事务仍按原数据和拍数结束。

# 3 CONV_DMA：独立握手、突发拆分与最终响应



CONV_DMA 把简化 FDMA 请求转换为 AXI 读写。adapter 和块写入器关注业务长度与数据，CONV_DMA 负责突发边界、拍数和响应。把这些职责集中在转换模块，避免每个业务模块分别实现 AXI 五通道控制。



## 3.1 AW/W 独立推进及历史端口名的真实含义



写请求保存地址和拍数后进入发送阶段。AW 和 W 分别保持 valid，分别记录接受结果；两者完成后再等待 B。AW 先完成、W 先展示或任一通道停顿，都要按各自的真实握手处理。

该模块保留了历史命名：CONV_DMA 的 fdma_wready 是源数据有效输入，fdma_wvalid 是向业务源返回的接受输出。PCIe 集成层用 fdma_w_source_valid 和 fdma_w_accept 明确这两种含义；adapter 的同名端口则按其自身方向解释。阅读时必须结合方向和连接，不能仅凭 valid、ready 的词尾推断作用。

写末拍被接受后，wbusy 仍保持到最后一个 B 响应被接受。块写入器据 fdma_wdone 与 fdma_werror 决定是否增加有效长度，使数据接受和写成功之间的责任边界明确。

## 4.2 清通知与释放可读块分别执行



读取 0x10 清除通知和相关错误记录，已经形成的可读块继续保留。CPU 按最早可读块的地址、长度与序号完成 C2H 读取，再向 0x14.bit0 写 1 释放一块。这样可以先处理通知，再完成可能较长的数据搬运，期间数据不会因读通知寄存器而被复用。

0x14 的写一操作形成单周期确认，读回为零，不要求先写零。writer 每次看到确认输入就处理一次，因此确认信号的单拍性质由寄存器模块保证。持续多拍的直接确认输入可能连续释放多块，不能把 writer 解释成内部另做了上升沿检测。

在 CPU 确认前，最早可读块的地址、有效长度、顺序号及对应数据保持。多块用例依次读清通知、读回数据再确认，核对剩余数量和下一块信息，用这种闭环判断块数据何时可以复用。

# 5 10G 收发与上行块写入



10G 发送和接收分别通过异步 FIFO 与 250 MHz 业务域连接。发送侧需要对远端接口反压保持在途拍；接收侧需要面对无法依赖本地暂停来消除的持续到达数据。两侧采用不同的保护与统计方式。



## 5.1 两拍成帧、FIFO 余量与发送反压



发送桥每帧读取两拍 64 bit 数据，先进入 512×64 bit 异步 FIFO，再在用户域形成 SOF 和 EOF。FWFT 输出让当前字直接可见，真正出队由发送接受沿控制。

反压期间，当前数据、SOF、EOF 和 REM 一起保持。提前推进 FIFO 读指针会使当前有效拍对应的数据变化；按接受沿推进才能让连续反压和恢复后的数据顺序保持一致。

预取同时考虑 FIFO 水位和一帧所需空间，在近满时暂停新的读取。正在进行的读事务仍按已接受的请求结束，水位保护与请求收尾分别处理。波形应把暂停请求、水位下降和重新读取串起来看。

## 5.2 接收 FIFO、低 32 bit 与丢字计数

## 5.3 写响应成功后才形成有效长度和可读块

周期事件提出收尾要求，在途写继续等待。最后一笔写已成功、没有未配对字且当前块非空时，才记录可读块信息。CPU 因此不会在 B 响应尚未确定时读到一个已经声明完成、实际仍可能写失败的块。

八个块位置顺序使用和回绕，CPU 确认后才能复用。队列已满时保护尚未确认的旧数据，新增数据的损失由计数反映。这里重点观察接口闭环，状态机内部的逐状态细节沿用原有设计说明。

# 6 1G 参数发送与同源计时



1G 支路把下行载荷中的配置编号转成周期参数帧。配置保存、跨域完成、周期机会和实际发出四拍是四个独立过程，需要在波形中分别定位。



## 6.1 首次合法编号与成组配置跨域



编号 1～10 对应参数表，首次合法 cfg_byte_valid 使源域保存 48 bit 参数组。非法编号不建立配置；已经保存有效配置后，后续编号事件按现有规则忽略。该保存点使连续周期帧使用同一组稳定参数。

源域在请求前准备数据，并一直保持到确认返回；目的域整体保存参数组。多位参数不能拆成若干独立单比特同步后再组合，因为各位可能在不同目的时钟沿到达，形成从未在源域存在过的数值。

configured 表示主机内部的跨域配置流程已完成。它用于允许本地发送，不表示子机已接收参数或已完成计算。配置阶段与后续发送阶段分别记录，有利于定位“没有配置”和“已经配置但等待发送条件”两类现象。

## 6.2 四拍帧、反压保持及忙时跳过



当前帧为四拍 32 bit，共 16 Byte，四拍 REM 均表示完整四字节。前两拍按协议安排参数与标识，第三、第四拍填零，SOF 只在首拍，EOF 只在第四拍。状态仅在本拍可以被接受时推进。

无反压时四拍占用 128 ns；反压期间当前拍的数据和帧标志保持。图中逐个用户时钟沿核对 valid、ready 与数据，可确认保持拍没有被重复计入，也没有在恢复时漏掉。

2 µs 事件到达时，若仍在发送或接口不能启动，该次机会计入跳过，不排队补发。采用周期机会而非发送请求队列，可避免一段长期反压结束后集中补发过时的周期帧。末拍接受与新事件同拍时，依据进入该采样沿前的忙状态处理。

现有有效 1G 记录中的首帧在 6896、6928、6960、6992 ns 接受，四个 32 bit 数据依次为 0xB80B0000、0x5000F000、0x00000000、0x00000000。该样例用于说明字节排列；其他编号使用相应参数表数据。

250 MHz 每拍为 4 ns。计时模块每 500 拍翻转一次 2 µs 事件位，每 12,500 拍形成一个 50 µs GPIO 周期，高、低各 6,250 拍。GPIO 上升沿与相应源事件由同一计数域形成，每个完整 50 µs 区间包含 25 次源事件。

事件位同步到 1G 用户域后，通过与前拍比较恢复一次 period_tick。采用翻转事件可跨越 4 ns 源脉冲与 32 ns 目的采样周期的差异。目的域实际看到事件的时间包含同步延迟和采样相位。

GPIO 在 1G 未配置或未建链时继续运行，CPU 可以独立使用该节拍。子机收到串行帧还受到发送等待、链路传输及接收处理的影响，主机源事件和子机实际处理开始需要分别理解。

## 7.2 25 MHz 初始化顺序

计数到 128 附近及饱和 255 后的具体输出沿由寄存器更新决定，波形按实际沿标注。再次主机复位会重新开始初始化。各时钟域复位采用异步置位、同步释放，不要求不同域在同一物理时刻解除。

## 9.1 下行、上行、状态与确认在同一实例中闭环



同一集成实例先通过寄存器提交下行任务，从模型存储读取两拍并检查 10G 帧数据，再从 10G 接收端送入两个有效字，经过真实写通路形成一个可读块。这样可以同时核对 FDMA 历史端口名的映射、mem_* 五通道和 DDR 状态的来源。

上行样例接受低字 0x01020304 与 0x05060708，最终 64 bit 存储内容为 0x0506070801020304。有效长度为 8 Byte。随后读取通知寄存器，确认可读块仍保留，再写读完确认释放它。

该记录在 2150 ns 同时形成可读块和通知，长度为 8 Byte。读清地址接受后，通知在 2178 ns 清除，而块信息继续保留；写入确认后，长度在 2290 ns 归零。这些时刻体现读清与释放块的独立作用。

# 10 如何从文字核对后续波形



每组先定位时钟域与业务入口，再找 valid/ready 的真实接受沿。把数据、长度、地址、ID 和帧末标志放在同一个接受过程内核对，最后观察状态或完成事件。仅有信号变化、某个状态达到目标值或仿真正常退出，都不足以代替这些对应关系。

长过程采用全景说明阶段关系，局部图解释关键接受沿。多时钟过程保留同步延迟，原始 X/Z 与未录制对象如实标注。信号表中的 TOP 层次用于理解主机模块关系；环境变量的原始路径和对应端口另列，避免把参考模型值当作实际中间寄存器。

当前有效的新运行共 54 次通过，另外六组历史波形按依赖及检查记录核验后复用。一次早期连接层采样失败的波形与源码仍保留。有限仿真覆盖本文列出的具体场景，不将它换算为整个设计的代码覆盖率或真实物理接口已通过。
