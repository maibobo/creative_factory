# RTDS历史时序与仿真问题：通俗说明

日期：2026-10-12。主工程：C:\project\RTDS\DDR\RTDS_test_DDR4_64bit_batch_dev。资料来自工程文档、实际报告/日志及E:\codex_history_md\PCIE-CPU。相同根因的多次失败合并讲解；辅助DDR BIST单独标明。本文总结已记录的问题，不把尚未执行的场景写成已发现故障。

当前最直接的结论：远程11:39:31布线报告为WNS=+0.077ns、WHS=+0.004ns，建立、保持、脉宽失败端点均为0，内部未约束端点为0。这是新取得的静态时序结果，替代“仍为−3.210ns”的旧状态；完整TOP的CDC检查、方法学告警与板级验证仍未全部关闭。[E01]

读本文只需记住三个区别：时序违例是“数据或复位释放赶不上要求的时钟边沿”；功能故障是“数据、计数或任务结束行为错了”；工具/测试台失败是“仿真尚未正确运行或检查方法错了”。三者分别列出。

## 一、时序、时钟与复位问题

### T01｜MIG输入时钟接法错误，工程根本走不到布线

现象：9月20日opt_design报Mig 66-99、Opt 31-306。一是差分时钟负端AK16没有进入有效约束；二是曾把MIG输入改接Clock Wizard输出，形成用户MMCM再接MIG MMCM的级联。

涉及代码：TOP.u_shared_100m_ibuf → clk_100m_ibuf → TOP.u_pcie → u_rtds_ddr4_backend → u_ddr4_mig.c0_sys_clk_i。正确接法是一个IBUFDS输出分两路：一路直接进入No_Buffer的MIG，另一路进入CLK_GEN；不能把第二路的MMCM输出再送回MIG。

处理：AK17/AK16及10ns时钟放入实际启用的DDR4_PIN.xdc；保留共享IBUFDS直连。整份旧PIN.xdc带有过时GT位置，曾引入PCIe/1G冲突，因此只迁移所需约束。后续opt/place/route已通过。这是物理时钟拓扑/约束错误，不是某条DDR数据路径跑慢。[E03、E04]

### T02｜PCIe参考时钟没有约束到顶层，很多路径没有被检查

现象：旧报告有16760个no_clock寄存器和48001个未约束内部端点。BD的OOC时钟名pcie_diff_clock_clk_p不能代替顶层pcie_diff_clk_p[0]。

层次：TOP.pcie_diff_clk_p[0] → TOP.u_pcie → design_1_wrapper_inst → design_1_i → util_ds_buf/XDMA参考时钟 → xdma_0_axi_aclk。处理是在有效DDR4_PIN.xdc对顶层建立100MHz参考时钟；后续no_clock及内部未约束端点归零。没有时钟约束时，“没有负WNS”不能说明所有路径合格。[E03、E01]

### T03｜MIG校准状态直接被250MHz寄存器读取

现象：9月20日最差−2.714ns。MIG的calDone_gated_reg_replica产生校准完成状态，经过backend的init_calib_complete和PCIe/BD状态连接，直接进入INFO_EXCH.axi_rdata_reg[1]。源为300MHz，目的为250MHz，旧分析要求只有约0.667ns。

功能影响：软件读0x2C时，跨域状态可能不稳定。处理：backend的ready_sync采用两级同步；软件状态取ready_sync[1]，不再取原始mig_calib_complete。给同步链添加ASYNC_REG、SHREG_EXTRACT属性，只豁免首级异步采样入口，第二级继续检查。历史后续报告该直连违例消失。[E04]

定位层次：TOP → u_pcie(PCIe.v) → u_rtds_ddr4_backend(rtds_ddr4_backend.sv) → u_ddr4_mig(厂商IP校准逻辑)；目的为TOP → u_pcie → design_1_wrapper_inst → design_1_i → INFO_EXCH_0 → inst(INFO_EXCH.v) → axi_rdata_reg[1]/D。旧报告的校准单元中间层级未完整保存在本次可读归档中，不能补造一条网表路径；这里列的是历史记录明确的端点与RTL连接。[E04、E12]

### T04｜两级同步器存在，但首级例外没有真正加载

现象：9月21日剩唯一−2.768ns路径：u_pcie/u_rtds_ddr4_backend/ui_reset_pipe_reg[1]_replica → 同层ready_sync_reg[0]/D。首级允许异步采样，工具却仍按普通同步数据检查。

原因：XDC把set_false_path包在if中，实际read_xdc报Designutils 20-1307，例外未生效。之前在Tcl上下文能找到对象，并不能证明XDC读取成功。

处理：改为直接命令，仅指向ready_sync_reg[0]/D；数量检查留给独立Tcl。ready_sync[0]/Q → ready_sync[1]/D正常计时。后来WNS=+0.011ns，失败端点为0。例外依据是明确的同步器结构，不是简单声称“两个MMCM一定异步”。[E05、E03]

### T05｜读温度的译码路径太长

现象：−0.759ns，数据路径4.131ns，其中布线3.505ns。旧连接把SYSMON的DO直接穿过寄存器地址译码，送到INFO_EXCH的AXI读数据寄存器。

完整模块链：TOP → u_temp_rd(TEMP_RD.v) → sys_mon_inst → inst → inst_sysmon(SYSMONE1.DO)；跨TOP的FPGA_TEMP_W，进入u_pcie → design_1_wrapper_inst → design_1_i → INFO_EXCH_0 → inst → axi_rdata_reg/D。旧具体位号/组合单元未完整归档，不冒充逐单元原始报告。

处理：TOP加入250MHz寄存器fpga_temp_status，先存温度和busy，再交给地址译码。寄存器地址/编码不变，只晚最多4ns。当前定位为TOP.v的fpga_temp_status声明与更新块。历史后续该违例消失。[E04、E12]

### T06｜AXI反压一路传到FDMA超时计数器，组合逻辑太长

现象：约−0.084ns，9级逻辑。业务侧AXI Clock Converter反压，经BD互连、CONV_DMA的握手及发送桥条件，进入adapter的fdma_wait_count使能。

层次链：TOP/u_pcie/u_rtds_ddr4_backend/u_axi_clock_converter；TOP/u_pcie/design_1_wrapper_inst/design_1_i中的AXI互连和CONV_DMA；TOP/u_pcie/u_pcie_fdma_aurora_brg_adapter/u_fdma_aurora_brg_tx；最后回到adapter.fdma_waiting/fdma_progress → fdma_wait_count。此处是已记录的RTL因果链，旧报告未保留每个互连LUT名称。

处理：fdma_waiting_q、fdma_progress_q先打一拍，再驱动计数及错误状态；数据握手不改，65535拍超时报告最多晚4ns。后续违例消失。注意这与S08“空闲误报超时”是不同根因：前者解决速度，后者解决判断条件。[E04、E12]

### T07｜新增恢复复位链的异步CLR入口被当作同步复位释放检查

现象：10月12日10:29/11:15报告WNS=−3.210ns、68个失败端点。最差路径是ui_reset_pipe_reg[1] → converter_s_reset_pipe_reg[10]/CLR，属于Recovery检查，并非DDR读数据Setup。外部DDR复位同步链到同一CLR也出现−2.335ns。

代码层次和全部数据节点见附录P01/P02。业务域与MIG域各有16级converter_*_reset_pipe；共同复位允许异步断言，释放必须分别经过本域16拍。CLR是这条受控复位同步链的入口，不能按一个普通跨域同步释放边沿要求它。

处理：两侧32个复位管线CLR，以及converter_ready_sync的2个CLR，合计34个定点入口例外。保留同步链后续Q→D、业务AXI和MIG内部路径检查。属性只说明同步结构，不会自动代替所有所需约束。[E06、E07]

### T08｜转换器就绪同步首级缺少异步入口例外

现象：−2.715ns，converter_m_reset_pipe_reg[15] → converter_ready_sync_reg[0]/D，300MHz → 250MHz，实际数据延迟仅0.335ns。完整层次与节点见P03。

处理：只豁免converter_ready_sync_reg[0]/D；第二级仍检查。这与T07合起来，在旧routed checkpoint加载约束后，WNS从−3.210ns变成−0.168ns；剩33个端点都在MIG内部，说明跨域入口问题已从该报告中去掉，但当时还没有全新实现通过结果。[E06]

### T09｜MIG内部真实同步路径布线太长

两次出现：9月约−0.068ns、13个端点；10月12日约−0.168ns、33个端点。最新失败样本是MIG事务队列txn_fifo_output_reg[1]经仲裁逻辑到periodic_read_address_reg[34]/CE；同族还有pageInfo → cmdBankP/cmdGroupP、事务队列自更新等。[E04、E06]

300MHz一拍3.333ns。P04的数据延迟3.172ns，布线占67.654%；还要扣除时钟偏斜、不确定性和触发器要求，所以最终差0.168ns。不是因为“官方IP不需管时序”，也不能凭报告认定恢复逻辑是唯一原因。新增逻辑可能改变全局布局，但这是原因推断。

处理：保留MIG原时钟和生成RTL，重新布局布线；必要时使用Explore/AggressiveExplore及布线后物理优化。不能用false path关闭真实同步路径。11:39新route结果已经整体通过；该次TOP.tcl仍显示默认place/route/phys_opt，没有布线后物理优化步骤，所以不能把通过归因于尚未实际执行的优化设置。[E01、E06、E07]

### T10｜约束写在磁盘上，但GUI重跑仍用了旧配置

现象：独立rtds_ddr4_recovery_cdc.xdc曾登记进离线XPR，但11:15实现只读取原两份用户XDC，仍有−3.210ns/68端点；Explore及post-route步骤也没有执行。[E07]

处理：将定点恢复例外并入实际加载的DDR4_PIN.xdc；优化设置由当前GUI Tcl Console执行Apply-TimingFix-20261012.tcl。11:39报告已为+0.077ns。教训是文件内容、当前GUI内存配置、实际TOP.tcl/runme.log是三个观察对象；只看保存后的XPR不能证明下一次实现用了它。[E01、E07]

### T11｜PCIe链路状态、复位及配置确认跨域存在结构风险

9月审计209条CDC-1、1条CDC-7、2条CDC-10。典型完整端点见P09：XDMA.user_lnk_up直接进入INFO_EXCH或TX bridge复位；另外1G配置返回确认在同步器前有组合逻辑。[E08]

处理：adapter用u_cdc_pcie_link_to_fdma同步PCIe链路状态；发送桥两侧复位由各自时钟域寄存并同步释放；1G cfg_dest_ack在目的域寄存；初始化core_reset/gt_reset使用init域寄存输出。board_cdc_smoke通过，只证明所测逻辑。当前11:39仍有TIMING-6/7/51：XDMA与主逻辑虽同为250MHz，工具不能证明共同相位，不能因此直接当作同一个时钟。[E08、E01]

10月10日完整TOP SpyGlass最后为66 Error、46 Warning、63 unsync、8 convergence；51条来自locked/reset链，8条来自GT黑盒边界。复位链、IRQ到XDMA、Gray计数重汇合及IP端口契约仍需逐项审查；后端局部同步约束和静态时序通过没有自动关闭这些问题。[E09]

### T12｜时钟级联、GT位置和外部接口约束告警

当前DRC仍有REQP-1853：TOP/u_clk_gen/clk_wiz_0_inst/inst/clkout3_buf → TOP/U_RTDS_FPGA_1G_INIT/U_BUFGCE_DIV_INIT/I。前一级全局缓冲再接分频缓冲可能增大偏斜；当前没有形成负WNS，但需复核时钟树接法。[E01]

### T13｜旧Aurora OOC DCP占用了PCIe lane0位置

现象：9月22日WNS已正，却有四个PCIe lane0口缺LOC，UCIO-1阻止bitstream。1G XCI已改到X0Y4，OOC DCP仍锁旧X0Y0；GUI又保留旧IP/implemented design状态。[E10]

### T14｜辅助DDR BIST的长组合路径

工程是axi_ddr4_full_bist_2020_2，不是当前RTDS业务工程。300.12MHz域中，读数据期望生成→比较→首错保存挤在一拍，基线−1.330ns/3079端点。P05给出beat_index → first_actual_data/CE的实际完整路径。处理是先采样实际/期望数据，再比较并保存首错。[E11]

辅助MIG也曾有−0.524ns校准路径，布线占91.872%，见P08；随整体布局变化收敛，不手改生成IP。WDATA最后修复已有2-burst随机反压冒烟PASS，但本文未取得对应最新实现通过证据，仍不能借主工程+0.077ns替它签核。[E11]

## 二、仿真暴露的功能故障

### S01｜上行写握手接反，数据进FIFO却写不完DDR

早期PCIe.v按同名连接fdma_wvalid/fdma_wready，但历史CONV_DMA两个端口的实际语义恰好与名字相反。adapter的valid与BD输出接到同一网，接收许可没有正确返回；64拍LocalLink进入FIFO后，rx_burst_done、FPGA_CPU_irq_req和usr_irq_req不出现。

处理：在PCIe.v以fdma_w_source_valid、fdma_w_accept分别连接，沿用已验证harness的交叉映射。7月真实Root Port的Aurora→CPU 512B、IRQ req/ack、C2H逐字节检查通过。修的是封装连接，不是CONV_DMA业务算法。[E13]

### S02｜软件看到下行结束，旧DDR读却没有结束

TC-F11，10月10日。旧任务已提交AR，测试hold_r阻塞R返回后使Aurora或PCIe链路失效。adapter清tx_active、复位发送桥并让INFO_EXCH清0x20；CONV_DMA仍在read_curr_st=3、fdma_rbusy=1，因为fdma_rready变0，剩余R拍没人接受。

恢复后发0x9000、32B的新任务，前两拍仍是旧16B：实际0055000100550100，期望0066000100660200。处理：tx_deliver_enable为0时，fdma_rready取fdma_rbusy，把旧R拍收完但不送TX FIFO，也不产生Byte1配置事件。当前远程TC-F11三种子通过；波形观察0x20、busy、R握手、tx_recovering及新旧载荷。[E14、E15]

### S03｜DDR复位丢掉旧读响应，新任务一直忙

同一TC-F11另一场景：AR已接受后ddr_sys_rst_n拉低。存储侧复位不再返回旧R，CONV_DMA仍按原长度等待；新任务busy=1、fresh_beats=0。只恢复ddr_ready不能补回丢失的响应。

处理：backend记住ARID及ARLEN+1。存储失效时，已展示的R拍保持；未展示的剩余拍补零数据、原RID、SLVERR，仅最后一拍RLAST=1。旧读全部接受前不允许新请求。TC-F13基础1/2/256拍、多个ID、长反压三种子通过；TC-F11当前三种子也通过。[E14、E15]

### S04｜DDR写到一半复位，上游等不到W/B结束

场景：AW已接受，W尚未收完或B尚未完成，DDR失效。直接丢事务会让CONV_DMA永久等WREADY/BVALID；把失败写补成OKAY又会让writer报告不存在的有效数据。

处理：backend记住AWID/原拍数，失效后接收并丢弃剩余旧W；全部旧W收齐才返回一次SLVERR B。已展示的B在反压下不改。CONV_DMA给writer fdma_wdone=1、fdma_werror=1，writer不增加head_len，累加丢字。TC-F14基础与writer错误组合三种子通过；不能由此推导物理DDR内容跨复位保留或部分写能够回滚。[E14]

### S05｜旧帧完成事件迟到，影响下一任务；停钟时不能只等固定拍数

TX EOF在Aurora用户域发生，tx_done_toggle_user同步回FDMA域后才形成tx_frame_done_fdma。任务已经停止时，旧完成事件仍可能到达；若立刻启动新任务，会错计帧数。用户时钟停住时，本域等8拍也不能证明用户域已停妥。

处理：tx_user_quiet给出实际用户域停止确认；等fdma_rbusy=0、确认到达且无旧完成事件后，连续8拍安静再退出tx_recovering。TC-F15覆盖故障相位、旧事件、停钟恢复等，当前三种子通过。安静8拍是满足前置条件后的检查，不是“断链后8拍一定恢复”。[E14、E15]

### S06｜真实MIG与Clock Converter复位范围不一致

只复位MIG可能让转换器一侧留下旧请求/响应。处理：converter_reset_n由主机复位、DDR系统复位和MIG接口复位共同形成；两侧分别同步16拍释放，再同步就绪返回。业务域旧事务记录只在全局s_axi_aresetn复位时清零，DDR单独复位期间仍能补错误响应。

TC-F16独立真实MIG＋converter＋DDR颗粒模型三种子通过：0x8000旧4拍读，已展示首拍保持OKAY，剩3拍SLVERR；重新校准后0x9000新4拍写/读正确。未覆盖当前完整真实XDMA＋共享互连＋MIG组合，也没有板级结果。[E14]

### S07｜正常连续命令被新增恢复隔离误拒绝

上一任务正常结束，0x20清0；软件马上写下一条，tx_recovering仍未退出，合法命令被当作异常恢复期间请求拒绝，后续等待超时。

处理：tx_recovery_aborted区分异常与正常结束；正常收尾允许暂存一条命令，锁tx_deferred_base/frames、置tx_restart_pending，清理后启动；异常恢复仍拒绝。连续任务三种子及真实寄存器边界归档通过。只能暂存一条，不是任意深度队列。[E14]

### S08｜没有任务也出现超时告警

初次恢复修改把非业务阶段fdma_rready常置1；空闲时valid=0，adapter把ready&&!valid算作等待，65535拍后置fdma_timeout_sticky，0x2C bit4误报。

处理：非业务阶段ready取fdma_rbusy；旧读仍忙才收尾，真正空闲ready=0。修正后恢复与隔离三种子通过。超时计数在adapter，不应写成CONV_DMA自行误计数。[E14]

### S09｜下行提交位与读回状态不同，第二次写1不起作用

历史INFO_EXCH的内部提交位仍为1，但对软件读回的结束状态已为0；下一次写1不产生新上升沿。处理：硬件完成事件同步清内部提交状态，统一0x20的启动及结束流程。寄存器模块与连续任务回归提供对应验证。0x20清0只表示任务结束，不等价数据全部成功。[E16、E14]

### S10｜上行过早通知CPU，末写响应/奇数尾字尚未结束

旧方案在末数据拍附近通知，不能证明DDR最后一次B已成功；周期到期时还可能只剩一个32bit字。当前writer先等成功fdma_wdone，再计有效长度；两个字用8B写，单字尾拍WSTRB=0F、只计4B，随后块才可读。[E16]

真实100ms用例采用250MHz、PERIOD_CYCLES=25000000，分别检查周期事件与块可读，包含空块、在途B及奇数尾字。历史三轮功能检查完成，其中种子750318462工具退出超时；该条保留“功能通过/工具退出超时”，不能改写成所有门禁通过。axi_tail读回证明高32bit保持。[E14、E16]

### S11｜读清通知、归还块及并发新通知容易被混为一件事

0x10读清IRQ不释放块；0x14一次确认只归还一块。新可读块通知与旧通知读清同拍时，新通知必须保留，否则软件可能看不到后续块。

当前真实INFO_EXCH五块读取用例TC-F12检查逐块地址/长度、确认后数量和第一可读块依次更新。这里既包含已验证协议，也纠正旧文档/软件使用误解；不是宣称每一种并发主机访问均已测试。[E14、E16]

### S12｜高地址配置失败

10月10日CARD_ADDR_HI=1快速集成失败：RX writer的地址高32bit固定0，高地址参数没有贯穿上行通路。默认高地址0的2113发送帧/24接收帧检查errors=0。

状态：可选高地址扩展尚未实现，不能把默认配置PASS扩大为64bit全地址支持。若需要此能力，需一起修改RX/TX/互连/backend的地址宽度、范围检查及模型，再单独回归。[E09]

### S13｜1G两拍旧版本与四拍目标不一致

F盘活动旧模块仍为两拍6B、局部63拍定时，测试按四拍16B检查而失败；远程当前TOP/模块已是四拍16B，且tick_toggle_2us连接已经存在。把前者写成后者“待统一/未接入”是基线混用。[E14]

当前远程TC-M01、TC-F09、TC-M08三种子均通过。1G四拍32bit：Byte0/1为duty低字节先发，Byte2～5为Vin低字节先发，Byte6=F0，余字节0；REM均3。250MHz每500拍产生源事件，GPIO每12500拍为50µs。用户域31.25MHz量化使SOF间隔出现1984/2016ns；这是采样量化，不能把线上SOF每次恰好2000ns作为已证明要求。[E15]

### S14｜同拍故障补充检查仍有FAIL，不能直接认定RTL错

tb_backend_edge_recovery三种子在k=2期望SLVERR，实际返回OKAY；样本为id=1、resp=0、last=0、data=0853e29274328a91。DDR复位请求到storage_ready下降有延迟，已装入响应寄存器的拍必须保持，即使尚未被RREADY接受也不能改错码。

状态：要按实际storage_ready变化、R寄存器装载和接受时刻重建独立参考队列。基础F13/F14通过仍成立，新增同拍/重复中断/并行集合判据待复核；本次不修改判据、RTL或FAIL日志。[E14]
