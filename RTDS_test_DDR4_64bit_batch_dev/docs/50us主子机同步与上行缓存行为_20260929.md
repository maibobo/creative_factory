## 主子机链路与同步方案（待定稿）

当前主机的 1G 光口 1（125 MHz 参考时钟 AB6/AB5）周期性发送 6 Byte 参数；10G 光口 5（156.25 MHz 参考时钟 V6/V5）用现有 Aurora 双工 IP 下发 CPU 的 16 Byte 原始帧，并接收子机回传。板上另有 1G 光口 2～4、10G 光口 6，启用新口需另行核对两板光模块、布线、IP 和约束。建议复用 10G 光口 5 的主机 TX 方向发同步帧；子机结果从相反方向回传，1G 口继续发送参数。

主机 250 MHz 域可每 12,500 拍产生一个名义 50 μs 事件并编号，通过握手或异步 FIFO 将完整事件送到 10G `user_clk` 域。10G TX 在帧边界优先选择同步帧，不能截断已有业务帧；受反压时保持数据和帧控制信号稳定。子机应在业务入口前识别、校验同步帧，按新序号和 RUN 状态产生一次应用周期触发。协议需确定与现有任意内容 16 Byte 业务帧不会碰撞的类型/长度、序号、CRC 和字节序；此前试验用的 16 Byte `RTDS` 字头不能直接定稿。

在链路就绪、TX 有余量且帧边界优先的条件下，普通业务流不应使同步帧积压一个周期；仍需测量事件到子机应用触发的延迟和抖动。50 μs 硬件同步不需要新增 PCIe 中断；已有中断用于主机 100 ms 上行块就绪。1G 现为 31.25 MHz 时钟下每 63 拍一次发送机会，即 2.016 μs；改成平均 2.0 μs 可交替 62/63 拍，平均 2.5 μs 可交替 78/79 拍，但需另定是否与 50 μs 事件对齐，本次不改节拍。

Aurora/GT CDR 恢复串行数据，不自动同步主机 250 MHz、10G/1G 用户时钟及子机应用时钟。主机周期源到 10G TX 需 CDC；子机 RX 到不同的应用时钟域时也需 CDC；跨域应传完整事件或参数，不能逐位独立同步序号。若子机解析和应用都在同一个 10G RX 用户时钟域，该段无需额外跨域。

两端对应 1G 或 10G 口使用相同的**标称频率和线速**，并不表示两块 FPGA 的时钟同相、同源。各板本地参考时钟有起始相位、频偏和漂移；1G 与 10G 又各自使用不同的本地用户时钟。光纤携带串行比特，接收 GT 的 CDR 锁定该比特流，Aurora 通过接收缓冲和时钟补偿把数据交给**本端** `user_clk` 接口；它完成的是链路数据交付，不会把两板的应用时钟相位锁成同一拍。AMD 的 [Aurora 64B/66B 时钟架构](https://docs.amd.com/r/en-US/pg074-aurora-64b66b/Aurora-64B/66B-Clocking-Architecture)说明用户接口受本端 `user_clk` 约束，[时钟补偿说明](https://docs.amd.com/r/en-US/pg074-aurora-64b66b/Clock-Compensation-Logic)明确允许两端参考时钟存在频差。

所以，**光纤两端的串行接收跨域由 GT/Aurora IP 处理**；应用 RTL 不要把主机寄存器直接当成子机寄存器同步采样。主机 250 MHz 周期源进入本端 10G `user_clk` 要做 CDC；子机从其 10G RX `user_clk` 转到另一个应用时钟要做 CDC，1G 参数转到子机应用时钟亦然。若解析器和使用者同在同一个本端 Aurora `user_clk` 域，则那一段没有额外 CDC。50 μs 同步帧同步的是**计算事件/序号**，不是强制两端时钟边沿重合；两条光链路的传播与缓存延迟也不会自动一致。

### 24 Byte 同步帧与现有 16 Byte 业务帧是否冲突

当前 PCIe→10G 适配器固定将软件下发数据切为 16 Byte 的独立帧；每帧两拍 64 bit，有 SOF/EOF。同步帧若由**单独的硬件发送源**产生 24 Byte 的独立帧，则是三拍 64 bit：首拍 SOF、末拍 EOF，每拍 8 个有效字节。当前 10G TX 的完整字节拍使用 `rem=3'b111`。子机应按握手后的 SOF/EOF 收完整帧、核对有效长度，再将 24 Byte 控制帧与 16 Byte 业务帧分流，并校验控制帧类型、版本和序号。这样无论 16 Byte 业务负载的字节取什么值，都不会与有效的 24 Byte 同步帧重合；不能只扫描 `RTDS` 等魔数来分类。帧边界或长度错误应判为异常，不能把相邻两帧拼接当作同步帧。

主机应在现有固定 16 Byte FDMA 发送器和 Aurora 核之间新增整帧仲裁，保持软件业务帧原样。同步事件在业务帧中途到来时等到下一帧边界；业务帧首拍已呈现并等待反压时也不能抢走它。所选来源的 `ready`、数据、SOF/EOF、REM 和 valid 必须一同保持到握手。**不应把现有 FDMA 适配器的 `FRAME_BYTES` 整体改为 24**，否则原有 16 Byte 下发协议会改变。

### 寄存器和软件流程能否不变

若 50 μs 只用于 FPGA→子机硬件同步，节拍由主机 RTL 自主生成，现有 PCIe 寄存器地址、`RD_START` 下发 16 Byte 业务帧、`CPU_WR_DONE` 完成通知、100 ms 上行块读取和 `CPU_REC_STATE=1` 逐块归还流程都可保持不变；软件无须每 50 μs 写命令或处理中断。可在链路就绪后发送 RUN=0 的同步帧，待**现有**首次合法参数配置和必要的 1G 链路条件具备后再发送 RUN=1；子机还须在收到首个完整 1G 参数帧后才允许开始计算。上述启停规则是待确认的 RTL 协议定义，不需要新增软件操作。

边界是：若要求软件随时控制 50 μs 运行/停止、读取漏发同步帧计数，或按 50 μs 序号逐结果核对，就不能笼统宣称软件完全不变。前两项需要控制/状态接口；最后一项至少需要子机回传可保留的周期序号，并评估当前上行存储不保留帧边界的限制。现有 `UP_BLOCK_SEQ` 是非空 100 ms DDR 块序号，不是 50 μs 周期号。

## 软件来不及取数时，当前上行实际发生什么

`rtl/rtds_rx_block_writer.v` 将上行数据按名义 100 ms 周期封存到 8 个 DDR 块，每块上限 256 KiB，只有**非空且已成功写入**的块才发布给 CPU。`UP_READY_BLOCKS` 是待取块数；`UP_HEAD_ADDR`、`UP_HEAD_LEN`、`UP_BLOCK_SEQ` 指向最老的待取块。块序号是发布序号，空窗口不发布块，也不增加这个序号。

队列达到 8 个未归还块时，写入器对后续读到的数据字执行拒收和丢失计数，**不会绕回覆盖最老的未归还 DDR 块**。`read_block` 只在软件发出 `CPU_REC_STATE=1` 的确认命令时前移一块；清除中断通知不归还块，读取寄存器或仅完成 C2H 也不归还。软件应先读取队头地址、长度、块序号并完成该块 C2H，确认本地数据可用后再写一次 `CPU_REC_STATE=1`。如果未确认，旧块会一直作为队头保留，直到复位或其他外部故障改变状态。

“新数据丢失”有两层边界：上游 `rtl/rtds_rx_frame_fifo.v` 的异步 FIFO 满或不可写时，新的 Aurora 拍不能入 FIFO，直接计数丢失；FIFO 中已排队的旧数据仍可能稍后被写入器读取。若八块已满，写入器继续从 FIFO 取数但拒绝写入 DDR，故随后被取出的数据也丢失。不能精确说某一时刻以后到达光口的每个字都立刻丢，或取走一块就能恢复此前已丢数据。`UP_DROP_WORD_CNT` 汇总 FIFO 与写入器丢失，单位是进入存储路径的 32 bit 数据字，不是 100 ms 块数。

即便八块未满，**当前 100 ms 窗口内单块达到 256 KiB**，后续数据也会被拒收，直到下一块可用；DDR/FDMA 写错误、DDR 或 PCIe 未就绪，以及 FIFO 满也可能造成丢失。因此“软件每 100 ms/500 ms 取一次”本身不保证无丢失：还须在每次取数时把积压块逐块 C2H 并逐块归还，长期平均处理速度不低于非空块产生速度，同时单窗口流量和瞬时 FIFO 压力都不越界。

若恰好每 100 ms 产生一个非空块，且每块不超过容量、无其他丢失，软件一直不归还时，第 1 块在约 100 ms 可读，第 8 块在约 800 ms 可读；从首次可读到八块占满约有 700 ms。其后新增数据开始被拒收。这个“700 ms”是特定流量假设下的缓存余量，不是保证软件每 700 ms 只取一块也能持续运行。已经丢失的数据不会因后续归还而补回。
