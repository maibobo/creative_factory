# RTDS 上板 ILA 抓取步骤与全部探针说明

核对日期：2026-10-13。适用工具：Vivado 2020.2。

远程工程：`C:\project\RTDS\DDR\RTDS_test_DDR4_64bit_batch_dev`。本文按当前 `TOP.ltx` 中实际启用的调试核，以及对应 RTL 连接整理；工程目录中未进入当前 bit 的旧 ILA 不计入清单。

## 1. Vivado 前台打印、软件寄存器和 ILA 各能看到什么

上板后的 Vivado Tcl Console 主要显示硬件连接、烧写、调试核识别、触发和采样上传操作，以及工具报错。仿真中的 `$display`、断言、PASS/FAIL 不会变成 FPGA 上板后的自动打印。脚本可以查询调试核属性、上传并导出已采数据，但不能凭信号名读取任意内部寄存器。

| 获取方式 | 当前可获取的信息 | 使用边界 |
| --- | --- | --- |
| Hardware Manager／MIG 调试界面 | FPGA 配置、调试核、DDR 校准结果 | `CAL PASS` 说明校准通过，不代表业务读写数据比对通过。 |
| FDMA ILA | 业务读写请求、地址、数据、长度及桥状态 | 观察 adapter 的业务 FDMA 通路；不直接观察 BAR 读写或 CPU 直接 DMA 通路。 |
| 温度 ILA | DRP 操作、周期计数、温度原始码及模块 busy | 可独立检查采样活动，不承担 PCIe／DDR 业务验证。 |
| RK3588 软件读用户 AXI-Lite BAR | DDR 状态、下行忙位、上行块数、队头地址／长度及累计丢字 | 只读到 RTL 已映射的状态，不能访问未导出的任意内部信号。 |

当前 bit 没有 VIO，也没有 JTAG-to-AXI Master。Vivado Console 不能通过现有 JTAG 核直接读取业务 BAR。块管理和错误汇总主要由软件读取寄存器；backend 的 `recovery_` 信号既未映射为寄存器，也未接入当前 ILA，因此两边均不能直接查看。

## 2. 当前实际启用的全部 ILA

当前有两组普通 ILA，共 20 个探针。另有 MIG 校准调试核和 debug hub，它们不是普通 ILA 探针组。`hw_ila_1`、`hw_ila_2` 等对象编号可能变化，选择时应核对实例路径。

| 分组 | 实例路径 | 探针数 | 采样时钟连接 | 实际采样频率 | 深度 |
| --- | --- | --- | --- | --- | --- |
| FDMA 业务 | `u_pcie/ila_FDMA_inst` | 14 | `PCIe.i_sys_clk`，TOP 接 `clk_250m` | 250MHz，4ns／点 | 1024 点 |
| 温度 | `u_temp_rd/ila_temp_inst` | 6 | `TEMP_RD.sys_clk`，TOP 接 `clk_250m` | 250MHz，4ns／点 | 1024 点 |

采样时钟以上层 RTL 实际连接为准。IP 文件中的名义频率字段及 debug hub 的时钟信息不能当成这两组 ILA 的实际采样频率。连续采样时，一组完整窗口约为 `1024 × 4ns = 4.096µs`。

### 2.1 FDMA 组：全部 14 个探针

下表中的时钟域均为业务 FDMA 域 `clk_250m`。数据虽然最终来自或流向 DDR／Aurora，表中探针观察的是它们在 FDMA 域的接口或状态，不是 MIG UI 域或 Aurora 用户时钟域。

| 探针 | LTX 信号名 | 捕获位宽 | 时钟域 | 含义及读取方法 |
| --- | --- | --- | --- | --- |
| probe0 | `u_pcie/fdma_raddr` | 32bit，原接口 `[31:0]` | `clk_250m` | 下行本次 DDR 读请求的字节地址。原接口为 64bit，本 ILA 只取低 32bit；当前 `CARD_ADDR_HI=0`。应在请求附近检查地址，不能把空闲时的值当成已接受事务。 |
| probe1 | `u_pcie/fdma_rareq` | 1bit | `clk_250m` | 业务读请求；发送桥提出请求后由 adapter 门控。失去发送条件后禁止新请求。适合作为下行开始的触发条件。 |
| probe2 | `u_pcie/fdma_rbusy` | 1bit | `clk_250m` | `CONV_DMA` 读状态不处于空闲，表示本次读事务仍在处理。请求被 busy 接受后桥进入数据阶段；busy 清零不能单独证明数据或子机结果正确。 |
| probe3 | `u_pcie/fdma_rdata` | 64bit | `clk_250m` | 当前业务 AXI 返回的读数据。仅在 `fdma_rvalid=1` 的采样点计入已接受数据；其他时间的数值可能只是总线保持值。 |
| probe4 | `u_pcie/fdma_rsize` | 16bit | `clk_250m` | 每次读请求的 64bit 拍数，不是字节数。当前每个 16Byte 帧固定为 2 拍。软件提交总长度可能包含多个这样的请求。 |
| probe5 | `u_pcie/fdma_rvalid` | 1bit | `clk_250m` | **读数据已接受脉冲**，实际等于 `M_AXI_RVALID && M_AXI_RREADY`。每个为 1 的采样点计一个接受拍，连续两拍可表现为连续两个采样点为 1。故障排空的旧读也可能出现此脉冲，不能据此证明该拍已交付 Aurora。 |
| probe6 | `u_pcie/fdma_waddr` | 32bit，原接口 `[31:0]` | `clk_250m` | 上行 writer 当前 DDR 写事务的字节地址。原接口为 64bit，本 ILA 只取低 32bit。应在写请求附近检查块基址与块内偏移。 |
| probe7 | `u_pcie/fdma_wareq` | 1bit | `clk_250m` | writer 提出的写请求，在请求状态保持，等 busy 接受。适合作为上行写入开始的触发条件。 |
| probe8 | `u_pcie/fdma_wbusy` | 1bit | `clk_250m` | `CONV_DMA` 写状态不处于空闲，包括准备、发送及等待 B 响应。busy 清零本身不区分成功、拒绝或错误结束。 |
| probe9 | `u_pcie/fdma_wdata` | 64bit | `clk_250m` | writer 准备写入的当前数据拍。当前业务保存每个有效 64bit 接收拍的低 32bit，再按顺序拼成 64bit 写拍。必须结合源有效理解；当前 ILA 缺少写接受和字节掩码，不能仅凭数据变化判断已写入。 |
| probe10 | `u_pcie/fdma_wsize` | 16bit | `clk_250m` | 本次写请求的 64bit 拍数，当前 writer 固定为 1。周期末奇数尾字也发一个 64bit 拍，但仅低四字节有效；掩码不在本 ILA 中。 |
| probe11 | `u_pcie/fdma_w_source_valid` | 1bit | `clk_250m` | **写源端有效**，表示 writer 正在提供当前写拍；不是接受脉冲。反压时可能连续保持为 1，不得按有效周期数计算成功写入拍数。 |
| probe12 | `u_pcie/adapter_rx_state_dbg` | 4bit | `clk_250m` | `RTDS_RX_BLOCK_WRITER` 的写事务状态，等于 `{1'b0,write_curr_st}`。0 空闲、1 请求、2 数据、3 等最终响应。不是 Aurora 接收状态或块队列数量。 |
| probe13 | `u_pcie/adapter_tx_state_dbg` | 4bit | `clk_250m` | 发送桥 FDMA 侧读状态，等于 `{2'b00,tx_fdma_dbg_bus[37:36]}`，实际为 `rd_state`。0 空闲、1 请求、2 接收读数据、3 等读 busy 清零。不是 Aurora 用户域发送状态，也不是 adapter 的全部恢复状态。 |

两个状态探针都使用 0～3，但含义不同：

| 数值 | `adapter_rx_state_dbg` | `adapter_tx_state_dbg` |
| --- | --- | --- |
| 0 | IDLE：尚无进行中的写事务 | RD_IDLE：等待链路、FIFO 空间及批量条件 |
| 1 | REQ：等待 `fdma_wbusy` 接受请求 | RD_REQ：等待 `fdma_rbusy` 接受请求 |
| 2 | DATA：提供写数据，等待写接受 | RD_DATA：接收规定拍数的读数据 |
| 3 | RESPONSE：等待 `fdma_wdone` | RD_WAIT：规定拍数已收齐，等待读 busy 清零 |

RX 正常路径为 `0→1→2→3→0`；TX 正常路径为 `0→1→2→3→0`。同样的数字序列描述不同的事务。RX 回到空闲表示写事务结束，但缺少 `fdma_werror` 探针，不能据此认定写成功。

### 2.2 温度组：全部 6 个探针

TOP 将 `TEMP_RD.SYS_CLK` 配置为 250000000，`RD_TEMP_CYCLE=1000µs`。因此 `CYCLE=250000`，计数完整周期为 1ms。这不是 ILA 一屏能够完整覆盖的周期。

| 探针 | LTX 信号名 | 位宽 | 时钟域 | 含义及读取方法 |
| --- | --- | --- | --- | --- |
| probe0 | `u_temp_rd/den_in` | 1bit | `clk_250m`，SYSMON 的 `dclk_in` 也接此时钟 | DRP 操作使能。计数值为 `CYCLE-10` 时，在随后寄存器输出上产生一拍使能。适合作为温度访问触发条件。 |
| probe1 | `u_temp_rd/dwe_in` | 1bit | `clk_250m` | DRP 写使能。当前 RTL 与 `den_in` 同时置 1；应按实际代码理解，不能把本操作描述成 `dwe_in=0` 的纯读事务。该信号不表示一次操作已完成。 |
| probe2 | `u_temp_rd/cnt_time` | 32bit | `clk_250m` | 温度操作周期计数，0～249999 循环；每拍递增，末值后回到 0，系统复位清零。立即触发可看计数活动，不能用 4.096µs 单屏证明整个 1ms 周期。 |
| probe3 | `u_temp_rd/daddr_in` | 8bit | `clk_250m` | SYSMON DRP 地址。当前复位为 0，之后保持 0；温度访问触发时检查实际地址。 |
| probe4 | `u_temp_rd/temp` | 16bit | SYSMON DRP 输出，由 `clk_250m` 域 ILA 采样 | SYSMON 的 `do_out` 原始码，不是直接的摄氏温度。`drdy_out` 未连接到本组探针，不能仅依据数值出现判断本次操作完成。 |
| probe5 | `u_temp_rd/busy` | 1bit | `clk_250m` | `TEMP_RD` 自行产生的周期末操作提示，依据最后 10 个计数值寄存输出；不是 SYSMON 的 `busy_out`，也不是 PCIe／DDR 忙状态。 |

### 2.3 MIG 校准调试核

实例路径：`u_pcie/u_rtds_ddr4_backend/u_ddr4_mig`。`TOP.ltx` 类型为 `XSDBS_V2`，不是普通 ILA；不存在可按上述方式枚举的 probe0～probeN 信号表。通过 Memory Calibration Debug／MIG 界面查看校准结果。不能把该核视为 backend AXI 响应或恢复过程的采样器。

### 2.4 当前未采集的重要信号

当前普通 ILA 没有采集 BAR AXI-Lite、PCIe 用户中断、`fdma_w_accept`、`fdma_wdone`、`fdma_werror`、`fdma_wstrb`、backend R/B 响应与 `recovery_` 状态、`storage_ready/ddr_ready`、块数量／队头／归还事件，以及 1G 配置／发送和 2µs／50µs 源事件。

这些功能的完整判定需要软件结果、对端结果或新增探针。仅在 Vivado Dashboard 中添加波形信号，不能补出 bit 中没有连接的探针。增加探针需要更新实现产物；本文不修改 RTL、探针或 bit。

## 3. 第一次上板：连接、烧写和探针确认

1. 点击左侧 **Open Hardware Manager**。
2. 点击 **Open Target → Auto Connect**。
3. 在 Hardware 窗口右键 FPGA，选择 **Program Device**。
4. 将 Bitstream file 和 Debug probes file 分别设为同一次实现的以下文件：

   ```text
   C:\project\RTDS\DDR\RTDS_test_DDR4_64bit_batch_dev\RTDS_test_DDR4_64bit.runs\impl_1\TOP.bit
   C:\project\RTDS\DDR\RTDS_test_DDR4_64bit_batch_dev\RTDS_test_DDR4_64bit.runs\impl_1\TOP.ltx
   ```

5. 点击 **Program**。完成后右键 FPGA，选择 **Refresh Device**。
6. 展开器件，按实例路径确认 FDMA ILA、温度 ILA 和 MIG 调试核。
7. 如果已烧入同版 bit，只需确认匹配的 `.ltx` 并刷新。后续每次重新抓取不需要重新烧写。

软件侧 PCIe 枚举应在实际连接 FPGA 的 RK3588 上检查。远程 Windows 是 JTAG 操作机，不能用它的设备管理器替代 RK3588 枚举检查。

## 4. 不需要软件配合：温度 ILA 自检

1. 双击 `u_temp_rd/ila_temp_inst`，打开 Dashboard。
2. 点击 **Run Trigger Immediate**，等待数据上传并显示波形。
3. 点击波形窗口的 **Zoom Fit**，看 `cnt_time` 是否递增。短 `den_in` 脉冲未被立即抓到不代表模块不工作。
4. 在 **Debug Probes** 中选择 `den_in`，右键 **Add Probes to Basic Trigger Setup**。
5. 将比较关系设为 `==`，值设为 `1`；只保留这个触发条件。
6. 点击 **Run Trigger**，等待下一次 DRP 操作，无需软件按钮。
7. 数据上传后观察 `den_in/dwe_in` 脉冲、计数跨越周期末、`busy` 和温度原始码。

**Run Trigger** 是先布防、再等待所设事件；**Run Trigger Immediate** 忽略条件立即采样，适合检查当前活动。抓业务事件应先 Run Trigger，再发业务。[Vivado 2020.2 触发说明](https://docs.amd.com/r/2020.2-English/ug908-vivado-programming-debugging/Running-the-Trigger)

## 5. FDMA ILA 的第一轮统一设置

双击 `u_pcie/ila_FDMA_inst`，在 Capture Mode Settings 或 ILA Core Properties 设置：

| 设置项 | 第一轮取值 | 原因 |
| --- | --- | --- |
| Trigger Mode | BASIC | 当前核未启用 Advanced Trigger。 |
| Number of Capture Windows | 1 | 先保留一次事件的连续过程。 |
| Data Depth | 1024 | 使用当前核全部采样深度。 |
| Trigger Position | 128 | 留出约 0.512µs 事件前数据，窗口剩余部分用于事件后过程。 |
| Auto Re-Trigger | 关闭 | 避免新事件覆盖尚未保存的结果。 |
| 采样条件 | 连续采样，不增加过滤条件 | 保留请求、数据和状态的先后关系。 |

触发位置是窗口中的采样点编号，不是时间值；1024 点的合法编号为 0～1023。[触发位置说明](https://docs.amd.com/r/2020.2-English/ug908-vivado-programming-debugging/Setting-the-Trigger-Position-in-the-Capture-Window)

## 6. 下行抓取：先布防，再由软件写 0x20

第一次使用 16Byte 单次任务。正常下行业务要求 PCIe、DDR、10G Aurora 发送条件均有效。

| 顺序 | Vivado 操作 | 软件／板上操作 |
| --- | --- | --- |
| 1 | 暂不点击运行 | 读取版本常量确认用户 BAR；要求 `0x20=0`、`0x2C.bit0/bit1=1`，且 10G 链路具备发送条件。 |
| 2 | 暂不点击运行 | H2C DMA 将已知 16Byte 数据写到 DDR `0x8000`，等待 DMA 完成。 |
| 3 | 暂不点击运行 | 写 `0x24=0x8000`、`0x28=0x10`，停在启动命令前，不写 `0x20`。 |
| 4 | 删除旧触发条件。在 Debug Probes 选择 `fdma_rareq`，右键 Add Probes to Basic Trigger Setup，设置 `==1` | 继续等待。 |
| 5 | 点击 **Run Trigger**，确认核进入等待触发状态 | 此时仍不提交任务。 |
| 6 | 保持等待 | 软件写 `0x20=1`，发起单次任务。 |
| 7 | 等数据自动上传，点击 **Zoom Fit**；总线右键 **Radix → Hexadecimal** | 保存输入载荷、结束时的 `0x20` 和 `0x2C`。 |
| 8 | 保存本次 `.ila` 后再准备下一次抓取 | 需要重复时再次提交任务，不能先发完再点击 Run Trigger。 |

本次检查：请求附近 `fdma_raddr=0x8000`、`fdma_rsize=2`；busy 表示正在处理；两个 `fdma_rvalid=1` 的采样点接受两个 64bit 数据拍。数据输入为字节 `00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F` 时，小端总线应依次为：

```text
0706050403020100
0F0E0D0C0B0A0908
```

该示例 Byte1 为 1，属于首次合法 1G 配置编号；若本次任务成功完成配置提取，可能锁定该配置，测试时应知晓这项业务作用。

本组波形可以检查业务 DDR 读地址、拍数和数据，不能证明 Aurora 完整发送或子机收到。`0x20` 清零也只表示本地任务结束，拒绝和中止均可能清零。

## 7. 上行抓取：先布防，再由子机发送

1. 暂停对端持续数据，保证本次已知数据可辨认；确认 DDR 和 10G 接收条件可用。
2. 删除下行触发条件，添加 `fdma_wareq`，设置 `==1`。
3. 点击 **Run Trigger**，确认进入等待触发状态。
4. **此后才让子机发送已知数据**。第一次可发送两个有效 64bit 接收拍，便于形成一个完整 64bit 写拍。
5. 等数据上传，点击 **Zoom Fit**，将地址／数据设为十六进制。
6. 检查 `fdma_waddr`、`fdma_wsize=1`、待写 `fdma_wdata`、源端有效及 RX 状态变化。
7. 保留波形后，软件等待生产周期的非空块实际发布，读 `0x30`、`0x18/0x1C`，C2H DMA 取回并比对。
8. **C2H DMA 完成后才写 `0x14=1` 归还该块**。

当前只保存每个有效接收拍的低 32bit。若两个接收拍低字依次为 `0x11223344`、`0x55667788`，且之前没有未配对字混入，完整待写数据应为：

```text
5566778811223344
```

复位后首次写块基址为 `0x00100000`；后续以实际写块位置与软件队头信息为准，不要把所有上行写请求都期待为该地址。写入活动先发生，可读块只有在周期结束、成功写响应和尾字处理完成后才发布，不能等软件看到有块后再抓最初写入事件。

`fdma_w_source_valid=1` 不能证明 DDR 写成功；RX 状态从 RESPONSE 返回 IDLE 也不区分成功和失败。当前缺少接受／响应／掩码探针，成功判定需要软件 DMA 比对和异常记录配合。

## 8. 软件侧应保存的核心状态

| 偏移 | 含义 | 抓取配合 |
| --- | --- | --- |
| `0x00/0x04/0x08` | 版本、构建标识、上行块容量 | 应分别读到 `0x00002001/0x20260914/0x00040000`，确认访问用户 BAR。 |
| `0x20` | 下行命令忙位 | 提交前等待 0；提交后观察任务结束。清零不等于子机收到。 |
| `0x24/0x28` | 下行 DDR 地址／字节长度 | 与 ILA 本次读地址和 2 拍分帧规则对应。 |
| `0x2C` | DDR ready、校准及异常记录 | 正常业务前要求低两位为 1；先保存异常，再清通知。 |
| `0x10` | 读清通知及相关异常记录 | 不释放块；不要用普通轮询反复读取，否则可能丢掉诊断现场。 |
| `0x30` | 可读块数 | 上行是否有数据以此为准。 |
| `0x18/0x1C` | 当前队头 DDR 地址／有效字节长度 | 按实际值做 C2H DMA，不能只按 ILA 的瞬时写地址取块。 |
| `0x14` | 写 1 归还当前一块 | 每块 DMA 完成后只写一次 1；不是普通 RW 测试寄存器。 |
| `0x34/0x38` | 可选队头顺序号／累计丢失 32bit 字数 | 保存便于顺序、完整性与故障定位；丢字数增长表示有数据丢失。 |

BAR 基础读写可以先独立联调；纯 BAR 读写和 CPU 直接 H2C/C2H DMA 不要求当前 FDMA ILA 出现动作。下行按手册 5.2 轮询 `0x20`；上行按 5.3 轮询 `0x30` 或由中断唤醒后排空队列。中断不是固定 100ms 定时信号，也不能按一次中断只取一块。

## 9. 抓不到或波形不完整时

| 现象 | 下一步 |
| --- | --- |
| 一直等待触发 | 确认先 Run Trigger、后产生事件；核对 ILA 实例和方向条件；检查业务实际能启动。不能仅以等待时间长判硬件失败。 |
| 下行无请求 | 检查 `0x20/0x2C`、参数和 10G 条件；仅完成 H2C DDR DMA 不会自动启动 adapter 下行读取。 |
| 上行无请求 | 确认对端产生有效接收数据、业务接收条件有效；一次低 32bit 字可能仍等另一个字配对或周期尾字处理。 |
| 立即触发后全零 | 无业务时可以正常；只说明该几微秒采样窗口内没有活动。先用温度 ILA 检查采样活动。 |
| 只有部分任务 | 窗口只有 4.096µs。缩小任务，或改用 `fdma_rvalid==1`／`fdma_w_source_valid==1` 对准数据阶段重新抓取。 |
| fdma_w_source_valid 连续为 1 | 可能是反压保持，不能把每个有效采样点都计为成功写拍。 |
| 请求和数据出现，但无法判写成功 | 保存软件数据比对和 `0x2C/0x38`；当前探针确实缺少最终写响应，需补证据。 |
| 抓不出 recovery 状态 | 这些信号未接当前 ILA，修改触发值无法解决；需另行更新探针和实现产物。 |

## 10. 保存一次板上采样

先保存当前数据，再重新布防。Tcl Console 可列出调试对象：

```tcl
get_hw_devices
get_hw_ilas
get_hw_probes
```

这些命令列出对象，不是打印全部信号当前值。以下 `hw_ila_1` 需替换为实际 FDMA 核对象名，输出目录使用已存在目录，文件名每次区分任务和日期：

```tcl
write_hw_ila_data {C:/project/RTDS/DDR/RTDS_test_DDR4_64bit_batch_dev/evidence/fdma_down_16B_20261013.ila} [upload_hw_ila_data hw_ila_1]
```

上传保存命令在采样完成后执行，不能在等待触发时提前执行。`.ila` 包含采样及显示配置，可重新读入：

```tcl
display_hw_ila_data [read_hw_ila_data {C:/project/RTDS/DDR/RTDS_test_DDR4_64bit_batch_dev/evidence/fdma_down_16B_20261013.ila}]
```

同一次采样同时保存：输入载荷、软件寄存器日志、DMA 比对结果、bit／ltx 版本和触发条件。板上 `.ila` 与已有仿真 WDB/VCD 是不同来源的证据，不混用采集日期或验证结论。[Vivado 2020.2 采样数据保存说明](https://docs.amd.com/r/2020.2-English/ug908-vivado-programming-debugging/Saving-Captured-ILA-Data-to-a-File)
