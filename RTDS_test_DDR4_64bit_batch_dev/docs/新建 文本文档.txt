软件读 0x20：bit0 为 1 表示下行任务仍占用，期间写 0x24（地址）或 0x28（长度）会被 RTL 忽略；bit0 为 0 时才配置这两个寄存器，再向 0x20 写 1 提交

如果你问的是**子机传来的上行数据存到辅助板 DDR 的哪里**，看寄存器 **`0x18 FPGA_CPU_START_ADDR`**。它给出当前最早一块待读数据的 DDR 起始地址；同时读 **`0x1C FPGA_CPU_LEN`**，得到这一块实际存了多少字节。`0x30 UP_READY_BLOCK_CNT` 大于 0 时，这组地址和长度才有效。

CPU 按 `0x18` 的地址和 `0x1C` 的长度完成 C2H 读取后，向 `0x14.bit0` 写 1；FPGA 才会切换到下一块，`0x18/0x1C` 随之更新。

如果问的是**CPU准备写入下行数据的位置**，则是 **`0x24 CPU_FPGA_START_ADDR`**，由 CPU 设置。

可以，完全不讲 RTL 信号，只讲协议原理。你可以这样跟同事解释：

**最底层的区别是：PCIe、以太网会把“物理链路的暂停和抖动”尽量封装在协议/IP内部；Aurora 更接近一条高速数据管道，这些时间变化更容易直接传到用户数据这一层。**

具体来说：

- **PCIe 是“事务协议”**。一次传输是一个完整事务，内部有缓存、流量控制、校验以及链路级重传。物理层哪怕短暂停一下，通常只是这个事务晚一点到，不会把这种暂停直接表现成“一个业务包中间断了”。
- **以太网是“完整帧协议”**。MAC/PCS 会处理物理层编码、时钟差异、帧间隔等细节，对上层交付的是一帧一帧的数据。底层短暂的时序变化通常被 IP 内部吸收。因此正常情况下，上层感受到的是“这一帧到了或没到”，而不是“这一帧因为底层补偿而从中间断一下”。当然，以太网本身并不是绝对不丢包，例如 CRC 错误、缓存溢出都可能造成整帧丢弃。
- **Aurora 更轻量**。它主要负责把高速串行链路可靠地搬成数据流，但不像 PCIe 那样提供完整的事务重试体系，也不像 Ethernet MAC 那样强调把数据整理成对上层稳定的完整帧节奏。时钟补偿、内部仲裁、收发时钟差异造成的短暂停顿，更可能直接体现在数据到达时间上。

所以“为什么以前 PCIe、Ethernet 没问题，Aurora 才出现”，最简单的解释不是：

> **PCIe / Ethernet 不会发生底层暂停，而 Aurora 会。**

而是：

> **三者底层都会有各种暂停和时序变化；PCIe、Ethernet 通常在协议/IP内部把这些变化消化掉了，Aurora 更容易把这种时间不连续暴露给用户设计。**

至于你前面的 **0.12%**，也可以用完全非 RTL 的说法：

> **0.12% 表示某类底层维护动作占用的时间比例，不等于 0.12% 的数据一定会丢。维护动作在低负载和高负载下都会发生；低负载时它往往落在没有业务数据的空闲时间里，所以感觉不到，高负载时更容易和业务数据重叠，所以更容易把设计里的问题暴露出来。**

一句话版本可以直接发给同事：

> **PCIe 和以太网不是没有底层暂停，而是它们有更厚的协议和缓存机制，把暂停变成了延迟或整帧处理；Aurora 更像高速直通管道，底层的时钟补偿和节奏变化更容易直接影响业务数据时序，所以以前没暴露的问题可能只在 Aurora 上出现。**


“我已经做了缓存，所以正常的短时停顿可以被吸收，不会立即形成反压；只有持续拥塞超过缓存能力，才会出现反压或丢数据。”
