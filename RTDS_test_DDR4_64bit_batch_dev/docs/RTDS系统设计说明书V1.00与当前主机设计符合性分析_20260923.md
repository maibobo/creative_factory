
## 1. 对照范围与结论

本文对照以下资料：

本文所称“当前主机设计”，指 F 盘工程中以 FPGA 为端点的 PCIe 原型适配逻辑：CPU 通过 XDMA、AXI-Lite 寄存器和 DDR 与 FPGA 交互，FPGA 再连接 1G/10G Aurora。它覆盖《系统设计说明书》中的 **PCIe 管理、配置下发、状态读取、过程数据回读、板载 DDR 缓存和部分 Aurora 传输接口**。


总体判断如下：

| 结论类别 | 当前情况 |
|---|---|
| 已直接覆盖 | PCIe Endpoint、配置/状态寄存器、H2C/C2H 数据通路、DDR 数据窗口、CPU 通知与确认、1G/10G 物理接口集成 |

## 2. 当前主机设计怎样覆盖说明书

### 2.1 PCIe 管理和数据回读

说明书要求管理板经主控 PCIe 对 FPGA 板卡完成配置下发、状态读取、数据回读，并以“寄存器 + 数据窗口”提供服务。当前工程通过以下结构覆盖：

```text
CPU/RK3588 软件
  ├─ AXI-Lite BAR → INFO_EXCH：命令、状态、队头元数据、统计
  ├─ H2C → DDR 下行窗口 → CONV_DMA → Aurora 10G
  └─ C2H ← DDR 上行块 ← CONV_DMA ← Aurora 10G
```

- XDMA 提供 PCIe Endpoint、AXI Memory Mapped 数据接口和 AXI-Lite 控制接口。
- `INFO_EXCH.v` 提供 32bit 小端寄存器访问。
- `CONV_DMA.v` 将 FDMA 请求转换为 AXI 访问，支持跨 4KiB 边界拆分、AW/W 独立握手、写响应完成和错误返回。
- `pcie_fdma_aurora_brg_adapter.v` 负责软件命令检查、DDR 读写调度、Aurora 数据桥接、块队列通知及状态统计。
- DDR 后端保持 AXI 64bit 数据宽度、32bit 地址和 5bit ID；XDMA 业务接口保持 64bit、250MHz。

因此，说明书中“管理板经 PCIe 配置、监视、回读 FPGA 板卡”的硬件端服务已经形成。CPU 驱动、Linux 通讯控制进程和后台协议不属于该 RTL 工程。

### 2.2 软件可见寄存器

当前寄存器对主机软件提供以下覆盖：

| 偏移 | 当前含义 | 对说明书的覆盖 |
|---|---|---|
| `0x00` | `VERSION=0x00002001` | FPGA 业务版本识别 |
| `0x04` | `PROG_TIME=0x20260914` | 程序版本日期 |
| `0x08` | `BUF_LEN_MAX=0x00040000` | 上行单块最大容量 256KiB |
| `0x0C` | FPGA 温度/状态 | 板卡运行状态的一部分 |
| `0x10` | 通知状态，读清 | 对应数据就绪通知；读清不释放数据 |
| `0x14` | CPU 读完确认 | 一次写 1 释放一个已呈现队头，硬件自动清零 |
| `0x18/0x1C` | 最老待取块地址/实际长度 | 支持 CPU 按完整块执行 C2H |
| `0x20` | 下行提交门铃 | H2C 完成后提交；处理完成、拒绝或中止后清零 |
| `0x24/0x28` | 下行地址/长度 | 16Byte 对齐，完整位于 32KiB 下行窗口 |
| `0x2C` | DDR/错误状态 | DDR 校准、忙和错误状态汇总 |
| `0x30` | 待取块数 | 缓存水位的直接可见量，范围 0～8 |
| `0x34` | 队头发布序号 | 支持软件检查块顺序和遗漏 |
| `0x38` | 丢失的 32bit 有效字累计数 | 覆盖 FIFO 溢出、缓存拒收和 DDR 写失败，饱和计数 |

主机软件顺序为：

- 下行：完成 H2C → 写 `0x24/0x28` → 写 `0x20=1` → 等待门铃自动清零；
- 上行：读取通知 → 读取 `0x18/0x1C/0x34` → 完成 C2H → 写 `0x14=1` 确认释放。

这覆盖了说明书提出的配置下发、状态查询、数据回读和中断/确认框架，并明确了数据所有权。软件必须使用单一队列消费者，不能在 C2H 完成前确认释放。

### 2.3 DDR 缓存和数据所有权

说明书要求 DDR 分块、读写地址隔离，避免读写冲突和数据撕裂；正文采用 A/B 两块乒乓。当前工程保留目标，但采用更具体的八块队列：

| 项目 | 说明书 V1.00 | 当前 F 盘实现 |
|---|---|---|
| 组织方式 | A/B 两块乒乓 | 8块循环所有权队列 |
| 每块容量 | 未在系统层固定 | 256KiB |
| 总上行空间 | A/B 语义 | 2MiB，`0x00100000～0x002FFFFF` |
| 发布节拍 | 管理板按100ms扫描；实时数据以50us组织 | DDR 域每100ms请求封块 |
| 发布条件 | 数据块写完后通知 | 非空、在途写及最终成功写响应结束后才发布 |
| 防覆盖 | 乒乓读写分离 | CPU ACK 前队头地址、长度、序号和内容保持；满队列不覆盖旧块 |
| 软件抖动余量 | 两块 | 空队列起步时约可吸收700ms未释放积压，实际余量随积压减少 |

八块方案实现了说明书的核心目标，并比两块乒乓更能吸收软件调度抖动；但它不是对 A/B 数据结构的逐字实现。若系统接口文件明确要求只有 A/B 状态位，软件或协议层需要重新定义为八块队列语义，不能继续用“两块交替”解释当前寄存器。

### 2.4 Aurora 接口和周期数据

当前硬件顶层已经集成 1G 与 10G Aurora 物理接口：

| 接口 | 当前实现 | 板级位置 |
|---|---|---|
| 1G Aurora | 32bit 用户接口，31.25MHz；首次合法 Byte1 映射为 48bit 参数，周期发送6Byte | 光口1，通道 `GTHE3_CHANNEL_X0Y4`，参考时钟 AB6/AB5 125MHz |
| 10G Aurora | 64bit LocalLink 双向接口；CPU 下行原样发送，线路上行进入 DDR | 光口5，通道 `GTHE3_CHANNEL_X0Y8`，参考时钟 V6/V5 156.25MHz |

1G 参数为小端 `duty[15:0] + Vin[31:0]`，首次合法编号 1～10 锁存到主机逻辑复位。发送器在 31.25MHz 域每63拍给出一次机会，名义周期为 `2.016us`；两拍发送，忙时跳过，不积压补发，链路恢复后从后续周期继续。

这在“2us 级周期数据”和独立 1G 通道方面覆盖了系统目标，但其业务含义和方向与 V1.00 有差别，见第3节。

### 2.5 板级、时钟、复位和 CDC

当前工程已按 RPT205/KU040 PCB 配置：

- 背板 PCIe x2：AF6/AF5 100MHz，H24 PERST#，GTH Quad 224；
- DDR4：64bit 物理总线及既有 MIG 管脚保持；系统差分时钟 AK17/AK16；
- 1G/10G：分别使用光口1和光口5，参考时钟上电自动输出；
- `CFGBVS=VCCO`、`CONFIG_VOLTAGE=3.3`；
- 悬空 AC34 不再作为 DDR 复位输入，DDR 复位由系统域同步产生；
- XDMA 链路状态、配置握手、计数和复位路径已增加同步器或本域寄存，避免直接跨时钟控制。

这些工作覆盖说明书中“链路状态可观测、链路未就绪不启动业务、复位后重新同步”的 FPGA 底层基础。整机“管理板—主处理板—辅助板”顺序上电、自检、看门狗和故障恢复策略不在当前 RTL 中。

## 3. 当前实现与说明书的主要差别

### 3.1 板卡角色和数据方向不完全一致

V1.00 中主处理板的定义是：1G 接收辅助板模拟量，10G 向辅助板发送应用结果；辅助板则相反。当前工程的业务方向是：

- 1G：主机侧向外周期发送6Byte参数，业务 RX 不进入 DDR；
- 10G：CPU 配置帧经 DDR 向外发送，同时接收线路有效数据写 DDR 后供 CPU 回读。

因此，当前工程更适合表述为“PCIe—DDR—Aurora 原型适配平台及当前联调业务映射”。如果最终定位为 V1.00 的主处理板，需要补齐 1G 模拟量接收、应用计算以及 10G 50us结果发送；如果定位为辅助板，则仍需补齐模拟量采集/模式选择、10G 应用帧解析校验和输出通道。

### 3.2 1G 周期是 2.016us，不是严格 2.000us

当前发送机会按31.25MHz用户时钟63拍生成，周期为 `63×32ns=2.016us`。反压或链路掉线时，实际成功发送间隔还会更长。V1.00 写的是2us实时节拍，因此当前实现属于接近2us的接口周期发送，不能据此声称满足严格2.000us闭环时限。

### 3.3 当前没有实现完整 50us 应用闭环

V1.00 要求应用逻辑在50us内完成计算，按50us组织结果帧并通过10G传输。当前工程没有应用算法，也没有强制按50us形成固定应用帧。10G下行由CPU门铃触发，上行由线路有效数据驱动，100ms只是DDR批次发布周期。

### 3.4 下行帧从计划中的128Byte改为16Byte

远端“新加需要修改计划”最初规定CPU下行和上行固定帧均为128Byte。当前代码已经改为：

- CPU→10G：每帧16Byte，批量长度为16Byte正整数倍；
- 下行窗口：`0x00008000～0x0000FFFF`，最多32KiB；
- Byte1只在首个DDR读拍真实握手时观测，用于首次1G配置，完整16Byte仍送10G。

因此，远端计划中的128Byte对齐、每帧16个64bit拍和“每块约2000个128Byte帧”的描述不再适用。

### 3.5 上行由固定帧改为低32bit连续字流

当前上行不保留线路SOF/EOF，也不要求固定帧长。每个有效64bit接收拍只保存低32bit，两个32bit字紧凑拼为一个DDR 64bit写拍；奇数尾字使用 `WSTRB=0x0F`。因此：

- DDR中的长度是4Byte整数倍；
- `0x38`统计的是丢失的32bit有效字，不是丢帧数；
- CPU不能仅依据DDR内容恢复原线路帧边界；
- FIFO中的积压数据按实际写入窗口归属，100ms块序号不是严格的线路到达时间戳。

这与 V1.00 的“固定周期组帧、帧同步、帧序号、校验和、错帧丢弃”存在明显差异。若系统仍要求逐帧校验和定位丢帧，需要在Aurora业务层保留帧元数据或增加帧头/序号，而不能只依赖当前连续字流。

### 3.6 监控覆盖不完整

当前已有 PCIe link、Aurora channel up、DDR校准/忙、队列水位、块序号、溢出/写失败统计及部分 sticky 状态。尚未完整实现：

- Aurora 误码率、帧校验错误和明确的帧丢失率；
- 说明书要求的模拟量缓存/应用数据发送缓存上下水位告警；
- 管理板统一状态汇总、告警记录及以太网上报；
- 网络断链后的状态缓存与恢复补传。

### 3.7 软件和整机功能未覆盖

以下属于说明书的管理板/后台软件范围，当前 FPGA 工程没有实现：

- RK3588、嵌入式 Linux、PCIe 驱动和统一设备接口；
- 后台机客户端、TCP 8006 服务、1s心跳、3周期断链判定、2～30s退避重连；
- 后台命令、状态/过程数据报文及100ms网络上送分包；
- 主控PCIe直发与经辅助板10G转发的双路径启停选择；
- 应用逻辑启停结果一致性和后台回显。

## 4. 与远端修改计划的演进关系

远端修改计划提供了当前实现的主要骨架：独立1G参数通道、10G上行、100ms×8块、DDR 2MiB上行窗口、32KiB下行窗口、CPU通知/确认及新增诊断寄存器。F盘工程对其作了以下落地和调整：

| 远端计划 | 当前落地 |
|---|---|
| 1G 首次合法配置、6Byte周期发送 | 已实现；周期方式改为1G域63拍，即2.016us |
| 250MHz域500拍事件跨域 | 已删除，避免为周期事件增加跨域；改用1G用户域本地计数 |
| 下行128Byte帧 | 改为16Byte帧，支持一个门铃批量发送多个完整帧 |
| 上行固定128Byte帧 | 改为低32bit连续有效字流，不保留帧边界 |
| 100ms×8块、每块256KiB | 保留 |
| 最终B响应后发布 | 保留，并将写错误计入丢失，不把失败位置暴露为有效空洞 |
| 丢帧统计 | 改为32bit有效字丢失统计，寄存器偏移不变 |
| CPU写0→1确认 | 当前写1形成一次确认并自动清零，不再要求软件先写0 |
| 版本V2.00 | 当前RTL为V2.01（`0x00002001`） |

这些调整已经反映到 `主机规格与寄存器总结.md`、`PCIe交互协议_V2.01.md` 和当前 RTL。软件开发应以 V2.01 为准，不能继续按远端早期计划中的128Byte固定帧和丢帧计数解释寄存器。

## 5. 验证证据及其边界

当前已有以下功能证据：

- 2026-09-20 七组模块用例通过：1G配置/周期发送、八块队列、真实CONV_DMA与4MiB行为RAM、`WSTRB=0x0F`尾拍、接收跨域FIFO、真实寄存器交互、300帧TX反压；
- 2026-09-21 board CDC smoke通过：16Byte下行、link-down、配置确认和GT/core复位释放；
- AXI ID静态审计通过：FDMA 1bit、XDMA 4bit到DDR 5bit的ID编码和返回无冲突；
- 1G/10G XCI、GT通道、参考时钟与板级XDC已做文件级一致性校验。

仍未由上述证据覆盖：

- 真实 PCIe Root Port 枚举、BAR、MSI、H2C/C2H 全链路；历史用例仍停在 `Polling.Active`，不能算通过；
- 真实 DDR4 颗粒训练、信号完整性和长期压力；
- 真实1G/10G光链路误码、吞吐及双向联调；
- 当前最新 RTL、CDC、GT/IP/XDC 组合的完整综合、实现、DRC和时序签核；
- 严格2us/50us整机闭环、RK3588软件及后台TCP联调。

2026-09-21早晨曾有修改前实现基线 `WNS +0.011ns / WHS +0.004ns`。随后又修改了板级管脚、GT位置、复位和CDC，因此该结果不能证明当前文件树实现通过。2026-09-22远端记录还出现过1G Aurora旧OOC缓存占用错误GT通道的问题；当时记录定位了缓存根因，但历史归档没有给出最终重跑通过结论。后续签核必须以重新生成IP后的新综合、实现、DRC、CDC和时序报告为准。

## 6. 面向系统设计说明书的后续补齐项

若目标是让当前工程成为 V1.00 所定义的完整主处理板，应至少补充：

1. 明确板卡角色和1G/10G方向，决定当前主机原型映射到主处理板还是辅助板；
2. 实现或接入1G模拟量接收、帧同步/校验、2us数据缓存和水位告警；
3. 接入应用逻辑并验证50us内计算完成，同时形成10G应用数据帧；
4. 恢复帧序号、校验和和逐帧错误统计，或正式修改系统说明书接受连续字流；
5. 决定系统层继续使用A/B术语，还是将接口规范更新为八块所有权队列；
6. 增加主控直发/辅助板转发两条启停路径及互斥选择；
7. 完成RK3588驱动、DMA/MMIO顺序、单消费者队列、TCP及后台协议；
8. 重新运行当前文件树的综合、实现、DRC、CDC、时序和bitstream，并完成PCIe、DDR、1G、10G实板联合压力测试。

若当前阶段仅定位为“PCIe原型适配开发”，则现有范围是合理的：它已形成可供主机软件使用的寄存器、DMA、DDR队列和Aurora桥接基础，只需明确其不是完整系统闭环验收结果。

## 7. 结论
