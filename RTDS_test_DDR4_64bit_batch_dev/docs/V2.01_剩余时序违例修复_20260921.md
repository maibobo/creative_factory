# V2.01 剩余时序违例修复（2026-09-21）

## 当前基线


- WNS -2.768 ns，TNS -2.768 ns，仅 1 个 setup 失败端点；WHS +0.004 ns，THS 0。
- 唯一失败路径：`ui_reset_pipe_reg[1]_replica` → `ready_sync_reg[0]/D`，MIG 300 MHz → 控制域 250 MHz。
- 控制域内部 WNS +0.263 ns，MIG 300 MHz 内部 WNS +0.033 ns；上轮温度、FDMA 和校准状态直连问题已消失。
- `no_clock=0`，`unconstrained_internal_endpoints=0`。仍有 1 个无 input delay 输入和 3 个无 output delay 输出，本次不凭空补外部接口时序参数。

这里的“失序”沿用历史语境，指静态时序违例，当前报告不构成 AXI 数据乱序的证据。

## 根因和修复

上轮 `DDR4_PIN.xdc` 使用 `if` 包裹 `set_false_path`。实际实现日志第 97 行明确记录：

```text
CRITICAL WARNING: [Designutils 20-1307] Command 'if' is not supported in the xdc constraint file.
```

因此首级同步器的例外未生效。上轮检查脚本在 Tcl 上下文手动执行同样的命令，仅证明对象能匹配，未验证 `read_xdc` 解析行为，遗漏了真正的失败环节。


两级同步器 RTL 及 `ASYNC_REG`、`SHREG_EXTRACT` 属性保持不变。例外只针对首级采样路径，第二级正常进行 setup/hold 检查；不增加全局异步时钟组，不修改 MIG 生成文件，不改变周期或增加 multicycle。

两个时钟来自共享参考时钟的不同 MMCM，不能仅凭“不同 MMCM”断言无固定相位关系。本次例外的依据是该单比特状态按两级同步协议传递、允许同步延迟，并非将全部相关跨域路径排除。

## 验证方法及边界

`regression/timing_xdc_fix_20260921/check_xdc.tcl` 打开已有 routed checkpoint，在内存中通过 **read_xdc 加载实际完整 XDC 文件**，检查两级属性、精确目标数量、首级例外以及第二级路径仍被分析，并输出重新计算的时序报告。不运行综合、布局、布线或 write_checkpoint，不修改原 routed DCP。


本轮按用户要求不启动综合、实现或 bitstream；最终新运行结果由用户手动产生。仅 XDC 改动可以复用现有综合网表重新实现；如果 GUI 显示综合过期，也可以接受 GUI 的依赖重跑。

## GUI 实现复核结果

2026-09-21 08:14 的 GUI 管理实现已完成 `route_design` 并生成 routed checkpoint；运行日志为 0 Error、0 Critical Warning。最终时序为 WNS **+0.011 ns**、TNS 0、WHS **+0.004 ns**、THS 0、脉宽裕量 0，所有用户指定时序约束满足。此前唯一的 `ui_reset_pipe_reg[1]` 到 `ready_sync_reg[0]/D` 的 -2.768 ns 违例已不再出现。

该结果的余量较小，主要是 `xdma_0_axi_aclk` 域 WNS +0.011 ns；后续因任何 RTL、IP、约束或布局变化而重新实现时，都应重新检查该时钟域。`check_timing` 仍报告 1 个未定义 input delay 和 3 个未定义 output delay，它们属于板级外部接口约束缺失，未通过 false path 掩盖。方法学报告还保留 XDMA 250 MHz 与主逻辑 250 MHz 并行时钟的时钟关系告警、GT LOC 建议及 IP 内部复位告警；这些不是本轮 setup/hold 失败，但上板前应按 IP/板卡连接进一步核实。
