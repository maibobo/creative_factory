# 测试分解与验证方法

测试点来自模块实际功能及上下文。先逐条读取规格，再拆出可观察、可判定的行为；基本功能是主要分类，接口交互、总线、跨域和异常按实际功能补充。知识库中的场景是提示，不代替当前规格。

## 从功能到测试

例如“收到命令后执行DDR写读校验”需要结合配置分解为启动前置条件、写地址与数据、读回比较、响应异常及完成状态。若项目只支持单拍、单outstanding，不强行要求实现乱序能力；可在合法范围内测试连续请求、反压和恢复，并明确不覆盖的能力。

| 规格中的信息 | 提取的测试思路 |
|---|---|
| 输入与输出 | 正常关系、禁止的输出、何时有效、数据/字节数是否一致 |
| 条件与状态 | 进入/离开状态、条件不同次序、条件同拍、等待及恢复 |
| 数值范围 | 最小、最大、边界前后；非法值仅在规格定义处理方式时测其反应 |
| 时序与容量 | 首尾拍、背靠背、反压、满空、在途事务与时限 |
| 异常处理 | 超时、错误响应、复位中断、丢弃与重试，以及异常后的下一笔正常事务 |

测试点编号使用项目/IP前缀加功能类别和类别内序号，例如DDR.001.001；类别不同则第二段改变，子类别单列。关联用例使用名称；一个用例覆盖多个测试点时分别反标编号与内容。

## 准备与输入怎么写

只写本例新增的核心变量与激励思路，通常3–30行。每个关键输入交代中文含义、来自哪个环境组件、为何这样设置以及对应哪个测试点。例如“AWREADY（写地址接收就绪）由AXI从机BFM控制，延迟接收地址以验证AW/W独立握手”，不用粘贴整套接口变量表。

预期结果要可观察，例如数据保持、握手次数、响应码、错误标志、恢复后的事务内容；不只写“运行正常”。执行过程列不保留，执行结果由实际运行后填写。

## 验证方案

UT聚焦模块行为，可用BFM模拟邻接接口；IT验证真实模块连接、配置和跨模块数据流。采用行为模型时说明模型覆盖到哪个接口，哪些初始化、PHY或软件行为未模拟。

按模板六章展开：验证目的；验证方法及回归安排/完成条件；环境组件；架构与数据流；组件功能设计；代表用例实例。组件设计分别说明激励、driver/BFM、monitor、RM、checker/scoreboard和覆盖的职责。非标准SV/UVM环境按实际组成说明即可。

代表用例应解释一笔事务从刺激到比较所经过的组件和数据，而非只贴框图。完成条件包含计划内功能结果、有效检查、遗留问题处理及覆盖边界，由项目确认；覆盖率数字本身不等于功能正确。
