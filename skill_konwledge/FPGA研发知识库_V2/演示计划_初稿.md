# FPGA研发体系价值演示计划（初稿）

状态：待用户审核；尚未进行对照试验。2026-10-13。

演示时间不限，采用可按讨论深度展开的模块化安排。重点展示用户已确认的厂商风格工程流程，以及团队自身DDR、PCIe、Aurora、以太网业务知识的结合。术语依据来自已确认项目口径，不借用两份已排除PDF为其背书。

## 1. 要让领导看见的价值

核心展示命题：团队已有的规范和工程经验，可以通过四个简短流程入口，在具体设计任务中变成可执行的技术选择、审查内容、测试场景和交付件。

三个需要通过演示验证的价值：少遗漏功能边界；更早发现设计和验证问题；减少工程师反复解释与修订交付件的时间。是否成立及收益大小，由实际输出和运行结果决定。

不要以文档数量或Skill数量作为效果指标。候选差异点必须落到可观察行为：

| 候选差异点 | 演示中展示什么 | 如何确认有价值 |
|---|---|---|
| 团队工程口径贯穿四阶段 | 同一功能在方案、RTL、测试和报告中的一致关系 | 检查功能遗漏、前后矛盾、需要人工纠正的次数 |
| 技术内容带适用条件 | 相同的FIFO、时钟或IP术语，在不同配置下选择不同实现与检查 | 统计错误套用历史参数、IP模式和接口语义的数量 |
| 企业/项目规则可执行 | 原有规则编号、例外、实际代码问题和整改对应 | 对适用规则逐项计数；同时报告误报，避免只靠多提问题取胜 |
| 验证能发现真实错误 | checker对丢拍、重复、反压不稳定、错误提交等受控缺陷报错 | 缺陷检出率和正常设计误报率 |
| 改动可以追踪到交付 | 修改一项需求后，方案、RTL、用例及检查同步更新 | 变更遗漏数、人工修改时间和复测范围合理性 |
| 离线仍能使用核心内容 | 断开联网条件后通过包内材料完成关键技术判断 | 必要资料可达性、缺失依赖数；GLM5.2效果需内网实测 |

这些是本方案的设计特点，未经竞品实测不宣称其他产品不具备。

## 2. 演示主线（先讲清价值，再展开技术）

| 环节顺序 | 内容 | 领导看到的证据 |
|---|---|---|
| 1 痛点 | 一个实际痛点：数据似乎已进入模块，为什么仍不能判定交付通过 | 从已有案例选接口语义或Host观察模型问题；标注历史记录与验证边界 |
| 2 对照 | 同一任务的对照输出 | 展示真正影响功能的差异，保留基线做对的部分；不比较文案长短 |
| 3 工程链路 | 一个功能贯穿四阶段 | 功能条目→实现决策→代码审查→测试点/用例→自检结果，逐步定位对应内容 |
| 4 验证有效性 | 给验证环境注入一个受控缺陷 | 正常版本通过、缺陷版本失败，以及定位到测试点的证据；使用隔离样例 |
| 5 收益 | 展示实测计分表 | 首轮功能结果、规则缺陷、人工返工、有效测试、总周期，含未完成项 |
| 6 推广 | 说明适用范围和下一步试点 | 给出实际可复用交付件、仍需工程师决策的内容，以及试点任务与验收口径 |

长时间的EDA编译和回归预先运行并保留完整记录；现场只做有把握的短演示。使用录制/归档结果时明确其身份，不冒充现场运行。

## 3. 演示任务与三组对照

建议采用一个新的“带反压和异常恢复的帧缓存控制模块”，调用项目允许的FIFO实现。它能展示接口、缓存、时序、复位和验证组织，而不要求现场等待完整DDR或PCIe模型启动。

工程师先完成统一输入规格，至少明确数据宽度、容量、最大帧长、时钟关系、允许的反压、复位时未完成帧处理及超时策略。测试前冻结取值；本计划不替工程师擅自决定项目参数。所选任务应没有可直接照抄的完整答案，排除库中近似成品RTL/TB。

| 组别 | 输入与使用方式 | 比较目的 |
|---|---|---|
| A：现有使用方式 | 相同需求、模板、项目规则和可访问技术资料，常规任务提示 | 建立真实可用的基线，不能故意不给必要规范 |
| B：四阶段流程 | A的全部材料，加四个流程Skill；没有新整理的技术决策正文 | 观察流程组织是否减少遗漏和返工 |
| C：完整体系 | B加按功能整理的技术知识与调用关系 | 观察知识组织的增量；C新增事实应同时补入A/B可访问的原始材料 |

固定模型、版本/设置、工具、预算与需求答复，用独立会话及输出目录。三组均可检索本组全部获准资料；不暗中手工给C挑答案。超过预算按未完成记录。A也使用真实日常提示，不设置弱化基线。

先做一次探索确认任务与指标可用，再在冻结条件下至少做三次独立重复。展示全部结果及中位数/范围；小样本只支持该任务结论。内网GLM5.2另做同模型A/B/C试点，不用不同模型间的差异冒充知识库收益。本轮先制作计划，不启动模型试验或EDA任务。

## 4. 量化指标与收益表达

| 指标 | 计算口径 | 说明 |
|---|---|---|
| 首轮功能验收率 | 首次提交通过的独立验收项数÷适用验收项总数 | 测试清单和权重提前冻结；同时报告未运行项 |
| 适用规范缺陷 | 人工复核确认的违规数量，按已有级别分类 | 同时给出检查项总数；不因代码行数少就判定更好 |
| 验证缺陷检出率 | 被验证环境正确检出的有效注入缺陷数÷有效注入缺陷总数 | 使用同一组缺陷；排除等价/未被激活的注入项并记录原因 |
| 正常设计误报率 | 正常场景被错误判失败的数量÷正常场景总数 | 防止通过“全部报错”获得高检出率 |
| 人工返工时间 | 工程师阅读、解释、纠正、复审的实际活跃分钟数 | 工具等待单列；区分首次与重复运行 |
| 交付总周期 | 统一需求下发至满足同一验收条件的实际时长 | 未达标不计算为更快完成 |
| 变更遗漏数 | 需求改动后应更新但未更新的相关输出项数 | 用一项预先冻结的变更做补充试验 |

节省比例 =（基线时间−完整体系时间）÷基线时间。存在零基线或未完成时不强行算百分比。

只有当人工时间节省有实测支持后，才估算推广收益：

年度净工时收益 = 单任务人工时间节省 × 年度适用任务量 − 年度知识维护与培训工时。

基线时间、任务量、维护成本和实际结果在演示材料中均填写真实数据，不预填“提升30%”等目标为成绩。功能正确性是前提，不能用更快生成文件抵消缺陷。

## 5. 准备与审核

需要准备：统一任务规格、A/B/C输入快照、近似答案排除清单、工程师审核的独立验收项、隔离的缺陷注入样例、计分表、四阶段代表交付件和运行记录。

旧案例用来说明为何选择这些检查；新任务对照用于检验体系是否带来增益。最有说服力的演示结果是一项具体问题被更早发现并减少返工，配合完整计分表，而不是只展示被选中的成功截图。

审核后再冻结演示任务和验收指标，制作实际对照材料。当前只交付演示计划，不执行模型对照、缺陷注入或EDA试验。


## 6. 主打优势：工程流程、本行业务与发布安全

| 优势主张 | 本体系的具体落点 | 对照指标 |
|---|---|---|
| 用户已确认的厂商风格流程在AI开发中持续执行 | 人工系统需求初值、规格/方案、四步代码检查、验证策划先于验证代码、阶段确认与问题闭环 | 适用流程项完成数/总数；没有依据却宣称完成的项数；阶段间矛盾数 |
| 上传与发布安全检查 | 上传前处理正文/隐藏信息，发布可选文档或代码包加密；当前为操作说明 | 预置敏感项发现与清理数/总数、脱敏后语义错误数、加密后授权接收可读性 |
| 团队编码口径直接落实到RTL | 四条CUSTOM-RTL规则、原有命名及审查口径、FPGA适用范围和例外 | 首次交付的违规数、整改轮数、误报数 |
| 知识贴近我们的FPGA业务 | DDR初始化/AXI读写、Aurora不可反压入口、PCIe Host观察模型、以太网数据与描述符一致性 | 预先冻结的业务边界遗漏率；错误引用其他工程参数的次数 |
| 设计与验证相互对应 | 规格→测试点→用例→验证代码反标，验证方案明确组件和数据流 | 有正确实质对应关系的功能数/适用功能总数，不仅检查ID是否存在 |
| 交付可接手、可修改 | 同一模板、清楚接口中文含义、异常与模型边界、顺序每日回归 | 另一名工程师理解/复现所需时间；需求变更遗漏数 |

建议领导版只保留三项核心数字：首轮功能验收率、有效缺陷检出率、人工返工分钟数。其余指标用于解释这三项为何变化。结果暂为空，不用文档覆盖率代替实际研发收益。

## 7. 与网上方案和其他人的做法怎样比较

已做公开页面初步查看，日期2026-10-13；仅用于选择对照样本，未安装、未运行或全面审查这些项目：

- [RTL-Auto-sim-verify-skills](https://github.com/lhx66/RTL-Auto-sim-verify-skills)：公开README描述RTL分析、自检TB、ModelSim仿真、日志分析和自动修复；也要求确认推断的设计意图。因此“有自检和修复闭环”不能作为我们独有的卖点。
- [verilog-generator](https://github.com/Eriemon/verilog-generator)：公开README描述Verilog-2001生成、行为解释、语义注释、诊断修复及TB准备。因此“代码可读、带语义注释”也不能单独证明优势。
- [rtl-skills](https://github.com/phamcuong21478/rtl-skills)：项目介绍覆盖架构、RTL、仿真、自检、回归、Vivado综合与文档。不能把“覆盖全流程”直接视为我们的独占能力。

本体系的比较重点是对我们团队的适配：同样获得项目规则和原始业务资料后，是否更准确执行既有工程流程、选择适用知识、覆盖业务边界并交付可接手的输出。对方能做到的要如实记录；未在已查看材料发现的内容标记“未确认”，不写“没有”。

比较分两层：A/B/C用于拆解流程和知识的增量；从上述公开候选中选一个满足环境条件的完整方案，以及本地同事版本，分别作为额外对照D/E。D/E保持原工作方式，不硬套我们的Skill；给相同输入资料、工具与预算，按同一功能标准验收。工具不兼容时先记录部署/适配成本，不能把环境失败算成RTL能力差。

预演前冻结候选版本/commit、文件清单、可用工具及改动；若要适配，保留原版与适配版差异和人工时间。领导材料列出比较样本，结论只覆盖实际测过的样本与任务，不写“优于全网”。

两阶段试点：先用一个新模块检查是否值得扩大投入，再扩到DDR/AXI控制、跨IP接口集成、既有模块变更三个业务任务；每个任务保留重复运行和人工复核。允许结论为“某类任务提升明显、另一类仍需补齐”。

建议试点决策口径：功能验收不退步、正常场景不增加误报，同时人工返工或有效缺陷检出有可重复改善，才讨论扩大使用。幅度用实测值展示；不提前设定必须赢的结果。


## 9. 安全检查展示（可选短环节）

用人工构造的示例文件放入虚构项目名、内网地址、文档作者属性和隐藏批注等测试项，演示上传前脱敏的检查范围；统计清理项及误删/语义破坏。发布时说明可选加密文档或代码包，并在授权接收端验证解密后内容完整。使用虚构信息，不展示真实凭据，不实际外发。当前仅有[安全操作说明](references/上传与发布安全检查.md)，不能展示为已实现自动扫描/加密产品。

本计划附属于知识库建设，先完善知识内容、引用与适用边界，再按审核结果准备演示；不在当前阶段投入模型比赛、PPT制作或大规模评测。
