## 2. 三个参考工程各自做什么

### 2.1 工程 1：XDMA 到片内 BRAM

工程 1 是最小的 XDMA Memory-Mapped 例程。核心拓扑是：

```text
PCIe Gen3 x8
    |
  XDMA
    | M_AXI，256 bit @ 250 MHz
    v
SmartConnect
    |
AXI BRAM Controller，256 bit
    |
32 KiB True Dual Port BRAM
```

控制面另有：

```text
XDMA M_AXI_LITE
    |
AXI Interconnect
    |
AXI GPIO @ 0x4000_0000 / 64 KiB
    +-- LED 输出
    +-- KEY 输入与用户中断
```

地址映射：

| XDMA 地址空间 | 下游 | 地址 |
| --- | --- | --- |
| `M_AXI` | BRAM | `0x0000_0000`，32 KiB |
| `M_AXI_LITE` | AXI GPIO | `0x4000_0000`，64 KiB |

H2C/C2H 通道并不是直接连接 BRAM 端口。主机驱动提交 DMA 后，XDMA 在卡端发起 AXI 读写：

- H2C：Host memory -> PCIe -> XDMA -> `M_AXI` 写 BRAM；
- C2H：XDMA 从 BRAM 发起 `M_AXI` 读 -> PCIe -> Host memory。

双口 BRAM 的两个端口都接在同一个 AXI BRAM Controller 上，工程 1 没有第二个用户逻辑 AXI master。

### 2.2 工程 3：Windows 端读写程序

工程 3 没有 FPGA 工程，只有 Qt/Windows 应用。它通过 Xilinx XDMA Windows 驱动完成：

```text
SetupAPI 枚举 GUID_DEVINTERFACE_XDMA
    |
    +-- 打开 \h2c_0
    +-- 打开 \c2h_0
    |
SetFilePointer(offset)
WriteFile / ReadFile
```

界面点击“发送数据”后：

1. 把文本编码成 UTF-8；
2. 对 `\h2c_0` 的 offset 0 执行 `WriteFile`；
3. 对 `\c2h_0` 的 offset 0 执行 `ReadFile`；
4. 显示读回文本。

因此工程 3 本质是工程 1 的 BRAM loopback 软件，也能直接用于工程 6 的 DDR offset 0 读回测试。它不打开 `\user`，不访问 AXI-Lite GPIO，也不测试中断。

这份程序适合作为 bring-up 样例，不适合作为当前工程的完整上位机：

- 只处理 channel 0；
- offset 使用 32-bit `long`；
- 错误返回值没有完整传回 UI；
- 小于 5 字节时采用“先读 10 字节再复制”的特殊处理；
- 枚举多个 XDMA 设备时保留的是最后一个设备路径；
- 不实现当前工程的寄存器协议、中断确认和 Aurora 数据窗口管理。

### 2.3 工程 6：XDMA 到板载 DDR4

工程 6 保留工程 1 的 XDMA 和 AXI-Lite GPIO，把 BRAM 数据面替换成 DDR4：

```text
PCIe Gen3 x8
    |
  XDMA
    | M_AXI，256 bit @ 250 MHz
    v
SmartConnect，NUM_CLKS=2
    | 256 bit @ DDR UI clock
    v
DDR4 MIG AXI slave
    |
板载 DDR4，4 GiB 地址空间
```

关键 DDR 配置：

| 配置 | 值 |
| --- | --- |
| FPGA | `xcku040-ffva1156-2-i` |
| Memory part | `MT40A512M16HA-083E` |
| 物理数据宽度 | 64 bit |
| AXI 数据宽度 | 256 bit |
| AXI 地址宽度 | 32 bit |
| DDR time period | 833 ps，约 1200 MHz CK / DDR4-2400 数据率 |
| 输入参考时钟周期 | 9996 ps，约 100 MHz |
| CAS latency | 16 |
| 地址映射 | `ROW_COLUMN_BANK` |
| XDMA 数据窗口 | `0x0000_0000`，4 GiB |
| AXI-Lite GPIO | `0x4000_0000`，64 KiB |

时钟与复位关系：

```text
XDMA axi_aclk --------------------> SmartConnect aclk
DDR c0_ddr4_ui_clk --------------> SmartConnect aclk1
DDR c0_ddr4_ui_clk_sync_rst -----> proc_sys_reset/ext_reset_in
proc_sys_reset/peripheral_aresetn -> DDR c0_ddr4_aresetn
pcie_rst_n -> NOT -> DDR sys_rst
```

SmartConnect 因而同时承担 XDMA 250 MHz 域到 DDR UI 时钟域的转换。

需要注意：`c0_init_calib_complete` 没有接入控制、状态或 AXI 请求门控。该例程能说明基础连法，但当前工程迁移时应增加校准完成状态和 memory-ready 门控。

## 3. 当前工程的对应结构

当前工程 `RTDS_test-1ch` 沿用了工程 1 的“XDMA 访问共享存储”思想，但已经从测试例程扩展成双主设备、双向数据桥：

```text
                         +---------------------------+
Host H2C/C2H <-> XDMA ---|                           |
                         | AXI Interconnect           |--> AXI BRAM Ctrl
Aurora adapter           |                           |        |
  <-> CONV_DMA ----------|                           |      64 KiB BRAM
                         +---------------------------+
```

两个 AXI master 都映射同一个 64 KiB BRAM：

| Master | 用途 | 地址 |
| --- | --- | --- |
| `xdma_0/M_AXI` | CPU H2C/C2H payload | `0x0000_0000`，64 KiB |
| `CONV_DMA_0/M_AXI` | Aurora adapter 的 FDMA 读写 | `0x0000_0000`，64 KiB |

AXI-Lite 控制面则把参考工程的 GPIO 换成了 `INFO_EXCH`：

```text
XDMA M_AXI_LITE
    |
AXI Interconnect
    |
INFO_EXCH @ 0x4000_0000 / 4 KiB
```

`INFO_EXCH` 保存地址、长度、启动、完成、接收确认和中断状态。XDMA 的 `usr_irq_req` 也不再来自 GPIO，而是来自当前 adapter 的 `FPGA_CPU_irq_req`。

当前 XDMA 与参考工程的主要差异：

| 项目 | 工程 1/6 | 当前工程 |
| --- | --- | --- |
| PCIe link | Gen3 x8 | Gen3 x2 |
| XDMA AXI 宽度 | 256 bit | 64 bit |
| H2C/C2H channel | 各 4 个 | 各 1 个 |
| Device ID | `0x8038` | `0x8032` |
| 用户中断 | 1 | 1 |
| payload memory | 32 KiB BRAM / 4 GiB DDR | 64 KiB BRAM |
| payload AXI master 数 | 1 | 2：XDMA + CONV_DMA |
| AXI-Lite slave | GPIO | INFO_EXCH |
| 工具版本 | 2023.1 / 2024.2 | 2020.2 |

## 4. 当前工程的真实双向数据流

### 4.1 CPU 到 Aurora

```text
CPU
  | 1. H2C 写 payload 到卡端 0x8000..0xffff
  v
XDMA -> BRAM

CPU
  | 2. 通过 \user 写 INFO_EXCH 的地址、长度、CPU_WR_DONE
  v
INFO_EXCH -> RD_START
  v
adapter -> CONV_DMA 发起 AXI read
  v
BRAM -> CONV_DMA -> adapter FIFO -> Aurora
```

当前 adapter 固定使用 512 B frame，即每帧 64 个 64-bit beat。CPU->Aurora 活动窗口为：

```text
0x0000_8000..0x0000_ffff
```

### 4.2 Aurora 到 CPU

```text
Aurora -> adapter FIFO
  v
CONV_DMA 发起 AXI write
  v
BRAM 0x0000_0000..0x0000_7fff
  v
adapter 更新 INFO_EXCH 状态并触发 XDMA user IRQ
  v
CPU 读取寄存器给出的地址/长度
  v
CPU 通过 C2H 读取 payload，并写 CPU_REC_STATE 确认
```

所以当前工程不是简单的“CPU 写后立刻从同一地址读回”。BRAM 是 CPU 与 Aurora 两侧共享的 payload mailbox，`INFO_EXCH` 是控制面，`CONV_DMA` 是 FPGA 侧的第二个内存访问者。

## 5. 工程 3 如何对应当前软件

工程 3 的底层 `\h2c_0`、`\c2h_0` 打开方式仍可复用，但调用顺序要扩展。

CPU->Aurora 至少需要：

1. `\h2c_0` 向 offset `0x8000` 写 payload；
2. 打开 `\user`；
3. `\user + 0x24` 写 `CPU_FPGA_START_ADDR=0x8000`；
4. `\user + 0x28` 写长度，必须是 512 B 的整数倍且不超过 32 KiB；
5. `\user + 0x20` 写 `CPU_WR_DONE` 上升沿，触发发送；
6. 轮询完成状态或等待事件。

这里 `\user` 的文件 offset 是 INFO_EXCH 内部偏移 `0x00..0x28`。XDMA 已把该 BAR 映射到卡端 AXI-Lite `0x4000_0000`，应用通常不需要把 `0x4000_0000` 再加到文件 offset。

Aurora->CPU 至少需要：

1. 等待 XDMA event 或轮询 INFO_EXCH；
2. 从 `\user + 0x18/0x1c` 读取 FPGA 给出的地址和长度；
3. 通过 `\c2h_0` 从该 payload offset 读取；
4. 通过 `\user + 0x14` 写 `CPU_REC_STATE` 进行接收确认；
5. 按协议清中断。

## 6. 工程 6 对当前 DDR 迁移的价值

工程 6 是当前工程 DDR 化最有价值的板级参考，但它不是可以直接替换的完整方案。

可以继承或核对：

- DDR4 part、64-bit byte-lane 组织和完整管脚表；
- `AK17/AK16` 的 100 MHz DDR 差分参考时钟；
- DDR4-2400、256-bit AXI、4 GiB 地址空间等 MIG 参数；
- SmartConnect 双时钟连接思路；
- DDR UI reset 到 AXI reset 的基本关系；
- 同一 FPGA 型号和同一 board A 的板级实现证据。

必须保留当前工程自己的部分：

- Gen3 x2、Device ID `0x8032`、单 H2C/C2H channel 的 XDMA 配置；
- `CONV_DMA + XDMA` 两主设备仲裁；
- `INFO_EXCH` 寄存器和中断协议；
- 64 KiB 首版逻辑窗口及 RX/TX 各 32 KiB 的软件契约；
- Aurora adapter、FIFO、CDC 和错误状态。

推荐目标 BD：

```text
CONV_DMA 64 bit @ 250 MHz ---- S00
                                  \
                                   AXI Interconnect/SmartConnect
                                  /         |
XDMA M_AXI 64 bit @ 250 MHz ---- S01       | width + clock conversion
                                            v
                                  DDR MIG S_AXI 256 bit @ ui_clk
                                            |
                                           DDR4
```

首版仍只映射最低 64 KiB。等 BRAM 基线、MIG 校准和 DDR H2C/C2H 都独立通过后，再扩大软件窗口。

## 7. 两个不能忽略的迁移风险

### 7.1 Vivado 版本不能直接回退

当前工程固定在 Vivado 2020.2。参考工程 1 的 BD 标记为 2023.1；工程 6 已在 2026-07-24 用 Vivado 2024.2 升级：

- XDMA Rev.23 -> Rev.31；
- AXI Interconnect Rev.29 -> Rev.34；
- SmartConnect Rev.20 -> Rev.25。

因此不能把工程 6 当前的 `.xpr/.bd/.xci` 直接加入 2020.2。正确做法是在 Vivado 2020.2 中按工程 6 的参数和管脚重新创建 DDR4 IP 与 BD 连接，并逐项核对端口和参数。

如果能从参考目录的备份或发布包中找到升级前的 2020.2 工程，它会比当前已升级版本更适合作为移植起点。

### 7.2 DDR 参考时钟与当前系统时钟占用同一对管脚

工程 6：

```text
AK17/AK16 -> DDR4 C0_SYS_CLK，100 MHz
```

当前工程：

```text
AK17/AK16 -> clk_p/clk_n -> CLK_GEN
                         +-> 250 MHz
                         +-> 156.25 MHz
                         +-> 100 MHz
```

不能把两个工程的输入缓冲原样并列实例化，否则会重复占用同一差分输入和管脚。

应在 2020.2 中选择一种明确架构：

1. 外部 100 MHz 只进入一个共享 IBUFDS/时钟入口，再分别送给 MIG 和系统 Clock Wizard；或
2. 由 MIG 接收外部 100 MHz，再使用允许的 UI/additional clock 输出和后级 Clock Wizard 生成系统时钟。

具体方案必须按 DDR4 IP 2020.2 对“外部差分时钟/无缓冲内部时钟”的支持方式确定，并通过 `report_clock_interaction`、DRC 和实现后的时钟专用路由检查。

## 8. 建议验证顺序

```text
G0  当前 64 KiB BRAM 全链路
    Host H2C -> BRAM -> CONV_DMA -> Aurora loop
    -> CONV_DMA -> BRAM -> Host C2H

G1  2020.2 独立 DDR MIG
    init_calib_complete + traffic generator/BIST

G2  当前 XDMA x2 -> DDR
    只测 H2C/C2H，不接 Aurora

G3  XDMA + CONV_DMA 双 master -> DDR
    加仲裁、随机 backpressure、AXI response 检查

G4  恢复 INFO_EXCH、IRQ、Aurora 全闭环
```

工程 1 给出最小 XDMA/BRAM 数据面，工程 3 给出 Windows 驱动访问入口，工程 6 给出板载 DDR4 的物理层与单主 AXI 接法；当前工程是在这条基础链路上增加第二个 AXI master、控制寄存器、中断以及 Aurora 数据桥。三者是递进关系，不是三个互相独立的实现。
