## 方法1：使用不同的工作区文件（推荐）

<!-- 本节围绕“方法1：使用不同的工作区文件（推荐）”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

每个项目保存为独立的工作区文件：

1. **文件 → 将工作区另存为...**
2. 保存为 `project1.code-workspace`、`project2.code-workspace`
3. 通过 **文件 → 打开工作区...** 切换不同项目

每个工作区文件会记录：
- 包含的文件夹
- 打开的文件
- 编辑器布局
- 扩展设置

---

## 方法2：多窗口模式

<!-- 本节围绕“方法2：多窗口模式”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

打开多个独立的 Trae 窗口，每个窗口对应一个项目：

1. **文件 → 新建窗口**（或 `Ctrl+Shift+N`）
2. 在新窗口中打开不同的项目文件夹
3. 每个窗口完全独立，互不干扰

---

## 方法3：使用工作区设置

<!-- 本节围绕“方法3：使用工作区设置”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

为每个工作区创建独立的配置文件：

在项目根目录创建 `.vscode/settings.json`：

```json
{
  "files.exclude": {
    "**/*.md": true
  },
  "search.exclude": {
    "**/node_modules": true
  }
}
```

这样每个项目可以有独立的忽略规则、扩展配置等。

---

## 方法4：使用配置文件切换

<!-- 本节围绕“方法4：使用配置文件切换”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

# 打开特定工作区
trae project1.code-workspace

# 打开特定文件夹
trae C:\project\LLM\pro_spi
```

## 终端默认路径与 `folders` 的关系

<!-- 本节围绕“终端默认路径与 `folders` 的关系”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

### 当前情况

| 项目 | 路径 |
|------|------|
| **工作区文件位置** | `C:\project\LLM\pro_spi\project1.code-workspace` |
| **终端默认路径** | `C:\project\LLM\pro_spi`（工作区文件所在目录） |
| **工作区包含的文件夹** | `C:\project\LLM\pro_spi\project1`（`folders` 中配置的） |

### 关键关系

<!-- 本节围绕“关键关系”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

- **终端默认路径** = 工作区文件（`.code-workspace`）所在的目录
- **`folders` 配置** = 工作区"包含"哪些文件夹（显示在左侧资源管理器）
- 两者是**独立**的：终端路径由工作区文件位置决定，`folders` 只决定资源管理器显示什么

<!-- 本节围绕“如何永久改变终端默认路径”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

### 方法1：移动工作区文件到新目录（推荐）

3. **重新打开工作区**：
   - 在新目录中打开 `project1.code-workspace`

### 方法2：修改 `folders` 路径指向新目录

<!-- 本节围绕“方法2：修改 `folders` 路径指向新目录”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

```

### 1. 系统架构概览

<!-- 本节围绕“1. 系统架构概览”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

这是一个**FIFO到AXI4的桥接设计**，主要用于将简单的FIFO接口转换为标准的AXI4接口，以便与DDR3存储控制器进行数据传输。

**整体架构图：**
```
┌─────────────────────────────────────────────────────────────────┐
│                     fifo_axi_adapter_top                        │
│  ┌──────────────┐   ┌─────────────────┐   ┌──────────────────┐  │
│  │ 写FIFO      │   │ fifo_to_axi4    │   │ AXI4 Master      │  │
│  └──────────────┘   └─────────────────┘   └──────────────────┘  │
│  ┌──────────────┐   ┌─────────────────┐   ┌──────────────────┐  │
│  │ 读FIFO      │   │ axi4_to_fifo    │   │ AXI4 Master      │  │
│  └──────────────┘   └─────────────────┘   └──────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

**核心设计理念：**
1. **时钟域隔离**：使用双时钟FIFO实现不同时钟域的数据传输（wr_fifo_clk/rdfifo_clk vs AXI时钟clk）
2. **突发传输优化**：利用AXI4的burst传输特性，一次burst最多传输32个数据（AXI_BURST_LEN=31）
3. **地址自动管理**：自动维护读写地址指针，到达地址上限（WR_AXI_BYTE_ADDR_END/RD_AXI_BYTE_ADDR_END）后回绕到起始地址

#### (1) fifo_axi_adapter（顶层模块）

<!-- 本节围绕“(1) fifo_axi_adapter（顶层模块）”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

**功能**：连接外部世界与AXI4转换模块，集成两个双时钟FIFO

**参数说明**：
- `FIFO_DW`：FIFO数据位宽（用户侧）
- `AXI_DATA_WIDTH`：AXI总线数据位宽（通常64/128位）
- `WR_AXI_BYTE_ADDR_BEGIN/END`：写地址范围
- `RD_AXI_BYTE_ADDR_BEGIN/END`：读地址范围

**关键信号**：
- `wr_fifo_clr/rdfifo_clr`：异步清除信号
- `wr_fifo_clk/rdfifo_clk`：FIFO侧时钟
- `wr_fifo_wren`：写FIFO写使能
- `rdfifo_rden`：读FIFO读使能
- `wr_fifo_full/rdfifo_empty`：状态指示

#### (2) fifo_to_axi4（写路径）

<!-- 本节围绕“(2) fifo_to_axi4（写路径）”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

**状态机设计（关键！）**：
```
IDLE (等待数据) → WR_ADDR (发送地址) → WR_DATA_PRE → WR_DATA (发送数据) → WR_RESP (等待响应) → 回IDLE
```

**关键设计要点**：
1. **数据缓存机制**：`fifo_rddata_latch`用于暂存FIFO输出数据，配合AXI4的握手信号
2. **Burst计数**：`wr_data_cnt`追踪当前burst已传输的数据量
3. **地址自动管理**：每次成功完成burst传输后，地址自动递增`(AXI_BURST_LEN+1)*(AXI_DATA_WIDTH/8)`

**核心信号时序**：
```
wr_ddr3_req条件：!fifo_rst_busy && !fifo_empty && (fifo_rd_cnt >= wr_req_cnt_thresh)
```
- 只有当FIFO中至少有一个burst的数据量时，才会启动AXI4传输

#### (3) axi4_to_fifo（读路径）

<!-- 本节围绕“(3) axi4_to_fifo（读路径）”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

**状态机设计**：
```
IDLE (等待FIFO空间) → RD_ADDR (发送读地址) → RD_RESP (接收数据) → 回IDLE
```

**关键设计要点**：
1. **流控机制**：`m_axi_rready = !fifo_alfull`，只有当FIFO有空间时才接收数据
2. **数据缓冲**：`rdfifo_din`直接连接AXI4读数据，配合`rdfifo_wren`控制写入

#### 时钟域交叉处理

<!-- 本节围绕“时钟域交叉处理”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->
- **写FIFO**：写时钟域（wr_fifo_clk）→ 读时钟域（clk，AXI时钟）
- **读FIFO**：写时钟域（clk）→ 读时钟域（rdfifo_clk）
- **同步器**：`wr_fifo_clr_sync_clk`和`rdfifo_clr_sync_clk`用于同步清除信号

**潜在风险**：
- 如果FIFO的复位信号跨时钟域未正确同步，可能导致FIFO状态不一致
- 建议复位信号采用三级同步器，确保亚稳态消除

本设计旨在解决**不同时钟域之间的数据传输**以及**从简单FIFO接口到标准AXI4协议的转换**问题。在FPGA开发中，经常会遇到以下场景：

- **高速数据采集**：采集前端可能使用较高位宽但简单的FIFO接口，而后端存储需要AXI4标准协议
- **跨时钟域处理**：采集时钟与存储器时钟完全不同，需要双时钟FIFO进行隔离
- **IP核复用**：现有的DDR3控制器通常提供AXI4接口，而用户侧设计可能只支持FIFO协议

本设计为上述场景提供了一个完整的解决方案。

#### 3.1 fifo_to_axi4模块详细分析

##### 3.1.1 状态机设计与原理

<!-- 本节围绕“3.1.1 状态机设计与原理”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

写路径采用5状态FSM设计，这是确保AXI4协议正确性的关键：

```
    ┌─────────────────────────────────────────────────────────────┐
    │                        IDLE State                              │
    │           (等待FIFO中积累足够的数据)                          │
    └──────────────────┬────────────────────────────────────────────┘
                       │ if (wr_ddr3_req == 1)
                       │
                       │
    ┌──────────────────▼────────────────────────────────────────────┐
    │                    WR_ADDR State                                │
    │         (发送写地址、长度、类型等控制信息)                       │
    └──────────────────┬────────────────────────────────────────────┘
                       │ if (m_axi_awready && m_axi_awvalid)
                       │
                       │
    ┌──────────────────▼────────────────────────────────────────────┐
    │                   WR_DATA_PRE State                            │
    │         (准备开始发送数据，提前一个周期使能)                    │
    └──────────────────┬────────────────────────────────────────────┘
                       │
                       │
    ┌──────────────────▼────────────────────────────────────────────┐
    │                     WR_DATA State                              │
    │         (连续发送32拍数据，同时从FIFO读取数据)                  │
    └──────────────────┬────────────────────────────────────────────┘
                       │ if (m_axi_wready && m_axi_wvalid && m_axi_wlast)
                       │
                       │
    ┌──────────────────▼────────────────────────────────────────────┐
    │                    WR_RESP State                               │
    │         (等待DDR控制器返回写响应)                              │
    └──────────────────┬────────────────────────────────────────────┘
                       │ if (成功)
                       │
                       │
    ┌──────────────────▼────────────────────────────────────────────┐
    │                    返回 IDLE State                              │
    │         (等待下次触发)                                          │
    └─────────────────────────────────────────────────────────────┘
```

**各状态详细说明**：

1. **IDLE状态**：
   - **任务**：持续监控FIFO状态
   - **退出条件**：`wr_ddr3_req == 1`（FIFO中至少有一个burst的数据）
   - **关键设计**：不立即启动传输，直到积累足够数据，保证传输效率

2. **WR_ADDR状态**：
   - **任务**：在AW通道上发送地址和控制信息
   - **信号**：
     - `m_axi_awvalid`：地址有效信号
     - `m_axi_awaddr`：起始地址
     - `m_axi_awlen`：突发长度（31=32拍）
     - `m_axi_awsize`：数据宽度（128位对应4'b100）
     - `m_axi_awburst`：突发类型（2'b01=INCR增量）
   - **退出条件**：`m_axi_awready && m_axi_awvalid`（地址握手成功）

3. **WR_DATA_PRE状态**：
   - **任务**：准备数据通道
   - **设计理由**：
     - FIFO读取有1周期延迟（fifo_rdreq→fifo_rddata_valid需要1拍）
     - 此状态提前发出`fifo_rdreq`，让FIFO数据准备好
     - 同时处理`m_axi_wvalid`的时序

4. **WR_DATA状态**：
   - **任务**：连续发送完整burst的数据
   - **关键计数器**：`wr_data_cnt`追踪已传输的数据量
   - **信号交互**：
     - `fifo_rdreq`：从FIFO读取下一个数据
     - `m_axi_wdata`：发送数据
     - `m_axi_wstrb`：字节使能（全选，128位对应16'hFFFF）
     - `m_axi_wlast`：最后一拍标记
   - **退出条件**：`m_axi_wready && m_axi_wvalid && m_axi_wlast`（最后一拍握手成功）

5. **WR_RESP状态**：
   - **任务**：等待B通道响应
   - **关键检查**：
     - `m_axi_bresp`：响应编码（2'b00=OKAY，成功）
     - `m_axi_bid`：匹配事务ID
   - **地址更新**：成功后地址自增`(AXI_BURST_LEN+1)*(AXI_DATA_WIDTH/8)`
   - **退出条件**：响应成功，返回IDLE

##### 3.1.2 地址自动管理机制

<!-- 本节围绕“3.1.2 地址自动管理机制”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

设计了完善的地址管理逻辑，让用户无需手动维护地址：

```verilog
// 地址回绕机制（关键设计！）
if (reset) begin
    m_axi_awaddr <= WR_AXI_BYTE_ADDR_BEGIN;
end else if (addr_clr || axi_awaddr_clr) begin
    m_axi_awaddr <= WR_AXI_BYTE_ADDR_BEGIN;  // 清除时回到起点
end else if (m_axi_awaddr >= WR_AXI_BYTE_ADDR_END) begin
    m_axi_awaddr <= WR_AXI_BYTE_ADDR_BEGIN;  // 到达上限回绕
end else if ((curr_wr_state == WR_RESP) && m_axi_bready && m_axi_bvalid &&
            (m_axi_bresp == 2'b00) && (m_axi_bid == AXI_ID[AXI_ID_WIDTH-1:0])) begin
    m_axi_awaddr <= m_axi_awaddr + ((m_axi_awlen + 1'b1)*(AXI_DATA_WIDTH/8));  // 自增
end else begin
    m_axi_awaddr <= m_axi_awaddr;  // 保持不变
end
```

**设计要点解析**：

1. **环形缓冲区概念**：地址范围被视为环形，到达上限自动回绕到起点
2. **用户侧简化**：外部用户只需写入FIFO，不需要关心地址
3. **回绕时机**：在每次完整burst传输成功后才检查并可能回绕
4. **应用场景**：适合数据缓存、视频帧缓冲等需要连续覆盖的场景

**注意事项**：此设计假设了存储器区域可以安全覆盖，对于需要永久存储数据的场景不适用！

##### 3.1.3 流控与触发条件

<!-- 本节围绕“3.1.3 流控与触发条件”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

触发写事务的条件非常关键，确保了传输效率和数据安全：

```verilog
assign wr_req_cnt_thresh = (m_axi_awlen == 'd0) ? 1'b1 : (AXI_BURST_LEN[7:0]+1'b1);
assign wr_ddr3_req = (fifo_rst_busy == 1'b0) && (!fifo_empty) && (fifo_rd_cnt >= wr_req_cnt_thresh) ? 1'b1:1'b0;
```

**三个必要条件解析**：

1. `!fifo_rst_busy`：FIFO已完成复位，不在复位忙碌状态
   - **必要性**：避免FIFO状态不稳定时读取数据

2. `!fifo_empty`：FIFO非空，至少有一个数据
   - **必要性**：基础条件，没有数据无法传输

3. `fifo_rd_cnt >= wr_req_cnt_thresh`：FIFO中至少有一个完整burst的数据
   - **必要性**：保证每次传输都是完整的burst，最大化总线利用率
   - **值计算**：如果burst长度为0（单次传输），阈值=1；否则阈值=burst长度

**为什么必须积累足够数据？**
- AXI4协议中，burst事务一旦开始不能中途停止
- 如果FIFO中数据不足，可能导致AXI传输中断或错误
- 完整burst传输比单次传输效率更高（减少地址和控制开销）

#### 3.2 数据通道时序设计

<!-- 本节围绕“3.2 数据通道时序设计”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

##### 3.2.1 FIFO读取与数据暂存

<!-- 本节围绕“3.2.1 FIFO读取与数据暂存”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

写路径采用了经典的“请求-有效-锁存”三级流水线：

```
          ┌──────────┐         ┌──────────┐         ┌──────────┐
fifo_rdreq│          │  valid  │          │ data    │          │
─────────►│ Stage 1  ├────────►│ Stage 2  ├────────►│ Stage 3  │
          │  请求    │         │  有效    │         │  锁存    │
          └──────────┘         └──────────┘         └──────────┘
                                                                 │
                                                                 │
                                                                 ▼
                                                            m_axi_wdata
```

**关键时序点**：
1. **Cycle 1**：发出`fifo_rdreq`
2. **Cycle 2**：`fifo_rddata_valid`有效，数据出现在FIFO输出端
3. **Cycle 3**：`fifo_rddata_latch`锁存数据，同时`m_axi_wvalid`拉高

这种设计确保了AXI4的握手信号与数据对齐，符合协议要求。

##### 3.2.2 写数据计数与LAST标记

<!-- 本节围绕“3.2.2 写数据计数与LAST标记”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

```verilog
// wr_data_cnt计数逻辑
if (reset) begin
    wr_data_cnt <= 'd0;
end else if (curr_wr_state == IDLE) begin
    wr_data_cnt <= 'd0;
end else if (m_axi_wready && m_axi_wvalid) begin
    wr_data_cnt <= wr_data_cnt + 1'b1;
end

// m_axi_wlast生成逻辑
if (reset) begin
    m_axi_wlast <= 'd0;
end else if (m_axi_wready && m_axi_wvalid && m_axi_wlast) begin
    m_axi_wlast <= 'd0;
end else if (m_axi_awlen == 'd0) begin
    m_axi_wlast <= 1'b1;  // 单次传输
end else if (m_axi_wready && m_axi_wvalid && (wr_data_cnt == m_axi_awlen - 1'b1)) begin
    m_axi_wlast <= 1'b1;  // 在第30拍拉高，第31拍(最后一拍)有效
end else begin
    m_axi_wlast <= m_axi_wlast;
end
```

**LAST标记设计关键点**：
- **提前一拍断言**：在倒数第二个数据时就设置`m_axi_wlast = 1`
- **在最后一拍握手时清除**：`m_axi_wready && m_axi_wvalid && m_axi_wlast`
- **单次传输处理**：特殊处理`m_axi_awlen == 0`的情况

#### 4.1 axi4_to_fifo模块详细分析

##### 4.1.1 读状态机设计

<!-- 本节围绕“4.1.1 读状态机设计”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

读路径相对简单，采用3状态设计：

```
    ┌─────────────────────────────────────────────────────────────┐
    │                        IDLE State                              │
    │           (等待FIFO有足够空间)                                │
    └──────────────────┬────────────────────────────────────────────┘
                       │ if (rd_ddr3_req == 1)
                       │
                       │
    ┌──────────────────▼────────────────────────────────────────────┐
    │                    RD_ADDR State                                │
    │         (发送读地址和控制信息)                                  │
    └──────────────────┬────────────────────────────────────────────┘
                       │ if (m_axi_arready && m_axi_arvalid)
                       │
                       │
    ┌──────────────────▼────────────────────────────────────────────┐
    │                   RD_RESP State                                │
    │         (接收数据直到m_axi_rlast)                             │
    └──────────────────┬────────────────────────────────────────────┘
                       │ if (成功)
                       │
                       │
    ┌──────────────────▼────────────────────────────────────────────┐
    │                    返回 IDLE State                              │
    └─────────────────────────────────────────────────────────────┘
```

**设计思想**：读操作相对简化，因为：
- 地址通道发送后，无需额外准备阶段
- 数据通道接收过程与写路径类似，但数据方向相反

##### 4.1.2 流控与反压机制

<!-- 本节围绕“4.1.2 流控与反压机制”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

读路径采用了巧妙的流控设计，直接用FIFO状态控制AXI4：

```verilog
assign m_axi_rready = !fifo_alfull;
```

**设计亮点**：
- **直接映射**：FIFO未满就可以接收数据
- **硬件级反压**：无需复杂的状态机处理流控
- **自动暂停**：FIFO满时，`m_axi_rready = 0`，AXI4主机自动停止发送

但这种设计有一个**潜在问题**：如果AXI4不支持接收端反压，可能导致传输错误！不过大多数现代AXI4控制器都支持此特性。

##### 4.1.3 读触发条件

<!-- 本节围绕“4.1.3 读触发条件”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

读事务的触发逻辑：

```verilog
assign rd_req_cnt_thresh = (1<<FIFO_ADDR_WIDTH) - (AXI_BURST_LEN[7:0]+1'b1);
assign rd_ddr3_req = (fifo_rst_busy == 1'b0) && (fifo_wr_cnt < rd_req_cnt_thresh-2'd2) ? 1'b1:1'b0;
```

**关键解析**：
- **阈值含义**：FIFO中剩余空间至少能容纳一个完整burst的数据
- **计算公式**：`FIFO深度 - burst长度`
- **减去2的原因**：为FIFO的读写指针差异留出安全裕度，避免溢出

### 八、性能分析与带宽估算

<!-- 本节围绕“八、性能分析与带宽估算”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

#### 8.1 理论带宽计算

<!-- 本节围绕“8.1 理论带宽计算”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

假设AXI4时钟频率为200MHz，数据位宽为128位：

```
理论带宽 = 频率 × 位宽 / 8
        = 200MHz × 128bit / 8
        = 3200 MB/s = 3.2 GB/s
```

但这只是理论峰值，实际中考虑以下因素：

| 因素 | 影响 | 估算 |
|------|------|------|
| FIFO状态转换开销 | 10%左右 | 扣除 |
| AXI4响应等待 | 5-20% | 扣除 |
| 用户侧数据率限制 | 可能很大 | 实际带宽 = min(AXI带宽, 用户侧带宽) |

**实际估算**：在理想用户侧数据率情况下，预计能达到2.5 GB/s以上。

#### 8.2 FIFO深度选择分析

<!-- 本节围绕“8.2 FIFO深度选择分析”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

当前FIFO深度为64，考虑burst长度为32：

- **最小深度**：至少需要≥2×burst长度（一个burst正在传输，一个burst正在积累）
- **当前深度**：64 = 2×32，刚好满足
- **建议**：如果系统中有其他不确定延迟，建议增加到128或256

### 2. Outstanding深度4设计方案

<!-- 本节围绕“2. Outstanding深度4设计方案”展开，阅读时可结合对应 RTL/testbench 的同名模块或任务。 -->

方案文件：[outstanding_depth4_design.md](file:///C:/project/LLM/pro_spi/outstanding_depth4_design.md)

核心设计要点：

- **写路径**：拆分AW/W状态机与B响应状态机，移除S_WR_RESP状态，W传输完成后直接回到IDLE发起新事务
- **读路径**：拆分AR状态机与R响应状态机，推荐使用固定ID=0保证R数据保序，避免重排序复杂度
- **事务跟踪表**：4入口表记录每个Outstanding事务的active/aw_done/w_done/b_done状态
- **地址管理**：4个独立地址寄存器，每事务独立递增和回绕
- **FIFO深度**：建议从64提升到256，确保4个事务的数据缓冲
- **参数化**：OUTSTANDING_DEPTH参数支持1/2/4，深度1时退化为当前设计
