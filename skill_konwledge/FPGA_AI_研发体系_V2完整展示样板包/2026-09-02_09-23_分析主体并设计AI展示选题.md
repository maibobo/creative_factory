## 二、你现在的观点，哪些对，哪些需要换一种说法

你的方法论基本成立：

- 两个模型意见一致，不等于 RTL 正确。模型之间只能互相提供候选意见，不能构成独立真值。
- 知识库不能提高模型的原创设计上限。它解决的是资料检索、参数依据、规则引用和证据追溯。
- PPT 做得好不能推出代码就写得好。必须分别用代码、仿真、时序、CDC 和板级结果验收。
- 提示词质量取决于使用者是否真正理解接口、时钟、复位、背压和验收边界。

但汇报时不要说“国产模型一个都不能用”。这个结论既没有被现有材料证明，也会让讨论变成模型站队。更有力的工程表述是：

> **任何裸模型输出都不作为验收证据。模型能否进入流程，由同一组工程基准、约束遵守情况和工具结果决定。**

这句话同时限制国产模型、Codex 和 Trae，没有双重标准。

## 三、为什么选 PCIe–Aurora 真实缺陷

现有项目已经有一个非常适合展示的真实问题：

- Aurora RX 的 64 拍数据已经进入 FIFO；
- 但 `rx_burst_done`、IRQ 和后续 C2H 不出现；
- 最终发现 `CONV_DMA` 的历史端口名与实际 valid/ready 语义相反，wrapper 按同名连接造成误接；
- 修复只发生在 `PCIe.v`，引入语义明确的 `fdma_w_source_valid` 和 `fdma_w_accept`，没有修改 FDMA、adapter 或厂商 IP。

问题和根因见[处理台账](E:/PCIE-CPU/docs/RTDS_test_XDMA_RootPort问题发现与处理台账.md:134)，当前修复后的连接见[PCIe.v](E:/PCIE-CPU/RTDS_test-1ch/RTDS_test.srcs/sources_1/new/PCIe.v:82)。

最终已有真实回归证据：

- Gen3 x2；
- 双向 512 B 数据；
- IRQ request/ack；
- scoreboard；
- `errors=0`；
- `RTDS_ROOTPORT_PASS`。

见[台账第236行](E:/PCIE-CPU/docs/RTDS_test_XDMA_RootPort问题发现与处理台账.md:236)和现有[summary.json](E:/centOS/pcie_cpu_vcs_migration/baseline_xsim/logs/summary.json)。

这个题目比“知识库问答”更完整，比“AI 生成全部 RTL”更可信。

需要注意：现有台账能证明缺陷、修复和回归，但不能证明当初一定是 AI 独立找到的。因此不能倒推宣传。正确做法是恢复故障快照，重新跑一遍有完整日志的 Codex 辅助过程。

## 四、工具怎么分工

| 角色 | 负责什么 | 不负责什么 |
|---|---|---|
| 工程师 | 冻结接口、定义 golden result、批准补丁、最终签核 | 不把判断权交给模型 |
| 知识库 | 提供接口规则、历史验证记录和证据路径 | 不生成架构，不证明代码正确 |
| Codex | 读取仓库、比较接口、生成断言和测试、执行命令、分析日志、提出最小补丁 | 不作为最终裁判 |
| Trae | 可作为代码浏览、现场展示或人工审核界面 | 不必充当第二个“验证模型” |
| Vivado/XSim | 编译、仿真、断言、scoreboard、回归 | 不负责解释产品需求 |
| 板级测试 | 最终确认 PHY、时序、环境和真实链路 | 不能被行为仿真替代 |

Codex 适合放在执行层，是因为官方 OpenAI Docs推荐的模式本身就是“给定可评分规则，运行测试，逐轮修改，保存结果和停止条件”，而不是让模型自我宣布正确。[OpenAI Docs：Iterate on difficult problems](https://learn.chatgpt.com/use-cases/iterate-on-difficult-problems)

我没有对你本机的 Trae 做同题实测，所以不建议先下“Codex 一定强于 Trae”的结论。可以用同一故障快照做小基准：正确定位占 40%，实际跑通测试占 25%，遵守修改边界占 20%，证据可追溯占 15%。

## 五、案例怎么制作

先建立一个脱敏、冻结版本的演示目录：

```text
fpga_ai_demo/
├─ spec/
│  ├─ interface_contract.md
│  └─ acceptance.md
├─ rules/
│  └─ fpga_debug_skill.md
├─ rtl/
│  ├─ before/PCIe.v
│  └─ after/PCIe.v
├─ tb/
├─ assertions/
├─ scripts/
│  ├─ run_demo.tcl
│  └─ run_demo.ps1
└─ evidence/
   ├─ before.log
   ├─ diagnosis.md
   ├─ approved.diff
   ├─ after.log
   └─ result.json
```

固定模板不要写成“请仔细检查代码”，而应写成工程合同：

```text
任务：
定位 Aurora→FDMA 数据已进入 FIFO、但写完成和 IRQ 不出现的原因。

权威输入：
接口契约、RTL 端口方向、已通过的 integration TB、
允许引用的知识库记录和指定仿真日志。

第一阶段权限：
只读 rtl/；只允许修改 tb/ 和 assertions/。

禁止：
不得修改厂商 IP；
不得按端口同名直接推断语义；
不得修改期望值来消除失败；
不得用另一个模型的意见作为通过证据；
未经 APPROVE_FIX 不得修改 rtl/。

通过条件：
指定仿真命令退出码为 0；
双向 512 B scoreboard 通过；
IRQ request/ack 出现；
assertion_error_count=0；
日志包含 RTDS_ROOTPORT_PASS。

停止条件：
接口语义存在冲突，或需要改变架构、延迟、吞吐率时停止，
列出证据并请求工程师决定。

输出：
现象、证据路径、根因假设、最小补丁、回归结果、未覆盖边界。
```

现场精简回归固定调用：

```powershell
& 'D:\Xilinx_2020_2\Vivado\2020.2\bin\vivado.bat' `
  -mode batch -source .\scripts\run_demo.tcl -notrace
```

完整 Root Port 回归已有记录约 36 分 40 秒，不能在 5 分钟现场等待。应另外提取一个 30 秒内完成的 wrapper 接口契约测试，现场跑这个；完整回归用预先保存的日志、JSON 和 SHA-256 证明。

# 30–50 分钟“AI辅助 FPGA 研发体系”讲述方案

## 一、核心判断

领导确实希望看到“设计方案 → RTL → 验证方案 → 验证代码 → 回归验收”的完整闭环，但他并没有要求把每一步都包装成 AI 独立完成。

讲话中更稳定的要求是：

- 不能只做代码润色、文档改写等“大路货”。
- 工作要拆成可快速收敛的小模块。
- 输入、分析、执行、验收、查错必须串起来。
- 最终沉淀成固定模板、Skill、知识库和团队可复用的方法。
- 如果局部案例足够有用、能成体系，也可以单独展示。

因此，主线应正面重构为：

> 固化的不是“任何人都能自动设计任何 IP”，而是“如何把一个未知设计逐步变成有依据、可审查、可运行、可验收的工程结果”。

| 组成 | 固化什么 | 不替代什么 |
|---|---|---|

- 候选方案；

- 最终责任人；
- 对应验证方法；

## 三、知识库在故事中的正确位置

真实时间线应明确讲成：

`6–7 月解决真实工程问题并形成验证证据`
→ `8 月 20 日把资料、参数、问题台账和边界整理成知识库`
→ `后续新任务使用知识库和固定流程`
→ `新结果经审核后再次入库`

不能说知识库促成了早于它完成的历史修复。

- 检索历史根因，减少重复走弯路。
- 把工程规则转成参数检查表、断言和测试点。
- 保留出处和证据，使新人接手时不依赖原作者记忆。

- 无出处或错误参数减少多少；
- 未标记假设减少多少；
- 仿真前发现多少问题；
- 到第一次有效回归需要几轮；
- 人工必须介入哪些决策；
- 最终是否通过相同 EDA 门禁。

## 五、多案例候选池

所有案例统一采用：

`目的 → 输入 → AI动作 → 人的决策 → 工具证据 → 结果 → 可复用资产 → 未覆盖边界`

### 案例 A：FDMA–Aurora 全流程协同开发

作为主案例。

- 人锁定接口、时钟、复位、512 B burst、FIFO、反压和验证边界。
- AI参与已有材料梳理、方案展开、代码修改与审查、测试点分解、SV平台和回归脚本完善。
- 工程师裁决 FIFO结构、复位策略、接口语义、资源与风险取舍。
- Vivado/XSim通过断言、九级观察队列、scoreboard、固定 Seed 和批量回归裁决结果。
- 最后把已验证规则、失败根因和边界整理成问题卡并纳入知识库。

必须说明这是对真实历史过程的归纳，不声称“一条提示词从零生成全部设计”。

### 案例 B：参数都对，层级用错了

组合两个易理解的参数问题：

- 真实 Aurora 64B/66B 用户时钟约 161.13 MHz，156.25 MHz属于另一层级的参考或仿真环境。
- Root Port参考模型默认 x8，而目标 Endpoint 为 Gen3 x2。

体现知识库的主要价值不是生成代码，而是绑定“参数—版本—层级—证据”。

### 案例 C：AI第一次判断错误，完整日志把它纠正

Vivado 2024.2 报 `Cannot find design unit work.-`：

- 初步曾怀疑 top 被错误设置成 `-`。
- 完整 `elaborate.log` 显示真正原因是覆盖率路径中的空格和独立减号。
- 路径修复后仿真运行，又暴露 TX FIFO monitor 的采样竞争。
- 端到端数据已经 PASS，证明不应直接修改 RTL。
- 统一使用 clocking block 快照后，固定 Seed 回归通过。

这个案例最能证明：

> AI的单次分析可能错，但“假设—工具执行—证据反驳—再修正”的体系可以可靠收敛。

### 案例 D：RX FIFO 报错，错误其实在验证环境

- 固定 Seed `564926` 报 almost_full 未出现。
- 根因是测试用例在 `wr_rst_busy` 尚未退出时开始灌入，部分数据没有真正写入 FIFO。
- 没有为了让测试通过而修改 DUT。
- 用例改为等待 busy 连续两拍为低后再注入。
- 原 Seed及历史 Seed复跑通过。

适合说明“AI辅助调试”不等于“看到失败就改RTL”。

### 案例 E：并行回归失败不等于逻辑失败

- 27 个任务中 25 个通过，2 个在读取 `xsim.ini` 阶段失败。
- 相同 testcase、相同 Seed 串行复跑通过。
- 失败被归为仿真环境瞬态问题，而不是 `TEST_FAIL`。
- 回归脚本增加失败分类、固定 Seed重放、失败现场保留和有限重试。

可与错误 Vivado 路径导致全部 `TOOL_FAIL`、旧日志造成假 PASS 一起组成“回归可信度”案例。

### 案例 F：数据已经到了，只是一直盯着错误的内存

使用 [PCIe/XDMA问题台账](E:/PCIE-CPU/docs/RTDS_test_XDMA_RootPort问题发现与处理台账.md:327) 中的 DMA-002：

- 卡侧 AXI 已搬运 512 B，但原观察数组一直不变。
- 一度怀疑 PCIe写入未到或延时不足。
- 实际是把官方 `DATA_STORE` 错当成完整 Host RAM。
- 增加 CQ Host-memory sink后，地址、长度和512 B逐字节scoreboard均通过。

管理层容易理解为：“货已经送到，但检查人员一直在看错误仓库。”

### 案例 G：历史端口名字误导了集成连接

保留 AUR-002 作为技术深入案例：

- 端口名叫 `valid/ready`，实际历史语义相反。
- 同名直连导致写突发和中断无法完成。
- 根据已通过的 integration harness 和模块内部赋值确认真实语义。
- 只修 wrapper映射，不修改已经验证的子模块。
- 适合技术答疑，不作为唯一主案例。

### 案例 H：规范本身也可以工程化

用现有代码规范包说明：

- 用户规则不是散落在提示词里，而是有稳定编号和单一事实源。
- 规范正文、评审表和检查脚本同步更新。
- 冲突条目有明确裁决，未批准单元保持 pending。
- 证明“可继承体系”可以管理规范和审查，但不能据此宣称已经自动完成某个芯片设计。

## 六、新留出案例：通用跨时钟流桥

用于知识库建成后的真实复用试验，不能让知识库包含该模块现成答案。

### 冻结输入

- 64 bit数据及包尾标志；
- 独立输入、输出时钟域；
- ready/valid流控；
- XPM异步FIFO，默认深度512；
- 输出侧允许反压；
- 要求无丢失、无重复、无乱序；
- 复位中止当前包并清空，双方 busy退出后才恢复传输。

其中“复位中途的数据如何处理”必须由工程师确认，Agent不得自行猜测。

### 全流程

1. 规格模板生成待澄清项和需求编号。
2. 知识库检索CDC、FIFO、复位、ready/valid和时钟约束。
3. Agent提出架构和参数候选。
4. 人批准复位策略、FIFO深度和吞吐假设。
5. Agent生成或修改RTL、SVA、scoreboard和回归脚本。
6. Vivado完成编译、展开和XSim运行。
7. 执行无反压、随机反压、时钟比例变化、满/空边界、中途复位和固定Seed重放。
8. 只有通过门禁的结论才能回灌知识库。

### 对照方式

使用同一个模型和冻结规格，分别执行：

- 只有普通提示词；
- 固定任务包+规则Skill+知识库。

比较来源错误、隐藏假设、人工干预次数、迭代轮数和最终回归结果。该试验只证明体系的增量作用，不声称消除了模型能力和使用者能力差异。

## 七、事实核验与验收

- 每个历史案例必须能回到实际代码、命令、日志或问题台账。
- “历史已完成”“知识库后整理”“未来留出试验”使用不同状态标识。
- 不把两个模型相互认可当成正确性证据。
- 不编造提效百分比；没有人工基线时只报告运行次数、迭代轮数和实际耗时。
- 不把LocalLink BFM通过说成Aurora GT、真实串行链路或上板通过。
- 不把单用例覆盖率报告说成七库官方merge结果。
- 每个案例必须至少指出一项AI不能自行决定的内容和一项EDA机器证据。
- 30分钟和50分钟讲述分别试讲，确保删减短案例不会破坏主线。

## 八、最终选取建议

- 如果最终只选一个：选“FDMA–Aurora人工+AI全流程协同”，把参数审查、RX reset-busy和回归脚本作为其中三个节点。
- 如果最终选两个：再加入“通用跨时钟流桥留出试验”，用它证明体系能够迁移，而不是只会复述已经入库的旧项目。

### 案例 A：FDMA–Aurora 全流程协同开发

作为主案例。

### 案例 B：参数都对，层级用错了

组合两个易理解的参数问题：

- 真实 Aurora 64B/66B 用户时钟约 161.13 MHz，156.25 MHz属于另一层级的参考或仿真环境。

体现知识库的主要价值不是生成代码，而是绑定“参数—版本—层级—证据”。

### 案例 C：AI第一次判断错误，完整日志把它纠正

Vivado 2024.2 报 `Cannot find design unit work.-`：

- 初步曾怀疑 top 被错误设置成 `-`。
- 完整 `elaborate.log` 显示真正原因是覆盖率路径中的空格和独立减号。
- 路径修复后仿真运行，又暴露 TX FIFO monitor 的采样竞争。
- 端到端数据已经 PASS，证明不应直接修改 RTL。
- 统一使用 clocking block 快照后，固定 Seed 回归通过。

这个案例最能证明：

> AI的单次分析可能错，但“假设—工具执行—证据反驳—再修正”的体系可以可靠收敛。

### 案例 D：RX FIFO 报错，错误其实在验证环境

- 固定 Seed `564926` 报 almost_full 未出现。
- 根因是测试用例在 `wr_rst_busy` 尚未退出时开始灌入，部分数据没有真正写入 FIFO。
- 没有为了让测试通过而修改 DUT。
- 用例改为等待 busy 连续两拍为低后再注入。
- 原 Seed及历史 Seed复跑通过。

适合说明“AI辅助调试”不等于“看到失败就改RTL”。

### 案例 E：并行回归失败不等于逻辑失败

- 27 个任务中 25 个通过，2 个在读取 `xsim.ini` 阶段失败。
- 相同 testcase、相同 Seed 串行复跑通过。
- 失败被归为仿真环境瞬态问题，而不是 `TEST_FAIL`。
- 回归脚本增加失败分类、固定 Seed重放、失败现场保留和有限重试。

可与错误 Vivado 路径导致全部 `TOOL_FAIL`、旧日志造成假 PASS 一起组成“回归可信度”案例。

### 案例 F：数据已经到了，只是一直盯着错误的内存

使用 [PCIe/XDMA问题台账](E:/PCIE-CPU/docs/RTDS_test_XDMA_RootPort问题发现与处理台账.md:327) 中的 DMA-002：

- 卡侧 AXI 已搬运 512 B，但原观察数组一直不变。

### 案例 G：历史端口名字误导了集成连接

保留 AUR-002 作为技术深入案例：

## 一、先把最容易争论的问题说清

你的判断基本正确：

- 知识库不能提高模型本身的推理和设计上限。
- 固定模板不能替代微架构设计能力。
- 两个模型相互认可不能证明 RTL 正确。
- AI参与全流程不等于AI拥有完整签核权。
- 不同项目的具体实现必然依赖相应的设计能力。

但这不等于领导要求的“可继承体系”无法成立。需要把“不依赖”定义在正确层级：

> 不依赖个人，是不依赖某一个人的隐性记忆、私人工作习惯和临场发挥；不是不再需要专业能力。

> 不依赖特殊项目内容，是体系内核不绑定某个项目；不是每个新项目都不需要接口、参数和场景适配。

因此，可以把体系表达成：

`可继承体系 = 固定骨架 + 领域规则 + 项目适配包 + 人/Agent执行 + 独立验收门禁`

其中：

| 层级 | 可以继承 | 仍需专业判断 |
|---|---|---|
| 固定骨架 | 任务拆分、输出格式、评审步骤、失败分类、验收流程 | 不涉及具体架构 |
| 领域规则 | CDC、FIFO、ready/valid、复位、4 KB边界、代码规范 | 规则冲突和适用范围 |
| 项目适配包 | 接口、时钟、吞吐、资源、IP版本、禁止项 | 每个项目必须重新填写 |
| 执行层 | 检索、方案展开、代码修改、测试生成、日志分析 | 人或足够强的Agent完成 |
| 验收层 | 编译、展开、仿真、断言、scoreboard、覆盖率 | 工程师解释结果边界 |

最适合面对领导的说法是：

> 体系不是取消专家，而是让专家能力有接口、关键判断有记录、执行过程可交接、最终结果有统一门槛。

### 0–5分钟：开场

### 5–12分钟：什么才算可继承

建议给出三个验收问题：

1. 原作者不在，别人能否找到需求、设计依据和历史问题？
2. 换一个项目，能否通过同一任务接口启动，而不用重新发明流程？
3. 换一个执行者或模型，是否仍由同一套EDA门禁验收？

只要这三点成立，就已经形成组织能力。

可以用Vivado作类比：

> Vivado的综合、实现和时序分析流程是固定的，但它不会自动替我们决定每个项目的时钟约束和微架构。AI研发体系也是同样的关系：轨道和验收规则固定，具体项目跑什么内容仍然需要设计。

建议把每个项目的固定工作接口定义为：

`任务包 → 待决策项 → 设计决策 → RTL → 测试点映射 → TB/断言 → 回归报告 → 问题卡 → 知识库`

每一步都有固定产物：

- 任务包：需求编号、来源、已知条件、待确认项、禁止假设、PASS标准。
- 设计决策：候选方案、取舍理由、责任人、风险和验证方法。
- RTL变更：对应哪个需求，修改了什么，哪些部分禁止改动。
- 验证映射：每项需求由哪个用例、断言和scoreboard检查。
- 回归报告：工具版本、Seed、编译/展开/仿真状态、错误类型和产物。
- 问题卡：现象、错误判断、决定性证据、根因、修复、复跑和适用边界。

> 知识库不能把低能力模型变成资深FPGA设计师，也不能直接证明生成的代码正确。它解决的是上下文治理，而不是模型智力。

### 2. 任务输入

工程师给出的关键输入包括：

- FDMA与LocalLink之间双向转换；
- 64 bit数据宽度；

这里体现的不是AI替代设计者，而是：

### 5. 用一个真实失败说明怎么闭环

固定Seed `564926` 报：

`RX FIFO almost_full was not observed`

如果只看结果，最容易怀疑FIFO深度或DUT写入逻辑。

实际证据是：

- FIFO深度为2048；
- 该Seed只生成2054个注入word；
- 用例开始注入时，写侧`wr_rst_busy`仍为1；
- 前几拍上游看似在发送，但FIFO没有真正写入；
- 额外6个word的余量刚好被复位窗口吃掉。

工程师在这里作了关键裁决：

> 不通过盲目增加注入量掩盖问题，也不修改RTL；测试环境必须先等FIFO真实可写。

修复后：

- 等待`wr_rst_busy`连续两个`user_clk`周期为0；
- 增加1000周期timeout；
- 日志显示busy在28个user clock后清除；
- 第一笔数据`word=0 wr_en=1`；
- Seed `564926`通过；
- 历史Seed `641547`、`926784`通过；
- 专项回归列表通过。

证据见[固定Seed调试记录](E:/codex_history_md/gpt_doc/2026-07-08_09-41_检查%20RX%20FIFO%20almost_full.md:304)。

这个案例的总结句是：

> AI辅助调试的价值，不是看到失败就更快地修改RTL，而是通过分层证据先确定究竟应该修改哪一层。

## 五、可独立选择的七个短案例

### 案例B：参数没错，层级错了

**故事钩子：** 两个人各拿一个“正确数字”，最后仍可能接错系统。

- 现象：Aurora用户时钟出现161.13 MHz和156.25 MHz两种说法。
- AI动作：检索综合日志、Aurora配置和官方资料，区分用户数据侧、GT参考和仿真模型。
- 人的决定：确定每个参数绑定的IP实例、版本和时钟层级。
- 工具证据：综合日志中ILA用户时钟周期约6.206 ns。
- 结果：不再通过改Debug Hub时钟去解决`channel_up=0`。
- 可复用资产：参数必须记录“数值+单位+版本+层级+来源”。
- 边界：这只解决参数语境，不证明链路一定能起来。

适合说明知识库的真实价值。

### 案例C：AI的第一次诊断是错的

**故事钩子：** 错误信息是`work.-`，最初以为top被设成了减号。

- 现象：Vivado 2024.2报告`Cannot find design unit work.-`。
- 第一判断：怀疑仿真top错误。
- 决定性证据：完整`elaborate.log`显示top正确，独立减号来自含空格的覆盖率路径。
- 修复：把覆盖率数据库放到不含空格和独立减号的短路径。
- 后续：仿真运行后又暴露TX FIFO监视器首字错位。
- 新证据：端到端LL和FDMA数据已经PASS，错误监视值恰好等于下一word。
- 根因：XPM FIFO为FWFT、`FIFO_READ_LATENCY=0`，两个monitor采样相位不一致。
- 修复：握手、数据和计数统一从同一个clocking block快照采样，不修改RTL。
- 结果：固定Seed及后续回归通过。

证据见[`work.-`与采样竞争记录](E:/gpt_doc/Vivado_2024.2_第8章_batch覆盖率_work_minus与采样问题修复.md:238)。

核心结论：

> 可靠体系不假设AI永远正确，而是确保每个判断都能被工具证据否定。

### 案例D：测试失败，但DUT没有错

即前述`wr_rst_busy`固定Seed案例。

它最适合作为主案例之外的独立展示，因为非专业听众也容易理解：

> 实验员在设备还没准备好时就开始计数，最后误判设备容量不足。

这是当前最推荐的第二案例。

### 案例E：并行回归FAIL不等于逻辑FAIL

- 27个并发任务中25个通过、2个失败。
- 两个失败均发生在早期读取`xsim.ini`阶段。
- 没有进入testcase，没有compare mismatch，也没有断言错误。
- 相同testcase和Seed串行复跑分别PASS。
- 原失败归类为Vivado/XSim并发文件访问瞬态，不是RTL故障。
- 回归脚本随后增加阶段分类、固定Seed重放、失败现场保留和基础设施故障串行重试。

详细证据见[Seed重放记录](E:/gpt_doc/failed_seed_replay_context_20260703.md:67)。

这个案例还能加入两个小插曲：

- 完整仿真已经`TEST_PASS`，但`close_sim`后写stdout失败，被旧launcher误记为FAIL。
- 另一台机器Vivado路径写错，所有任务0.4秒左右全部`TOOL_FAIL`，连Vivado banner都没有出现。

核心结论：

> 自动化回归必须区分COMPILE、ELAB、SIM_SETUP、COMPARE、ASSERT、TIMEOUT、TOOL和ARTIFACT；一个笼统的红色FAIL没有工程意义。

### 案例F：数据到了，却一直看错仓库

使用PCIe/XDMA问题台账中的DMA-002：

- 卡侧AXI已经读出512 B；
- 原观察数组的sentinel一直不变；
- 一度怀疑PCIe Memory Write没有到达；
- 实际上官方`DATA_STORE`只是Host向Endpoint发数据时的数据源，不是完整双向Host RAM；
- 增加CQ Host-memory sink后，地址、长度和512 B逐字节scoreboard全部通过。

证据见[问题台账](E:/PCIE-CPU/docs/RTDS_test_XDMA_RootPort问题发现与处理台账.md:327)。

适合管理层的类比：

> 货已经送到，但我们一直在检查错误的仓库。

边界：该sink是仿真兼容模型，不等同于真实CPU、DDR、操作系统和IOMMU。

### 案例G：端口名字误导了连接

AUR-002：

- 历史模块端口叫`fdma_wvalid/fdma_wready`，但实际方向语义与名字相反；
- wrapper按同名直连后，LocalLink数据可以进入FIFO，但写突发和中断无法完成；
- 已通过的integration harness使用交叉映射；
- 最终只修改wrapper，引入`source_valid`和`accept`语义网；
- 已验证的FDMA、adapter和`CONV_DMA`本体不改；
- 后续Aurora→CPU 512 B、IRQ和C2H均通过。

证据见[问题台账](E:/PCIE-CPU/docs/RTDS_test_XDMA_RootPort问题发现与处理台账.md:343)。

这个案例技术价值很高，但需要解释历史命名，不建议作为面向管理层的唯一案例。

### 案例H：把代码规范本身做成可执行资产

现有规范包已经采用：

- 稳定规则编号；
- JSON单一事实源；
- 规范正文、用户规则页和评审表同步生成；
- 规则冲突有正式裁决；
- 未批准的标准单元保持`pending_user_input`；
- 校验脚本检查结构、引用和禁止写法。

入口见[代码规范包](E:/centOS/代码规则建立/代码规范输出/README.md)。

它可以证明：

> Skill不是一段很长的提示词，而是规则源、模板、检查工具和验收记录的组合。

但它只能证明规范管理链路已经建立，不能说它已经自动完成某个生产RTL项目的签核。

## 六、真正检验知识库的新留出案例

原计划中的“通用跨时钟流桥”需要修正：当前知识库已经收录了内部`axis_async_fifo.sv`，如果直接让Agent检索全库，会发生答案泄漏。

因此建议改成：

# 包级原子跨时钟流桥留出试验

### 冻结任务

- 64 bit数据；
- 独立输入、输出时钟；
- ready/valid；
- 包尾标志；
- XPM异步FIFO，深度512；
- 包长1–256 beat；
- 输出允许随机反压；
- 任一时钟域可在包中途复位；
- 要求接收端不能得到被复位截断的旧包；
- 无丢失、无重复、无乱序；
- 复位恢复必须等待FIFO双方busy退出。

这里故意包含一个真正的架构问题：

> 如果采用cut-through，前半包已经送给接收端以后发生复位，系统无法把已经送出的数据收回来。要满足“不能输出截断包”，就必须采用整包缓存后提交，或者修改系统契约。

Agent必须先发现这个矛盾，不能直接写RTL。工程师随后统一选择“整包缓存后提交”或批准新的接口契约，再让三组实验得到相同裁决。

### 知识库隔离

实验知识库只允许：

- 官方FIFO/CDC/AXI-Stream资料；
- 通用代码规范；
- 通用证据等级和回归规则。

明确排除：

- `axis_async_fifo.sv`；
- FDMA–Aurora桥RTL和TB；
- NVMe/AXI现成桥实现；
- 包含目标实现答案的历史问题台账；
- 前两组实验的会话内容。

### 建议做三组，而不是两组

| 组别 | 输入 |
|---|---|
| A | 普通自然语言需求 |
| B | 冻结任务包+固定Skill，不提供知识库 |
| C | 冻结任务包+固定Skill+过滤后的知识库 |

这样才能分别观察：

- 模板和Skill带来的影响；
- 在同样Skill基础上，知识库额外带来的影响。

三组必须使用：

- 同一个模型和推理等级；
- 独立新会话；
- 独立工作目录；
- 相同Vivado版本；
- 相同人类决策答复；
- 相同时间和迭代上限；
- Agent不可见的同一组隐藏回归。

### 验收用例

至少包括：

- 无反压；
- 随机输出反压；
- 输入快于输出；
- 输出快于输入；
- FIFO接近满；
- 1 beat和256 beat包；
- 包尾附近反压；
- 空闲复位；
- 包中途复位；
- 复位释放时valid仍为1；
- 固定Seed重放；
- 不同时钟相位及频率比。

### 比较指标

- 编码前主动发现多少待澄清项；
- 产生多少无来源参数；
- 产生多少隐藏假设；
- 首次编译通过需要几轮；
- 首次进入有效仿真需要几轮；
- 首次通过基础测试需要几轮；
- 隐藏回归结果；
- 人工决策次数和实际投入分钟数；
- Agent是否试图通过修改测试掩盖DUT问题；
- 最终报告是否准确标注未覆盖边界。

这个留出案例当前状态必须写成“待执行对照实验”，不能在汇报中提前说它已经证明了复用效果。

## 八、领导可能追问的答法

**“既然还需要专家，这套体系有什么价值？”**

> 它把专家投入从重复执行转移到需求、架构、异常和签核节点；同时让普通执行过程有统一输入、过程记录和工具验收。它降低的是对某个具体人的依赖，不是取消专业能力。

**“这算不算AI全流程？”**

> 算AI参与全流程，但不等于AI独占全流程权责。闭环完整是指环节、反馈和证据完整，不是所有环节都由同一个主体完成。

**“知识库有没有提高代码生成能力？”**

> 它不提高模型本身的推理上限，主要降低版本混淆、参数串用、遗漏历史限制和无来源结论。增益要通过同模型、同规格、同门禁的留出实验测量。

**“为什么不用两个模型相互校验？”**

> 模型可以互相提出问题，但两个模型达成一致仍可能共同出错。最终验收必须来自规格追踪、编译、展开、仿真、断言、scoreboard和回归结果。

**“国产模型能不能放进去？”**

> 当前没有工程证据证明某个较弱模型可以承担复杂架构和跨文件调试，因此不在主案例中作这种承诺。后续可以让不同模型执行同一冻结任务，由同一EDA门禁分级，而不是凭主观评价选择。

**“为什么历史案例能证明知识库？”**

> 历史案例不能证明知识库带来了原始修复。它只证明哪些经验值得沉淀。知识库的增量价值由建库后的隔离留出实验证明。

## 九、必须避免的表述

不要说：

- “AI从零自主完成了整个IP。”
- “知识库让模型具备了资深设计能力。”
- “两个模型相互校验，所以代码正确。”
- “知识库帮助解决了早于建库日期的历史问题。”
- “PCIe到Aurora全链路和上板全部通过。”
- “七份覆盖率数据库已由XCRG正式merge。”
- “TRAE完成了这些代码。”——目前可追溯历史主要是Codex，除非后续补出TRAE实际记录。
- “效率提升了百分之多少。”——目前缺少同任务人工基线。

推荐结尾：

> 我们不是要把芯片研发变成不需要能力的流水线，也不是要证明某个模型能够包办设计。真正值得固化的是：任务如何进入，哪些问题必须先澄清，方案如何留下依据，代码如何与需求关联，失败如何分类，结果由什么证据验收，以及经验如何进入下一次项目。
>
