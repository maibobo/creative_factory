# Aurora

先确定8B/10B或64B/66B、lane数、线路速率、用户接口宽度、framing/streaming、CRC和流控配置。原生IP接口与项目包装接口分别说明，不能把某个LocalLink包装器的信号定义套到全部配置。

## 用户接口

以本包总线桥的64 bit包装接口为例：TX包含data、valid、ready、SOF、EOF、REM；RX包含data、valid、SOF、EOF、REM，采用不可反压入口。实际IP的流控能力以所选模式确认。

发送仅在valid和ready同时有效时消费一拍；停顿期间数据、首尾标记和REM保持。REM只在尾拍表示有效字节数减一，完整64 bit尾拍为7，32 bit尾拍为3。中间拍按全宽处理，位宽转换同时处理字节顺序和帧界限。

接收没有业务ready时，后级FIFO承担暂停吸收，需定义溢出时是丢字、丢整帧还是报错。线路上的流控功能、用户接口ready与本地FIFO门控不是同一件事。

## 时钟和复位

| 项目 | 核对内容 |
|---|---|
| GT参考时钟 | 时钟频率、收发器位置及引脚约束 |
| 内部并行时钟 | 收发器数据宽度、编码与共享逻辑 |
| 用户接口时钟 | Core生成结构、接口宽度及实际时序约束 |
| 初始化时钟 | 复位控制对时钟稳定性的要求 |
| BFM时钟 | 用户边界模型的配置，不能据此推定真实Core |

64B/66B编码、lane和内部并行宽度共同影响时钟，不能仅用线路速率除以用户总线宽度确定user_clk。示例BFM的156.25 MHz表示接口模型配置。物理IP时钟从其配置、生成结构和产品指南确认。

协议reset与GT/PMA初始化分别设计。用户逻辑采用对应域复位及Core状态，启动前检查channel_up等实际条件。链路下降时停止新帧，已接受数据和未完成帧的处理由上层契约决定。

## 错误与检查

lane_up、channel_up、hard/soft error、CRC结果有不同范围。CRC错误要结合结果有效信号，不能只将极性翻转当作正确判断。错误统计的清除和新事件同拍优先级在设计中明确。

| 场景 | 观察 |
|---|---|
| 启动与掉线 | 就绪前业务门控、恢复后第一帧、旧帧隔离 |
| TX反压 | 首中尾停顿，valid和所有有效字段保持 |
| RX拥塞 | 入队/拒绝/输出字数，错误报告与下一帧对齐 |
| 尾字节 | REM、EOF、字节顺序及端到端有效载荷 |
| 复位 | 协议重启与GT初始化的作用范围 |

用户接口BFM检查桥接与业务层；Core/GT模型检查建链和串行层，板级还检查数据、时序和信号完整性。分层报告，不以channel_up替代数据正确。
