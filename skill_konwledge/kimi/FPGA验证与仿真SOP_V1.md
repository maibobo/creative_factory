## 1. 目的

规范 FPGA 功能验证与仿真工作，做到：

- 测试点、用例、验证方案、验证代码、仿真结果全程**可反标、可追溯**；
- 验证结论**有据可依**：PASS 以实际检查通过为准，不以"跑完""有 PASS 字样"代替；
- **人机分工明确**：AI 助手承担分解、生成、执行辅助，人工在关键节点审核把关；
- SOP **轻量化、可裁剪、可执行**，按验证环境规模裁剪必做与可选步骤，与知识库、Skills 配套使用并持续迭代。

## 2. 角色与人机分工

| 角色 | 职责 |
|---|---|
| 验证负责人（人） | 确认输入资料齐备；主持各人工审核点；对验证结论签字负责 |
| 设计人员（人） | 提供并澄清功能规格；参与失败根因判定（区分需求/判据、DUT、TB、环境） |
| AI 助手（WorkBuddy + FPGA研发知识库_V2） | 辅助测试点分解、用例与方案起草、验证代码生成、回归脚本编写、结果整理与报告起草 |
| 人工审核点 | A：测试点/用例表确认；B：验证方案评审；C：验证环境与代表用例走查；D：回归结果与仿真报告确认 |

**分工原则**：AI 产出均为"待确认稿"，未经对应人工审核点通过不得进入下一阶段；凡涉及改变已确认功能或验收判据的，一律退回对应阶段由人确认。

## 5. 阶段 S1：验证策划（测试点、用例与验证方案）

### 5.1 执行步骤

1. **测试点分解**：逐条读取功能规格，拆出可观察、可判定的行为。主要按**基本功能**分类，再按实际场景补充接口交互、总线、跨时钟和异常。提取思路：

   | 规格中的信息 | 提取的测试思路 |
   |---|---|
   | 输入与输出 | 正常关系、禁止的输出、何时有效、数据/字节数一致性 |
   | 条件与状态 | 进入/离开状态、条件不同次序、条件同拍、等待及恢复 |
   | 数值范围 | 最小、最大、边界前后；非法值仅在规格定义处理方式时测其反应 |
   | 时序与容量 | 首尾拍、背靠背、反压、满空、在途事务与时限 |
   | 异常处理 | 超时、错误响应、复位中断、丢弃与重试、异常后的下一笔正常事务 |

   知识库中的场景是提示，不代替当前规格；不强行要求实现规格外的能力（如配置不支持乱序则不测乱序），但需在表中明确不覆盖的项。

   分解示例：DDR 的"100 ms 事件提出封块"应分解为普通双字、奇数尾字、延迟成功响应、写错误不累计、空周期、队头保护和确认释放等多个测试点，避免只做一个"写读成功"用例；总线桥反压应分别放在首、中、尾拍，检查完整字段保持。

2. **编号与反标**：测试点编号 = 项目/IP前缀 + 功能类别 + 类别内序号（如 DDR.001.001）；测试点反标规格编号与描述，关联用例名称；用例反标测试点编号与内容。一个用例覆盖多个测试点时分别反标。

3. **用例设计**：先确定每项检查，再选择定向与随机组合——确定位置的故障配合随机数据或停顿，能覆盖相邻周期而不依赖偶然触发。"准备与输入"只写本例核心变量与激励思路（约 3–30 行），交代关键输入的中文含义、来自哪个环境组件、为何这样设置、对应哪个测试点；预期结果必须可观察（数据保持、握手次数、响应码、错误标志、恢复后事务内容），不写"运行正常"。**表中行顺序即回归执行顺序**。

4. **验证方案编写**：按模板六章展开——验证目的；验证方法及回归安排/完成条件；环境组件；架构与数据流；组件功能设计（激励、driver/BFM、monitor、RM、checker/scoreboard、覆盖分别说明）；代表用例实例（解释一笔事务从刺激到比较经过的组件和数据，而非只贴框图）。UT 聚焦模块行为（可用 BFM 模拟邻接接口），IT 验证真实模块连接、配置和跨模块数据流；采用行为模型时须写明模型覆盖到哪个接口、哪些初始化/PHY/软件行为未模拟。

### 5.2 工具/Skills 调用

| 环节 | 人机分工 |
|---|---|
| 测试点与用例起草 | AI 助手基于知识库验证策划类能力起草 Excel 测试表，人逐条核对补充 |
| 验证方案起草 | AI 助手按模板起草 Word 方案，人审核方法与完成条件 |
| 场景补充 | AI 助手按功能上下文从知识库检索 AXI/CDC/FIFO/跨IP 等主题场景供人选用 |

### 5.3 人工审核点

- **审核点 A（测试点/用例表确认）**：验证负责人 + 设计人员确认测试点分类完整、编号反标正确、预期结果可判定、不覆盖项已声明。
- **审核点 B（验证方案评审）**：确认 UT/IT 划分、环境组件职责、完成条件与回归安排、模型边界声明。

### 5.4 输出成果

- 《设计规格_测试点_测试用例表》（Excel，反标完整）
- 《验证方案》（Word）

### 5.5 验收标准

- 每条已确认功能规格均有测试点覆盖或有明确的不覆盖声明；
- 测试点↔规格、用例↔测试点双向反标完整；
- 用例预期结果全部可观察、可判定；
- 审核点 A、B 均通过并有记录。

## 6. 阶段 S2：验证环境搭建与验证代码编写

### 6.1 执行步骤

1. **环境选型**：按功能规模和既有环境选择——简单模块用基本 TB，小型用轻量 SV，复杂或大型用完整 SV，已有 UVM 或明确需求时用轻量 UVM。不按文件数量判断质量，只保留有实际职责的组件。
2. **组件搭建**（完整 SV 可参考的组件职责与常见问题）：

   | 组件 | 负责内容 | 常见红线 |
   |---|---|---|
   | tb_top/interface | 连接 DUT、时钟复位、采样/驱动边界 | 同一信号多处驱动、驱动采样竞态 |
   | test/激励 | 当前测试点的事务、约束、错误注入 | 不检查 randomize 结果、激励未真正到达 |
   | driver/BFM | 将事务落实到协议、处理握手复位 | 用待发送对象冒充已完成事务 |
   | monitor | 从实际接口采样重建事务 | 看错接口、漏尾拍、发布后改对象 |
   | RM | 按功能语义计算预期 | 复制 DUT 控制逻辑导致共同错误 |
   | checker/scoreboard | 协议/端到端比较、顺序与残留检查 | 只数数量不比数据、未知响应不报错 |
   | coverage | 记录真实发生的场景 | 从刺激意图采样、前件未发生声称覆盖 |
   | env/config | 组件连接与配置 | 默认配置与本次 DUT 参数不一致 |

3. **反标与映射**：验证代码注释反标测试点；建立用例名称到实际仿真入口的一一对应（或明确的参数化映射）。
4. **采样与所有权约定**：同步接口使用明确的 driver/monitor 采样时序（clocking block 成员读写，不混用 pin 读值）；monitor 发布的 transaction 是观察快照，消费者需要缓存或修改时自行复制；单一驱动者原则同样适用于基本 TB；异步复位单独说明采样和线程恢复策略。
5. **检查与结束条件**：端到端比较实际有效字节、地址、长度、ID 和错误语义；测试正常结束须满足——刺激完成、在途事务归零、比较队列清空、checker 无失败；**watchdog 超时是异常退出，不是正常完成条件**；SVA 明确时钟、复位及有界时限，关键蕴含配合触发覆盖。复位中断事务时，DUT、monitor、RM、scoreboard 按同一已确认语义清理，**不能只清空检查队列而使 DUT 输出的旧数据失去比较对象**。
6. **编译冒烟**：先编译（查语言与依赖）、再展开（查顶层、参数、绑定、IP 模型）、最后运行用例。找不到工具/许可证/库/模型属环境或构建异常，**不记作 DUT 功能失败**；已 include 的 class 文件不得重复编译。

### 6.2 工具/Skills 调用

| 环节 | 人机分工 |
|---|---|
| 验证代码生成 | AI 助手基于知识库仿真回归类能力生成环境与用例骨架，人走查关键组件 |
| 编译冒烟 | AI 助手执行编译/展开并解读日志，人判定异常类别 |

### 6.3 人工审核点

- **审核点 C（环境与代表用例走查）**：抽查 RM 未复制 DUT 逻辑、checker 确实比数据、覆盖采样自真实发生场景、用例入口映射正确。

### 6.4 输出成果

- 验证环境代码（含反标注释）、用例入口清单、编译/展开通过记录

### 6.5 验收标准

- 编译与展开无错误；代表用例可运行到正常结束条件；
- 用例名称与仿真入口一一对应；审核点 C 通过。

## 7. 阶段 S3：仿真执行与每日回归

### 7.1 执行步骤

1. **固定现场**：固定源文件、顶层、宏/参数、工具与 IP 库版本、filelist、配置和用例入口后再执行。
2. **按序执行**：按用例表行顺序运行，不分优先级；每轮使用独立结果目录，保存输入配置、命令、Seed、日志和结果。
3. **失败处置**：功能不匹配或用例超时——保留现场（输入、Seed、日志）后**继续**后续用例；编译或环境失效——**停止**并标记后续用例未运行。
4. **每日回归**：沿用项目既有回归脚本入口，由当前项目填写工具命令和判据；实现或时序修改影响逻辑时，补做相应回归。
5. **PASS 判定**：需同时满足——正常结束、实际通过标志、无失败标志、满足验证方案的检查条件。**进程返回 0、日志含 PASS 字样、链路就绪等单项均不能替代完整判定**；脚本能识别文本不代表测试点充分覆盖；未激励、未检查或因环境中断的项保留"未完成"状态。结果可复现以"相同工具和配置下同 Seed 重放"为准，不承诺跨工具位级一致。

### 7.2 工具/Skills 调用

| 环节 | 人机分工 |
|---|---|
| 回归脚本编写与执行 | AI 助手编写/维护回归入口并执行，汇总每轮结果 |
| 结果初筛 | AI 助手分类汇总失败用例与日志，人确认分类正确性 |

### 7.3 输出成果

- 每轮回归的结果目录（配置、命令、Seed、日志、结果）、回归汇总记录

### 7.4 验收标准

- 结果目录完整可复现（同 Seed 同版本可重跑）；
- 每用例状态明确：PASS / 功能失败 / 超时 / 未运行（原因标注）。

## 8. 阶段 S4：失败定位、修复与复测

### 8.1 执行步骤

1. **现象分类定位**：

   | 现象 | 优先核对 |
   |---|---|
   | 无法编译/展开 | 完整日志、文件表、库映射、参数转义、路径空格、实际顶层 |
   | 没有事务或覆盖不增长 | 前置条件、复位 busy、链路/校准、刺激是否真正握手 |
   | 数据错一拍 | FIFO 读模式、接口采样边沿、clocking block 快照、尾拍有效范围 |
   | DMA 完成但数据不匹配 | 地址/字节有效、真实接收路径、Host 模型职责、monitor 位置 |
   | 有 PASS 字样仍有错误 | 总错误计数、checker、残留队列、超时、日志是否属于本轮 |
   | 时好时坏 | 同 Seed/同版本复现，分辨调度竞态、随机配置与真实边界错误 |

2. **判定修复对象**：先区分问题属于需求/判据、DUT、TB 还是环境，再决定修复对象与责任方。
3. **复测与回归**：固定 Seed 复现后进行必要扩展验证；修复后复测并执行必要回归；**不通过无限重跑直到成功来覆盖原失败**；需改变已确认功能或判据时退回 S1 人工确认。

### 8.2 工具/Skills 调用

| 环节 | 人机分工 |
|---|---|
| 日志与波形初析 | AI 助手按现象分类表给出定位建议，人判定根因归属 |
| 复测执行 | AI 助手执行复测与回归，人确认结果 |

### 8.3 输出成果

- 失败定位记录（现象、根因分类、修复对象、复测结果）

### 8.4 验收标准

- 每个失败用例有明确根因分类与处置结论；
- 修复项均有复测通过记录及必要回归记录；无"以重跑掩盖失败"情形。

## 9. 阶段 S5：结果回填与仿真报告

### 9.1 执行步骤

1. **回填测试表**：按真实执行结果回填；未执行项明确标注"待执行"及原因。
2. **编写仿真报告**（按模板四章组织）：测试版本；仿真与回归结果概览；分功能/用例的现象、必要证据与结论；验证范围、未覆盖内容与遗留问题。报告应描述数据接受、响应、检查和完成等**具体事件**，使结果能被另一位工程师独立复核。
3. **模型边界声明**：行为级内存、用户接口 BFM、真实 IP 模型和板级软件分别属于不同验证层级；**验收不把行为模型通过扩展为真实 IP 或板级通过**。
4. **归档与脱敏**：交付件需上传或发布时，按知识库《上传与发布安全检查》完成脱敏，并按需选择加密发布。

### 9.2 工具/Skills 调用

| 环节 | 人机分工 |
|---|---|
| 报告起草 | AI 助手按模板起草报告并汇总数据，人审核结论与遗留问题处置 |
| 回填与归档 | AI 助手回填测试表、整理归档目录，人抽检 |

### 9.3 人工审核点

- **审核点 D（报告确认）**：验证负责人确认结论与证据一致、未覆盖项与遗留问题处置明确、模型边界声明完整。

### 9.4 输出成果

- 《仿真报告》（Word）、回填完成的测试表、归档的回归结果目录

### 9.5 验收标准（本 SOP 总出口）

- 计划内功能用例全部执行且有明确结论，未完成项有原因与处置计划；
- 报告结论与回归记录、测试表三者一致；
- 审核点 D 通过，交付物齐套归档。

## 11. 质量红线（全阶段适用）

1. 预期结果不可判定（"运行正常"）的用例不得进入执行；
2. watchdog 超时、环境中断不得记为 PASS；
3. 覆盖率数字本身不等于功能正确，完成条件以计划内功能结果 + 有效检查 + 遗留问题处置为准；
4. 行为模型/仿真通过不得扩展为真实 IP 或板级通过；
5. 不得以无限重跑掩盖失败；
6. 改变已确认功能或判据必须退回人工确认。
