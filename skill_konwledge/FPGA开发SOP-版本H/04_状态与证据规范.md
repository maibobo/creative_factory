# 状态与证据规范

## 1. 每个阶段都要记录

```text
stage_id
project_id
design_baseline
rtl_baseline
tool_name
tool_version
command_or_operation
input_manifest
output_artifacts
status
owner
timestamp
open_issues
```

## 2. 问题记录格式

```text
Issue ID:
Stage:
Severity: CRITICAL | MAJOR | MINOR | SUGGESTION
Category: design | rtl | testbench | environment | timeout | tool_defect | timing
Evidence:
Expected:
Observed:
Impact:
Proposed action:
Owner:
Status: OPEN | FIXED | VERIFIED | ACCEPTED_RISK | BLOCKED
Verification needed:
```

## 3. 证据等级

| 等级 | 说明 | 可支持的结论 |
|---|---|---|
| `STATIC` | 设计/代码阅读得到的判断 | 风险、假设、建议 |
| `TOOL_VERIFIED` | Lint、Elaboration、CDC、Timing 等工具输出 | 工具检查结果 |
| `SIM_VERIFIED` | 有日志、波形、Checker 和 Seed 的仿真 | 指定场景的功能结论 |
| `IMPLEMENTATION_VERIFIED` | 综合/实现/时序报告 | 资源、时序和实现结论 |
| `HW_VERIFIED` | ILA/VIO 或板级测试证据 | 指定硬件场景结论 |

低等级证据不能替代高等级证据。例如 `STATIC` 不能替代 `SIM_VERIFIED`，功能仿真不能替代 `IMPLEMENTATION_VERIFIED`。

## 4. 报告与原始证据

- 报告必须记录工具版本、目标器件、基线版本和运行时间。
- 任何 PASS 必须能定位到原始日志、报告、波形或数据库。
- 失败报告优先记录第一个因果错误，后续级联错误单独标记。
- 修复前后使用相同输入和判定标准，才允许比较结果。
- 仿真结果必须记录 Seed；Coverage 必须记录数据库和生成命令。
- Timing/Methodology 修改后必须重新执行对应检查，不能只修改报告文字。

## 5. 追溯链

```text
Requirement ID
  → Design Section
  → RTL Module / Signal
  → Review Issue or Risk
  → Test ID / Tool Check
  → Evidence Artifact
  → Final Status
```

## 6. 允许的闭环方向

```text
需求变更 → 设计基线更新 → RTL/Review/验证影响分析
Review问题 → Test ID 或工具检查
仿真失败 → 设计 / RTL / TB / 环境分类
时序失败 → RTL / 约束 / 架构分类
硬件失败 → 版本 / 配置 / 时钟复位 / 逻辑分类
```

禁止直接根据 DUT 当前输出修改 Expected；禁止通过延长 Timeout、降低 Assertion 严重级别或删除 Checker 来制造 PASS。
