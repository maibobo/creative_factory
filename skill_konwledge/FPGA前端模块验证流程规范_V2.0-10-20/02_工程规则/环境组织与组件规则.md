# 环境组织与组件规则

## 1 环境类别与组件职责

按并发、事务关联和复用需求选择基础 TB、轻量级 SV、完整 SV／轻量级 UVM。基础 TB 可以合并文件，不能缺少观察和自检查；轻量级 SV 明确事务和组件边界；完整环境集中管理配置、并行场景和结束。普通 SV 不强制使用 UVM 生命周期。

| 组件或关系 | 必须满足的规则 | 检查证据 |
| --- | --- | --- |
| 顶层与接口 | 方向、位宽、参数一致，每个驱动信号有唯一所有者 | 端口对照、连接和运行诊断 |
| Test | 组织场景与约束，不代替实际接受事件 | 输入 Monitor 与发送计划分别可查 |
| Driver | 协议时序独立，接受后才推进，复位可取消或恢复 | 等待保持、接收计数和复位响应 |
| Monitor | 被动观察真实接口，不从 Driver 计划直接构造实际结果 | 首尾拍与等待拍的真实重建 |
| 参考模型 | 按规格解释已接受输入，维护必要功能状态 | 手算例子和状态更新依据 |
| Scoreboard | 关联预期与实际，检查数据、顺序、数量和异常响应 | 错误、额外、缺失及残留都有报错路径 |
| 配置 | 采用单一明确来源和优先级，关键值启动时核对 | DUT、模型和组件的有效参数一致 |
| 队列连接 | 所有者和生产消费关系明确，无观察丢失和无界增长 | 容量、阻塞、复位和排空诊断 |
| 生命周期 | 先完成连接再启动，结束前处理完全部依赖任务 | 不存在未启动线程或提前停止通道 |
| 复位 | 驱动、模型和比较器使用相同保留/取消语义 | 接受、完成、取消和剩余关系可解释 |
| 错误上报 | 首错有上下文，局部错误进入统一结果 | 受控错误能导致用例最终失败 |
| 调试措施 | 正常运行移除改变功能的强制值和临时屏蔽 | 自检副本与实际用例配置分开 |

interface 约定驱动和采样关系。事务发布后不可由生产者继续修改；消费者需要改变内容时复制，动态数组和嵌套对象按语义深复制。mailbox 或队列连接说明容量与阻塞，Monitor 不能因消费者暂未处理而漏采样。参考模型与 Scoreboard 分开职责，前者算预期，后者做匹配和检查。

多个并行线程操作同一个队列时，明确修改者和同步方式。临时延时不能保证无竞争。所有在途事务保留可关联信息，复位、错误和超时后不能留下一批无人负责的事务。

完整 SV 自行定义创建、连接、启动、运行、复位、停止和检查责任。轻量级 UVM 明确 build/connect/run/check/report，核对实际组件类型、配置获取及 TLM 连接。sequence 决定场景，Driver 执行接口，Monitor 被动重建。objection 仅管理运行期，不能代替业务排空判断。

多接口场景通过真实事件和状态协调，不能以固定延时推测另一通道完成。配置替换、工厂替换或 agent 主被动切换后，确认实际行为和驱动所有权；被动组件不得仍然驱动信号。

## 2 驱动、采样与对象管理

同步接口的接受条件以协议定义及约定采样边沿为准。valid/ready 类接口只有二者在该边沿同时有效才完成一次传输；信号电平持续多拍不等于只发生一次，也不等于没有握手就已发送。Driver 和 Monitor 使用一致规则，统计必须来自真实接口。

| 必须满足的规则 | 可发现的错误 |
| --- | --- |
| 未接受时保持规定的有效数据与侧带 | 等待时推进造成数据丢失 |
| 接受后才更新事务进度和输入计数 | 发送计划被误当实际数据 |
| Monitor 被动采样，不控制就绪或有效 | 观察组件改变待验证行为 |
| 同一事务字段来自同一采样快照 | 数据和尾拍标志错位 |
| 驱动与观察避免同一区域竞争 | 相同种子偶现、错一拍 |
| clocking block 的读写边界使用一致 | 混用直接引脚读值得到不同快照 |
| 控制未知态显式报告 | 宽松比较把不确定值当正确 |
| 发布对象保持稳定，修改者先复制 | 历史队列全部变成最后一笔 |
| 动态数组及嵌套对象按需要深复制 | 只复制句柄仍共享数据 |
| 配置共享需说明只读或修改所有者 | 某组件改变其他组件的有效模式 |

方案应说明驱动发生在何时、DUT 在何时采样、Monitor 观察的是哪个时刻的值。不能简单在同一边沿随意读写而假定总能得到期望顺序。已有稳定接口约定可复用，但替换为新时钟或新模型时重新核对。

复位进入可能不等待正常采样边沿，线程需要单独响应并停止旧事务。复位退出后不能立即使用上一拍缓存的数据；先确认有效状态，再重建新事务。数据无效时可以不比较内容，但控制和协议要求仍需检查。

Monitor 循环复用一个 transaction 并把同一句柄多次放入队列，后续修改会使历史记录改变。应每次生成新对象或发布独立快照，动态内容也按语义复制。消费者若仅只读且生命周期受控，可共享只读对象；需要修改或长期缓存时必须确保不会污染其他订阅者。

Driver 接收到 Test 对象后如果还要延时、拆拍或修改字段，应明确对象是否已转移所有权。Test 不应在 Driver 使用期间再次随机化同一对象。Scoreboard 保存的预期和实际记录分别独立，不能引用同一底层缓冲区后进行自我比较。

使用连续两笔明显不同数据及中间等待，检查 Monitor 捕获的序列、时间和侧带；再复用输入对象验证历史记录不变。此类检查针对具体数据流风险，不要求为每个类形式化测试。工程师确认采样关系和所有权写入方案组件设计，按 S05 审查模板实现。

## 3 模型与结果检查

预期从规格和真实接受的输入产生。允许读取配置和规格定义的外部状态，不能直接读取待验证的 DUT 输出或内部计算结果来构造“正确值”。模型应表达外部功能而非逐行复制 RTL 控制逻辑，降低共同实现错误的风险。

| 必须满足的规则 | 检查依据 |
| --- | --- |
| 模型输入来自实际接受事件 | 被拒绝或取消前的计划不误入预期 |
| 数据单位、符号、溢出和截断语义明确 | 手算边界结果与模型一致 |
| 状态只保留计算预期所需内容 | 不依赖不属于规格的内部状态编码 |
| 比较内容、长度和必要侧带 | 相同计数的数据错仍可发现 |
| 顺序或 ID 关联符合实际协议 | 不把合法乱序当错或非法交换漏过 |
| 字节屏蔽仅应用于无效数据范围 | 有效数据及控制未知态不被屏蔽 |
| 无预期的实际输出报额外响应 | 不静默丢弃无法匹配的输出 |
| 结束前检查未满足预期 | 丢失响应由残留或超时发现 |
| 复位和错误导致的状态变化有定义 | 旧事务不影响新业务，取消有记录 |
| 模型或检查修改后重审历史结果 | 原通过不在错误判据下继续沿用 |

局部协议检查发现等待期间不稳定、非法控制和响应时限；端到端比较发现数据内容、顺序、重复和遗漏。两者独立提供信息，同一根因可关联同一问题，但不能相互替代。中间接口比较仅在确有定位价值或规格边界时加入，不为了层数增加重复检查。

对数据重排、宽度转换和帧拼接，预期宜先变成规范化有效字节序列，再按输出格式构造检查对象；标识和错误语义单独保留。不能简单把输入拍数等同输出拍数，也不能比较未定义填充位。

选少量可手算例子，包括一般值、边界和需要保留状态的场景；核对预期的生成和消费时机。受控改变一个有效字节、交换两笔或删除一个响应，确认对应错误能进入最终结果。自检恢复后再执行正常用例，不把故意错误作为 DUT 失败。

日志至少报告首个不同字节或字段、事务键、预期和实际值、用例及时间。大数组可保存摘要和首错位置，原始必要数据能通过证据索引查到，避免海量打印淹没真正错误。

模型不表达的初始化、真实物理错误和外部软件行为应明确限制。若本模块依赖这些行为，应补充合适模型或用例。工程师确认模型不是“能运行即正确”，而是输入、转换、状态、复位和比较与目标规格一致。

至少对关键数据路径证明受控数据错误可被发现，对缺失应答证明有超时或残留检查。需要检查重复、错序或未知响应的环境，应证明对应路径能报错。自检只在可恢复的验证副本进行，恢复后执行正常场景。没有失败路径的空比较函数不算检查器。

| 连接位置 | 检查动作 | 发现问题后的处理 |
| --- | --- | --- |
| Driver 到接口 | 跟踪一笔事务从对象到真实接受，核对字段和等待 | 修正推进条件，不能把发送对象直接当 Monitor 输出 |
| 输入 Monitor 到模型 | 对照实际接受数与模型入队数，检查漏发和重发 | 明确发布时机及消费者，避免一笔多次预测 |
| 输出 Monitor 到比较器 | 用不同数据核对首尾、有效字节和关联键 | 修正重建，不能靠放宽比较掩盖错采样 |
| 配置到各组件 | 比较启动日志中的实际值及 DUT 参数 | 定义唯一来源或优先级，缺失配置立即报告 |
| 复位协调 | 检查所有组件收到同一复位并清理相应状态 | 建立统一语义，保留取消信息和恢复检查 |
| 结束协调 | 停止新激励后观察模型、输出及队列完成 | 修正完成条件，不靠固定延时强制退出 |

公共组件只承担实际需要的职责。协议驱动中不夹杂预期计算，Monitor 不依据测试想法过滤“不感兴趣”事务，Scoreboard 不偷偷修改 Driver 的等待策略。职责边界不清会造成环境帮助 DUT 得到正确结果，从而掩盖设计问题。

基础 TB 可以把这些动作写为任务和过程块；轻量级 SV 可以用类和 mailbox；完整环境可以用 agent 和 TLM。相同的有效观察与检查要求适用于三种形式，不能因为采用框架就默认线程、连接和对象管理一定正确。

证明关键检查能对错误给出失败，并避免将合法行为误报。自检只在可恢复的验证副本中进行，针对已知风险设计少量有区分力的场景，不建立与实现逐句对应的庞大测试。自检证据和 DUT 正常验证结果分开记录。

| 检查对象 | 必须确认的性质 |
| --- | --- |
| 数据比较 | 修改有效字节能报预期与实际差异 |
| 顺序检查 | 严格顺序接口交换事务会失败 |
| 数量和关联 | 缺失、重复及未知响应不会静默被丢弃 |
| 有界等待 | 需要的响应缺失能在上限失败 |
| 结束检查 | 队列残留或检查未启动不会通过 |
| 断言接入 | 启用后的受控违例进入统一失败 |
| 合法容忍 | 允许的等待、乱序和取消不会被错误禁止 |
| 恢复 | 临时注入、强制和屏蔽已移除，正常场景通过 |

优先在模型或比较输入上受控改变数据，不需要修改正式 DUT。检查协议稳定性时，可在验证副本构造明确违例；检查缺失时阻止一笔必要响应，确认超时或残留。必须说明自检针对什么机制，不将人为异常写成真实 DUT 缺陷。

不应同时修改参考值和实际值使错误互相抵消。注入的数据必须落在有效比较范围，否则无法证明检查器能检测有效错误。检查断言还应验证前提确实发生，单纯没有失败并不证明它工作。

误报优先看采样关系、合法等待、取消语义、ID 规则和未定义数据；漏报优先看观察是否启动、数据是否真正比较、掩码和宽松相等、对象共享及结束是否过早。修正时保留正确判据，不通过扩大容忍消除真实错误。

若发现共享检查器漏检，识别依赖它的历史结果，修复后自检并复测受影响范围。自检通过不能证明全部规格充分，仍需测试点和实际用例对应。工程师按 S03/S05 确认副本范围、恢复及结论。

## 4 复位、并发与结束

复位检查不仅看寄存器初值，还检查事务如何中断及恢复。首先从规格确定已接受但未完成的事务是取消、保留还是重试，环境所有组件按同一规则执行。未定义时先确认，不允许 Driver、模型和 Scoreboard 各自选择方便实现的策略。

| 必须满足的规则 | 检查依据 |
| --- | --- |
| 复位有效电平、进入和退出关系明确 | 与 DUT、模型接口及方案一致 |
| 复位期间接口驱动回到规定状态 | 没有旧线程继续写业务信号 |
| 未接受事务与已接受事务分别处理 | 不把未接收计划算作丢失 |
| 在途事务取消或保留有可核对记录 | 接受、完成、取消和剩余关系一致 |
| Monitor 不将中断片段拼成新事务 | 帧、包或多拍事务边界重新建立 |
| 模型和比较器按相同语义清理 | 不会一方保留而另一方清空 |
| 必要时区分复位前后事务代次 | 旧响应不误匹配新请求 |
| 退出后等待有效就绪条件 | 复位撤销不等于 IP 已经可接受业务 |
| 首笔新业务有内容与完成检查 | 不能只观察静态初值就算恢复 |
| 重复复位和关键时刻按适用风险检查 | 不要求无意义穷举，但边界有依据 |

至少根据模块行为选择空闲、输入未被接受、接受后等待输出、部分输出和事务完成附近等情形。简单单拍模块可减少不成立的场景，但说明没有对应在途状态。对多个独立复位域，按本模块可观察的功能约定处理，不扩大成其他验证范围。

复位发生在握手附近时，要根据实际接受边沿判定事务属于已接受还是未接受。不能以软件式“先调用复位任务”推断硬件从未接收。复位中断后的计数记录应解释取消，而不是直接把所有历史计数清零掩盖问题。

撤销复位后确认依赖模型忙状态、就绪或其他初始化条件，再发新业务。新事务采用与旧数据明显不同的标识或载荷，检查没有旧数据泄漏、没有残留错误状态、没有重复完成。若规格允许旧响应继续返回，比较器按相应代次和顺序处理，不能一概丢弃。

复位过程的就绪等待和恢复事务等待分别有上限，日志说明停在哪一步。工具模型没有响应复位时，应区分模型限制和 DUT 错误。复位测试失败后保存原时间关系、种子和配置，修复时重查 Driver、Monitor、模型及结束逻辑，而非只改 DUT 复位语句。

方案写复位语义，表单写场景，运行记录保存取消和恢复证据。工程师确认上述信息一致，按 S05 接受代码；临时注入和复位强制值按 S03 恢复。复位规则改变会影响旧结果，应按变更规则重新判断和复测。

用于本模块实际支持多个独立接口、分离通道、多个请求源或在途事务的情况。没有相关能力时说明不适用，不因接口名称推断支持全部并发特性。并发的重点是事件关系和共享状态，不是同时启动很多线程。

| 必须满足的要求 | 检查依据 |
| --- | --- |
| 每条通道的接受事件单独定义 | 地址、数据与响应不会混成一次握手 |
| 整笔事务完成关系明确 | 某通道结束不提前报告全部完成 |
| 共享驱动信号只有一个所有者 | 多线程通过仲裁或队列提交 |
| 共享模型状态和队列修改规则清楚 | 不依赖线程偶然执行顺序 |
| 协调使用实际事件或可查询状态 | 不用估计延时推断另一通道完成 |
| 合法通道先后和同时条件有检查 | 不全部人为串行化而遗漏交互 |
| 独立随机源可复现且配置可查 | 不因并行覆盖数据文件改变刺激 |
| 资源限制按实际能力建模 | 最大在途、ID 和容量不会被无意超用 |
| 复位和中止作用到全部相关线程 | 没有旧请求源继续驱动或等待 |
| 全部通道共同支持结束判断 | 不留未检查响应或孤立任务 |

将请求接受、数据接受、处理完成和响应分别列成事件关系。协议允许独立先后时选择有区分力的组合；有依赖时场景遵守依赖，不生成未定义输入。共享缓存或仲裁模块需要检查同时申请、持续占用、资源释放及恢复，公平性仅在规格有要求时给具体判据。

被动 Monitor 不应为了避免拥塞主动改变 ready。需要背压的由明确 BFM 或 Driver 控制，观察与驱动职责分开。下游比较任务较慢时采取缓存和容量诊断，不让 Monitor 默默漏事件。

瞬时事件可能在等待者启动前已经发生，不能简单把一次触发当永久就绪。需要保存状态或按明确顺序启动。共享变量更新使用可解释同步关系，不能用长延时掩盖竞争。出现同种子偶现时优先检查这些关系及共享对象所有权。

停止新请求后等待所有通道按协议完成或取消，检查在途、队列及错误。某个激励源提前结束不能导致环境提前关闭。对通道关联或共享状态修改，复测原失败、合法先后、同时事件及复位恢复，不仅单独运行各接口。记录及代码确认对应 S04/S05。
