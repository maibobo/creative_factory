# 仿真、复现与问题定位方法

工程师编写和完善方案与代码，AI 辅助查漏补缺、生成模板和定位，工具提供实际结果。按当前模块需要选用下述方法，示例不代表已经执行的项目结果。

## 工具与执行入口

核对表单有效用例、入口名称、实际参数、种子、工具、库与输出目录。列表行与运行可以是一对多，例如同一用例多个种子，但报告必须知道每条运行属于哪一项。启动前保存有效列表和配置，避免运行期间被编辑导致前后使用不同内容。安全：文件与命令 S03，证据隔离 S04，结论 S05。

```text
make run tc=tc_stream_backpressure seed=123456 mode=default wave=fsdb
```

`tc` 必填，其他项可省略，命令解析后写实际值。上例只用于支持 FSDB 的后端；XSim 不原生输出该格式。请求不被支持时应返回明确异常，不能静默忽略。没有请求波形时，项目是否仍保存默认波形由本次配置决定并记录。

启动后先确认编译展开成功及模型已经就绪，再判断用例有没有真实输入。结束后读取本轮日志、结果及所要求产物，不从以前打开的工具窗口复制结论。命令不存在或后端未适配时写环境未就绪，本包不包含脚本实现。

```text
h_regress -cur
h_regress -rerun
```

当前列表采用确认的用例、种子和配置。执行异常项重跑时读取原记录，在新目录使用修复版本重新运行并关联旧运行编号。若原始种子缺失，不生成猜测值冒充原条件；先恢复记录或明确无法严格重放，并说明替代检查。

独立用例功能失败可以继续；共享编译或模型失效后，受影响项停止并标明未执行。已经启动但被中止的项与从未启动的项分别保留原因。重跑成功不删除原失败，最终报告说明哪个修改解决了问题。

## 结果与固定条件

运行记录能够说明测了什么、结果怎样、如何复现即可。通常保留用例、实际种子和配置、适用版本，以及结果与日志位置；发生问题时补充首错和修复前后的对应记录。事务计数等诊断信息按功能需要保留，不要求所有模块维护同一套字段，也不为已有记录另建重复表单。

保存用例、实际种子、模式、宏参数、RTL/TB、工具、模型和库，以及工作目录依赖。随机调用次数和对象创建顺序可能改变序列，多线程和共享文件也可能产生差异。相同 seed 但配置变了不是同条件，不同工具版本也不能保证相同序列。

严格复现时对照首个错误时间关系及事务特征；只看到相同“数据不一致”字符串不足以确认同一原因。若原条件不可恢复，说明缺口和替代验证，不补造原记录。首次失败保留，新运行有独立编号。

通过、失败、异常、未执行是互斥的最终状态，根因另记。工具未启动不是 DUT 失败；功能比较已通过但要求波形缺失，最终记录异常并保留比较事实；有真实功能失败又缺产物时保留失败及附加原因。列表总数由逐例结果重算，用例数与运行次数分开。

日志中的 PASS 只是信息之一，要核对正常结束、检查器启动、真实业务、零错误及无不明残留。预期错误用例可能合法打印错误响应，不能简单搜索 ERROR 决定失败；应判断它是否与预期及统一错误机制一致。

| 场景 | 最终状态 | 原因字段与后续 |
|---|---|---|
| 内容顺序正确，结束及产物满足要求 | 通过 | 保存本轮计数与证据位置 |
| 第五笔输出错误 | 失败 | 保存预期、实际值及首错，进入问题闭环 |
| 等待响应超过规定上限 | 失败 | 写等待对象和在途信息，判断根因后修复 |
| 工具启动或库加载失败 | 异常 | 功能未完成，修正配置并重跑 |
| 比较通过但请求波形缺失 | 异常 | 保留比较结果，修复保存机制并补齐证据 |
| 共享环境中断后剩余项未启动 | 未执行 | 关联导致停止的运行或环境记录 |

## 从首次异常定位

把一笔事务沿输入接受、预期生成、输出观察和比较排列。找最早与正确关系不一致的位置，而不是从最后的 watchdog 或残留错误直接猜。后续大量错误可能只是第一笔漏采样造成的连锁反应；修复前要验证该因果关系。

可以列“时间—事件—预期—实际”短表，保留必要上下文，不需要把整段波形逐拍抄入报告。若预期在输入未接受前已经入队，优先查模型驱动来源；若真实输出正确但比较错，优先查采样和关联；若输入与预期一致而输出首次偏离，再检查 DUT 相关路径。

数据总错一拍：可能是读模式、采样边沿或尾标志快照；用短、不同载荷和已知延迟核对。历史队列变成同一值：优先检查共享对象和动态字段复制。无事务：查复位、就绪、发送有效及接收条件。结束卡住：比较接受、完成、取消和剩余，找未消费队列。

这些是候选原因，不能未经证据直接作为根因。每个假设应有能够支持或排除的观察。例如怀疑采样错误，检查约定边沿前后稳定值和 Monitor 记录，而不是同时改时钟、延迟和比较器后看是否通过。

保持失败条件，增加能定位首个偏离的日志或波形；优先改变观察而非刺激。需要受控改变条件时一次聚焦一个因果问题，记录改变及结果。临时强制值和错误注入只用于可恢复副本，正式复测前移除。

诊断不要求另建缩减工程。可以利用原用例、固定种子和关键时间窗缩小观察范围，避免丢失真实依赖。修复依据是确认的规格和原因，不能用放宽比较或不断增加等待让结果偶然通过。

已知现象：输出总字节数正确，只有非整拍帧尾部出错。不能直接认定 DUT 的尾拍逻辑错误。先核对规格长度单位，输入 Monitor 收集的有效字节，模型如何构造尾部，再看输出实际有效位和 Monitor 采样。选择短且不同的字节，保留原等待关系，找到首个差异。

| 假设 | 支持或排除它的观察 | 可能处理 |
|---|---|---|
| 模型把拍数当字节数 | 模型有效序列长度与实际接受不符 | 修正单位并重查依赖结果 |
| Monitor 尾标志错采一拍 | 引脚快照与发布对象不同 | 修正采样关系，检查连续和等待 |
| DUT 尾部选择错误 | 输入与预期正确、真实输出首次偏离 | 修正对应逻辑并复测相关尾长 |

每个假设用事实区分，不同时改多个位置后只看能否通过。修复后原条件、整拍、不同尾长和尾部反压共同支持关闭。

已知现象：复位前全部正确，复位后第一笔与预期不符。先确认复位语义和发生时刻，列已接受、已完成、取消和剩余；再检查 Driver 是否仍运行旧任务、Monitor 是否保留半笔、模型和 Scoreboard 是否清理一致、旧响应是否误匹配新请求。

若输出是真正的新数据但预期还是旧数据，优先查环境清理；若预期正确而输出旧数据，检查 DUT 及依赖模型；若两者都无法区分，使用明显不同的新载荷和事务标识增加可观察性。新刺激用于定位时应记录变化，不能冒充原条件复测。

修复后要在空闲、接受未完成、部分输出和恢复首笔等适用条件检查。只是重新把复位时间挪到空闲区让用例通过，并没有修复在途问题。

先核对种子是否控制所有随机源，版本、参数和模型是否相同；再查共享工作目录、初始化文件、进程状态和线程竞争。比较真实接受序列及最后完成事件，确认不同发生在输入、处理还是结束。

如果输入完全一致但 Monitor 历史记录变化，考虑对象共享和采样竞态；如果输入已经不同，查随机调用和外部输入；如果业务完成但未结束，查队列和计数，不归为 DUT 卡死。重复运行可采集现象，不能以多数通过否认原失败。

## 修改与复测

先执行原失败条件，再按修改影响选正常、边界、等待、复位及随机组合。参考模型或比较器变更可能使多条旧通过失效，应重新判断依赖范围。报告写根因、修改、原条件运行、关联运行和确认人，不只写“已修复”。

例：尾拍反压后重复输出，修正推进条件后原例通过，还应检查首拍等待、连续帧和不同尾长。若仅新种子通过而原种子未跑，缺少关闭依据；若改了模型后“全通过”，还需证明新模型的预期正确。

若修正尾拍字节选择，原失败复测之外，还应检查整拍、非整拍、最短、最长、尾拍等待和连续帧。若修正复位清理，检查空闲复位、接受后未完成、部分输出及恢复首笔。若修正比较器的对象复制，需要重查所有共享该比较器的用例，不能只重跑报错的一例。

修改说明应包含改变了什么外部行为、为何符合规格、影响哪些检查。延长超时若只是修正原来少计的合法等待，应提供时限依据；如果是在掩盖永不返回，不能接受。临时屏蔽检查须在正式复测前恢复。

“问题 P001：尾拍等待后重复接受。原记录 run_0007，原种子与配置见索引。修改发送进度仅在真实握手后推进。修复版本 run_0019 原条件通过，尾拍等待用例及连续帧、最短帧用例通过，相关随机运行见清单。原错误消失，未出现新错误，工程师确认关闭。”

这段只是格式示例，不能替代实际日志。若相关用例仍失败，应保留问题待处理，不能把其中一条通过写成全部关闭。关闭结论要能找到根因、修改与两类复测证据。

一般遗留写受影响功能和配置、出现条件、规避或使用限制、责任人、后续措施及接受人。接受是对明确限制的判断，不代表修复。严重问题或关键检查失效未解决时，出口不通过。证据与实际版本不符、无法说明修改影响时，仍保持待确认。

AI 区分观察事实和原因假设，工程师确认后修改或完善环境与用例，再由工具执行。结果放入[仿真回归报告](../../03_项目模板/仿真回归报告模板.docx)，判定见[回归与结果判定规则](../../02_工程规则/回归与结果判定规则.md)。
