# 覆盖率检查与完善方法

工程师编写和完善方案与代码，AI 辅助查漏补缺、生成模板和定位，工具提供实际结果。按当前模块需要选用下述方法，示例不代表已经执行的项目结果。

## 理解报告与范围

行说明可执行语句是否执行，条件说明逻辑取值，状态机说明工具识别到的状态和转换是否经过。它们都不直接回答数据是否正确、规格是否完整和检查器是否有效。某段代码被执行但输出错误，功能仍失败；高数值也不能抵消关键行为没有判据。

工具口径、源语言、优化、识别和配置影响统计。报告中没有某指标时先确认支持与采集状态，不能直接填零。当前参数不生成的逻辑与生成后未触发的逻辑分开处理。指标解释优先准确，不追求跨工具格式完全相同。

| 层次 | 问题 | 要找的事实 |
|---|---|---|
| 统计层 | 当前报告是不是本次 DUT 和配置 | 文件、实例、版本、选项及参与运行 |
| 能力层 | 工具能否统计该语言和对象 | 实际版本能力、诊断及识别结果 |
| 范围层 | 行为是否属于约定合法配置 | 参数、生成条件和交付范围 |
| 事件层 | 目标是否真的被触发和接受 | 就绪、真实握手、状态和关键计数 |
| 模型层 | 环境能否产生相应条件 | BFM 控制能力、模型接口和限制 |

先解决前面层次，避免围绕无效报告补测。若统计对象错误，增加用例没有意义；若模型永远固定就绪，随机 Test 可能无法制造等待；若参数关闭功能，必须判断是否还需要其他配置，而非修改输入强行触发不存在逻辑。

## 查明未覆盖原因

不可达应指出前提与条件关系。例如规格保证两个状态互斥，某条件组合在合法输入下不成立，需要说明该保证及代码关系。仅因从未观察到，不能证明不可达。防御性逻辑也需要明确它防御什么条件，能否通过已定义错误入口检查。

不适用指当前约定范围不含该行为，不支持指工具没有测量能力，模型限制指环境没有表达能力。三者不能混用。本项目需要的主要行为即使模型无法表达，也仍需补验证或保留未完成，而非自动作为合理排除。

Test 发送数量很多，但输出接收一直开启，缓存占用没有达到满。原因在事件关系，不能从请求数量推断容量状态。先根据真实输入接受、输出取走和取消计算占用，再定向暂停输出形成临界条件。检查满时允许的接受行为、数据保持以及释放后的恢复。

若占用关系已经到满而报告仍未变化，核对范围、配置、代码位置及工具统计单位。不要为了使数字变化而改变 DUT 的正常逻辑。补测结束后同时检查功能和目标执行信息，出现满条件但数据丢失仍是失败。

当前模式关闭可选功能，源码中相关部分在本次展开时不存在。记录参数和生成依据，确认交付是否只含当前模式。若还要交付开启模式，建立相应模型、约束、用例和结果，不能用关闭模式的数值代表全部能力。

若当前确不需要，说明本次范围及确认人，后续范围变化时重新评估。这里是配置适用判断，不是人工把未执行改为已执行。工具报告原值保留，说明与测量分开。

先确认错误属于规定输入范围及模块需要处理的行为。若是定义的错误响应，检查模型能否从合法入口产生它，Test 是否控制了正确字段，输入是否被接受。可以注入时编写预期错误和恢复的用例；模型不能表达时明确缺口及替代办法。

若防御代码针对规格下不可能的组合，应说明互斥前提和逻辑关系。不能仅因为一直没遇到就说不可达，也不能随意对内部信号强制值后把结果当真实接口证据。调试注入与功能验证证据的范围应明确。

核对工具版本、识别结果和源语言。没有原生状态机统计时，如实记录能力，使用实际状态进入、退出和转换相关用例说明已测行为。一个状态信号截图只能支持可见现象，需要结合用例和时序关系，不能证明所有转换。

如果状态编码不适合工具识别，不应仅为了统计外观修改正确设计。先判断是否有可用工具或功能证据满足本次目标；缺少关键证据则保留未完成。不能将人工列出的状态个数作为工具百分比。

## 补测与工具限制

补测写清目标条件、控制者、输入顺序、如何证明事件出现以及输出怎样检查。正常用例没有触发错误处理时，先确认规格定义错误和恢复，再用可控模型入口注入；随机等待没有触发满条件时，定向控制输入输出节奏；长度边界缺失时，明确单位和分界再选择数据。

不能只写“增加随机次数”。如果约束排除了目标、复位未退出或 Driver 没有真正接受，增加次数仍无效。定向稳定触发后，随机才适合扩大交互组合。补测之后看目标位置与实际事件，再看功能比较是否通过，不只看总体数值增加。

同一源文件不同参数可能生成不同结构。合并前确认工具允许且统计口径有意义，保留各配置和参与运行；如果结构变化很大，分开呈现更容易判断。不能仅为得到更高数值而合并版本不同或范围不一致的数据。

失败运行的执行信息可辅助理解触发，但不作为成功功能证据。报告同时保存运行状态，让工程师知道“代码经过”和“功能通过”的区别。原始数据库和报告独立保留，人工摘要引用它们，不改写分母或隐藏不利运行。

缓存满路径未执行：先查实际输入接受与输出取走，可能因每次输入同时输出导致永远不满。补测暂停输出、逐笔形成临界状态，再检查满时规定行为和释放后的恢复。观察目标事件与功能结果，不是只把请求数量增大。

可选功能路径未执行：当前参数关闭，查交付是否需要开启；若需要，补配置与用例，并核对模型、约束和预期；若不需要，报告记录参数和范围依据。不能用关闭配置通过代表开启配置。

状态机没有原生统计：核对工具识别和版本，记录能力限制，用测试点、状态进入退出及转换的实际证据解释已测范围。不能把状态名称清单或人工确认写成原生百分比，也不能从工具不识别推断状态行为不存在。

## 解释结果与确认

将原始指标、范围和支持状态简洁记录；对重要未覆盖项写“位置—行为—原因—证据—处理—剩余影响”。补测与一般问题关联时保留运行编号。工程师重点确认原因是否基于事实、关键行为是否仍缺证据，最后与功能结果共同支持出口判断。

无效：“此处无法覆盖，已说明。”有效：“当前模式关闭该入口，参数及生成条件见方案，交付范围不含开启模式；工程师确认本次不适用，后续开启需要新增测试。”后者有事实、范围和影响，可以被核对。

无效：“模型问题。”有效：“当前接口模型始终返回正常响应，不能从配置注入该错误；该错误处理属于约定功能，需扩展模型或采用已确认入口补测，当前保持未完成。”模型限制不是功能完成证据。

如果输出内容明显错误，即使所有相关行都已执行也应先处理功能问题。若检查器本身不可靠，覆盖率结果只能说明执行情况，不能支持完成。补测时检查器应能识别目标错误，否则执行到代码仍然可能假通过。

只记录行、条件、状态机。AI 帮助整理原因和补测建议，工程师对照实际结果确认。结论纳入[仿真回归报告](../../03_项目模板/仿真回归报告模板.docx)，要求见[代码覆盖率检查规则](../../02_工程规则/代码覆盖率检查规则.md)和[未覆盖项处理规则](../../02_工程规则/未覆盖项处理规则.md)。
