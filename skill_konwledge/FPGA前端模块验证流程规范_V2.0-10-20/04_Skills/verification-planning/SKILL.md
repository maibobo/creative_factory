# 测试点分解与验证方案方法

工程师编写和完善方案与代码，AI 辅助查漏补缺、生成模板和定位，工具提供实际结果。按当前模块需要选用下述方法，示例不代表已经执行的项目结果。

## 从规格建立检查

一句规格常把多件事合在一起。以“接收请求后搬运数据并返回完成”为例，需要提取请求何时接受、源和目的地址单位、长度含义、有效字节、允许等待、完成条件以及错误后的状态。测试点不是接口信号表，而是能区分正确和错误的行为。

先写一条正常因果链：接受合法请求 → 获得相关数据 → 生成应有输出 → 所有要求动作完成 → 返回一次完成。再把每个连接处可能的变化展开：前提未满足、接收延迟、数据间断、尾部处理、并发和复位。这样能找到真实风险，而不是机械给每个端口建立一个点。

| 分解视角 | 要问的问题 | 适合形成的检查 |
|---|---|---|
| 输入与输出 | 什么输入会导致什么输出，什么输出禁止出现 | 内容、数量、标识和错误响应 |
| 接受条件 | 发出请求与被接受是否是同一事件 | 握手计数及未接受期间保持 |
| 数量边界 | 长度、深度、地址和计数在哪改变行为 | 临界前后、尾字节及容量释放 |
| 时间与并发 | 谁先发生、是否同拍、能否等待 | 连续、独立通道、反压及恢复 |
| 状态与异常 | 哪个事件改变状态，异常后如何继续 | 进入退出、取消及下一笔正常业务 |
| 参数与模型 | 什么配置改变路径，模型表达什么 | 实际合法配置及支持限制 |

对深度为 D 的缓存，关键不只是发送 D 笔，而是实际接受和取出的相对关系。先建立空状态，再逐笔接受且不取出，观察接近满与满时的规定行为；释放一个位置，再检查能否按协议接受新数据。若同拍进出会改变满判断，安排该条件。非法满写的响应只有规格定义时才检查，不能自己规定丢弃或报错。

对长度 L 的事务，先确认字节还是数据拍。数据位宽为 W 字节时，非整拍长度涉及尾拍有效范围；检查有效字节序列，不能比较填充部分。边界选择来自计数、分包和容量变化，例如最短、最长及相关分界前后，不是毫无依据列若干随机长度。

对时序，选择能够改变状态关系的先后条件。请求先到数据后到、数据先准备但请求未接受、两个独立通道同拍等是否成立，取决于协议及模块能力。没有该能力的模块不强行加入用例，先记录适用判断。

## 场景与用例写法

“验证反压”只是意图。可实现判据包括：有效事务未被接受时数据和必要侧带保持；恢复后每笔只接受一次；输出有效字节与被接受输入的规格变换一致；最后队列清空且无多余完成。局部稳定性和端到端比较回答不同问题，通常要配合。

“验证复位恢复”应说明旧事务取消或保留、新事务何时允许开始、首笔新输出是什么、旧数据是否可能泄漏。只看寄存器清零不能回答恢复。若规格未定义在途处理，先提出澄清问题，并标明哪些点依赖该答案。

预期来自规格和实际接受输入，观察来自真实接口。对于转换模块，给一个可手算例子确认字节顺序、符号、截断或饱和；对于缓存和请求关联，明确参考队列的建立与消费。不能把 DUT 输出记录下来再与自身比较。

定向用于稳定触发边界和建立可解释例子，随机扩大合法组合。对等待风险，随机等待位置和长度比只随机数据更有效；对长度换算，随机合法长度及尾部形态；对关联，随机合法 ID 和完成顺序。关键边界仍需定向保证，概率设置不是事件出现证据。

随机约束来自规格，字段相关性要共同满足。若地址、长度和有效字节彼此矛盾，普通随机会产生未定义场景，不能把检查失败直接归责 DUT。需要非法输入时单独说明目的和预期响应。约束过紧导致目标永远不出现时，应检查生成逻辑而非只增加种子。

1. 接收端 BFM 控制 ready，正常情况下允许接收；用例指定中间第一个有效输出出现后暂停接收。
2. Test 产生八笔示例事务，每笔数据带不同序号，Driver 遵守握手保持规则，未接受时不提前发送下一笔。
3. 等待长度采用当前用例约定范围，随机模式保存实际种子；关键的尾拍等待另有定向安排，不全靠随机命中。
4. 输入和输出 Monitor 分别只记录真实接受事件，参考模型从输入接收队列构造预期。
5. 输入完成后继续接收并比较，等待所有已接受事务结束，设置有依据的总等待上限。

这些内容说明本例差异；时钟周期、公共复位和仿真库不重复粘贴到每个用例。对外部模型施加的错误或等待，要说明它是否属于协议允许行为。

等待期间输出 valid 保持有效时，数据及与该拍相关的侧带信息保持；接受后才允许推进。输出有效字节序列与被接受输入的规格变换一致，数量、内容和顺序都正确；没有额外输出或重复完成。在途事务归零，预期和实际队列无不明残留，错误计数为零。规定的超时没有发生。

对取消语义明确的复位用例，要先记录哪些事务被取消，再检查新业务；不能同时要求旧事务全部输出且全部取消。预期中写“恢复正常”过于笼统，应具体为复位退出、模型就绪、新帧接受与完整输出。

## 环境与芯片支持点

基础 TB 适合状态简单、顺序关系清楚、预期直接计算的模块；轻量级 SV 适合事务复用、多个场景及等待复位协调；完整 SV／轻量级 UVM 适合多接口、多在途和复杂关联。实现形式不决定检查质量，应选择能维护清楚数据流和生命周期的最简单适用形式。

模型选择关注它是否表达待验证行为。理想内存可验证地址数据映射，但不证明真实校准；流 BFM 可验证反压，但不证明物理链路；FIFO 模型若读模式不一致，会造成一拍差异。方案写版本、参数、库、初始化、就绪及限制，不能只写“使用厂商模型”。

| 依赖对象 | 必须记录的具体内容 | 对本模块的检查影响 |
|---|---|---|
| FIFO 或片内存储 | 数据位宽、深度、读模式、复位忙、初始化及输出延迟 | 首次读出时刻、满空边界、同拍读写及复位恢复 |
| 外部存储控制接口 | 用户接口宽度、地址单位、就绪、校准及错误反馈 | 未就绪不发业务、地址长度换算、读写内容一致 |
| 流接口 IP | 字节有效、帧结束、就绪与有效语义、复位条件 | 尾拍、反压、帧边界及恢复，不延伸到物理层结论 |
| 请求应答类 IP | 通道独立性、ID 和顺序约束、完成及错误码 | 多通道接受关系、事务关联、未知或重复响应 |
| 时钟或复位辅助模型 | 输出时钟条件、锁定状态、复位传播及模型启动限制 | 观察业务启动前提，不凭固定延时假定就绪 |
| 数据初始化文件 | 来源、相对路径、字节排列、加载时机和默认值 | 未加载时应有诊断，不能用全零掩盖缺失 |

记录器件系列、IP 配置与模型版本，并明确 RTL 中实例与模型入口如何对应。库映射和编译顺序应由实际使用版本确定，源文件完整不代表模型一定能正确展开。加密模型先确认后端兼容性，不能在不兼容时删掉受限部分后继续宣称原 IP 已验证。

Xilinx 项目区分 IDE 管理的仿真工程与独立运行入口，确认导出的源文件、库和初始化材料是否完整。国产器件项目核对供应商模型说明及现有仿真器支持情况，重点检查语言、加密、路径大小写和文件依赖。方案记录已确认事实和待确认项，不填写未经验证的兼容性结论。

若验证目标仅是模块在接口边界接收、等待和返回数据，BFM 可以提供可控且容易注入异常的邻接行为。若模块依赖特定 IP 的初始化、忙状态、读模式或特殊应答，则模型必须表达这些关系；通用 BFM 没有表达的部分应明确限制或补充相应模型。

例如用理想内存 BFM 可验证地址到数据的映射、长度和等待，但不证明真实器件校准或物理接口能力。使用理想固定延迟可能隐藏模块对可变延迟的错误假设，若接口允许等待，就应设计相应变化。选择标准是能否表达待验证行为，不是模型文件越完整越好。

列出复位有效时间、撤销方式、忙状态清除、就绪到业务允许之间的条件，并用状态信号或已确认的时序关系等待。每次等待都给上限和失败信息。对模型中途失去就绪、错误反馈、复位恢复等行为，先确认接口是否允许及模块应如何处理，再安排刺激。

复位前已经被接受的数据是否保留，模型和 DUT 必须一致；若模型会清空存储而模块需要保留，不能直接共用默认复位。模型不支持错误注入时，不通过修改模型输出而省略恢复规则；应记录替代办法、适用边界和需要补足的证据。

## 查漏补缺与确认

建议写成“缺口—原因—补充—需确认”。例如“尾拍有效字节未说明，现有比较可能漏尾部；补充有效字节序列比较；需确认长度单位及尾部标识”。工程师决定采纳并更新表单，AI 不替他把待确认内容定为事实。输出应改善一个具体判断，避免重复流程阶段名称。

| 现有写法或现象 | 判断 | 应补的知识或方法 |
|---|---|---|
| “随机发数据一百轮” | 无法知道检查哪些行为 | 写合法范围、主要随机维度、真实事件和判据 |
| “收到完成即可通过” | 数据可能错误或重复 | 增加内容、顺序、有效长度和结束一致性 |
| “驱动已发送八笔” | 不证明 DUT 接受八笔 | 从输入真实握手建立预期 |
| “复位后信号为零” | 不证明在途清理与新业务恢复 | 检查取消规则和首笔新事务 |
| “模型不支持，写为不适用” | 混淆能力缺失与需求范围 | 明确约定目标，补证据或保留未完成 |
| “全部参数都随机化” | 可能生成未支持组合 | 先确认合法配置及字段相关关系 |
| “用了 UVM 所以检查完整” | 框架不自动提供正确判据 | 审查实际组件、观察和比较路径 |
| “正常用例通过后再想边界” | 方案可能遗漏关键结构 | 从数值和状态变化提前推导边界 |

提问要附具体分歧和影响。例如“长度为字节还是数据拍？这会改变尾拍有效字节和完成计数”，比“请完善接口规格”更容易回答。把一个问题限定在能改变判据的事实；不为无影响的实现偏好增加确认负担。

对未定义输入，不先选择最容易实现的响应。可以列出两种可能解释及对应检查差异，等待工程师明确；其他独立点继续推进。最终用方案和表单记录确认结果，不把临时聊天解释当唯一工程依据。

工程师先写测试点和方案初稿，AI 指出具体遗漏、依据和改法，工程师完善后再用于实现。使用[表单](../../03_项目模板/测试点分解表单模板.xlsx)和[验证方案模板](../../03_项目模板/验证方案模板.docx)，要求见[测试点与用例设计规则](../../02_工程规则/测试点与用例设计规则.md)。
