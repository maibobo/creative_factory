# 验证环境与用例实现方法

工程师编写和完善方案与代码，AI 辅助查漏补缺、生成模板和定位，工具提供实际结果。按当前模块需要选用下述方法，示例不代表已经执行的项目结果。

## 架构与三类环境

先写一笔输入如何被接受、如何产生预期、实际输出在哪里形成、何时比较和结束，再分组件。Driver 把抽象事务落实到协议；Monitor 从真实接口重建事件；参考模型从已接受输入计算结果；Scoreboard 处理关联及比较。Test 决定场景，不提供实际观察结果。

基础 TB 可以把职责放在一个文件，重要的是数据来源和所有者清楚。轻量级 SV 通过 interface、mailbox 或队列解耦；完整环境把多个接口按事务依赖组织。普通 SV 自主管理生命周期，UVM 使用相应框架机制，两者都不能自动保证业务排空。

适用于少量接口、顺序关系简单、预期结果可直接计算的模块。文件可以少，职责不能缺失。建立顶层、初始化、发送任务、输入输出观察、预期队列、比较和结束控制七部分；规模小的实现可放在同一文件，但应能指出每一部分的位置。文件操作执行 S03，判据和代码审查执行 S05。

列出端口方向、位宽、时钟、复位及必要模型，逐项对照 DUT 实例。没有使用的输入按合法空闲值处理，不能悬空；保留接口错误诊断，不能为了消除警告直接屏蔽。配置由单一位置传入 DUT 和模型，启动时打印实际值。

时钟按方案周期产生，复位按有效电平和退出关系控制；复位撤销后等待模块或依赖模型就绪。等待有上限，错误信息写明等待对象。若 DUT 没有就绪信号，应使用规格确认的启动规则，不能随意增加延时直到偶尔通过。

适用于多种场景、需要事务抽象、反压和复位协调、但无需完整框架的模块。至少明确 interface、事务、Test、Driver、Monitor、参考模型、Scoreboard 和配置的职责；是否独立成文件由维护需要决定。工程师在 AI 模板上实现实际行为，不能把类名和空方法当作环境完成。安全：S02、S03、S05。

interface 统一信号方向和驱动/采样时机，必要时使用 clocking block 管理时间关系；使用后通过一致的成员读写，避免与直接引脚读值混合成不同快照。复位异步进入时单独规定线程响应，不能只依赖正常时钟边沿发现复位。

事务只包含当前功能需要的字段，如有效数据、字节数、标识和错误属性。控制 Driver 的等待选项与被观察的实际事务信息分开，避免 Monitor 复制刺激意图。动态数组、嵌套对象和共享配置的复制边界应写清；发布后修改对象会污染已入队历史，必须用稳定快照。

Test 产生场景 → Driver 执行协议 → DUT 接受输入 → 输入 Monitor 发布真实事务 → 参考模型产生预期 → Scoreboard 入预期队列；DUT 输出 → 输出 Monitor 发布实际事务 → Scoreboard 关联并比较。每一条连接标明生产者、消费者及队列所有者。

使用 mailbox 或队列时，说明阻塞条件、容量和复位清理方式。被动 Monitor 不应因为下游暂时未取数据而漏掉接口事件；采用缓存时应有容量诊断。模型计算慢时可通过独立队列解耦，但结束前必须处理完缓存内容。

适用于多接口、并行场景、多在途事务、复杂事务关联或已有组件复用需求。完整 SV 与轻量级 UVM 属于同一适用类别的两种实现形式，分别说明生命周期，不能要求普通 SV 实现框架专用机制。目标是控制复杂度并提高检查可信性，不是增加无实际职责的层级。安全：S02、S03、S05。

明确创建、连接、初始化、启动、运行、复位、停止和检查八类动作的负责人。创建完配置与队列再启动依赖线程；连接检查能发现空虚接口、缺少消费者和重复驱动。事件用于表达状态或依赖，不能把一次瞬时事件当作永久就绪标志；需要可查询状态时保留状态变量并定义更新规则。

启动时记录各关键线程已就绪，再发业务。停止新激励后等待在途和模型队列处理完成，通知观察线程收尾，再检查统计。异常退出仍应保存首错与剩余事务。共享对象、队列和状态要有清楚所有者，竞争不能靠长延时“解决”。

| 位置 | 实际职责 | 工程师检查点 |
|---|---|---|
| test／env | 创建配置、选择场景和组织组件 | 实际创建类型与配置正确，未生成无用层级 |
| build | 建立组件并获取配置 | 配置缺失及时报错，不静默使用错误默认值 |
| connect | 连接 sequencer、driver、monitor 和比较路径 | TLM 连接确实有消费者，虚接口已设置 |
| run | 执行场景、驱动、观察和模型任务 | 线程真实启动，复位时可退出或重启 |
| check／report | 核对残留、计数、错误与最终报告 | 不只打印状态，异常进入最终结论 |

sequence 组织事务，sequencer 协调多个序列，Driver 执行协议，Monitor 观察真实事件。analysis 传递对象时仍需处理所有权；框架不会自动替用户复制可变事务。objection 延长运行期，释放之前确认业务和比较完成，不能以固定等待后释放代替结束判断。

## 事件、模型与比较

Test 计划八笔输入，Driver 已经准备第三笔但接收端一直等待，此时模型只能知道已接受的两笔。若按计划八笔直接建立必须输出的预期，可能把合法等待误报成丢失；若按 Driver 任务完成直接给实际值，则可能漏掉 DUT 接收错误。

对 valid/ready 接口，定义接受边沿后仅在二者有效时记录数据。请求、数据、响应分通道时分别记录各通道接受，再依据协议建立整笔关系。一个通道完成不是整笔完成。事件之间有依赖时用可观察状态或同步关系，不靠估计延时。

模型保留外部功能所需的最少状态。缓存模型可以是按接受顺序组织的队列，不必复制内部 RAM 指针和状态编码；算术模型使用规格运算，但明确有限位宽、符号、截断、饱和或回绕。过于贴近 RTL 会复制相同错误，过于理想则可能忽略关键约束。

| 模块行为 | 合适的模型 | 必须补充的语义 |
|---|---|---|
| 无状态数据变换 | 独立计算函数 | 位宽、字节顺序、有效范围和算术边界 |
| 缓存顺序转发 | 已接受输入队列 | 复位取消、容量和输出消费时机 |
| 宽度转换或拼拆帧 | 规范化有效字节序列 | 帧界、尾字节和输出重组规则 |
| 多请求应答 | 按键保存的预期集合 | ID 复用、顺序域、完成与取消 |
| 配置影响行为 | 功能状态加实际配置 | 配置生效时点及合法变更范围 |

先将输入变成规格意义上的预期结果，再与实际事务比较。严格顺序接口按队首消费，不能任意搜索相同载荷而容忍错序。允许乱序时，关联键必须符合 ID 和顺序域规则，并检查未知响应、重复完成和同 ID 复用。

有效数据按字节或字段比较，忽略范围只来自明确的无效语义。控制 X/Z 需要独立处理，宽松相等或掩码不能把它们当正确。数量守恒用于发现缺失，但无法发现内容错误或等量替换，因此与内容和关联检查配合。

假设输入一拍包含四个有效字节，输出一拍最多两个字节。模型先按已接受输入生成四字节规范序列，而不是预计输出也只有一拍。输出 Monitor 按真实接受重建两拍数据，再对有效字节和帧结束比较。最后一拍不满时仅比较有效范围，结束与字节数仍必须正确。

模型维护待输出字节和帧边界，不能只用总字节计数。若把两帧数据错误拼在一起，总字节数可能相同，但帧界和结束标志不同；因此需将边界作为独立语义保存。等待期间数据和尾部标志都要保持，不能只比较最终拼接内容而漏掉协议错误。

两个相同 ID 请求是否能同时在途，取决于协议及模块能力。若同 ID 必须按顺序返回，可为每个有效 ID 维护顺序队列；不同 ID 完成允许交错。匹配后检查数据、长度和错误语义，再释放对应资源。只保留一个 ID 到对象映射会覆盖同 ID 的第二笔请求，需要避免。

若 ID 不允许同时复用，生成器必须遵守该限制，检查器也应检测意外冲突。ID 空间回绕时，旧完成已经释放才能合法重用；复位前后可能需要环境代次区分。不能把“同一 ID 出现”作为通用重复错误条件。

## 对象、复位与结束

发布对象是历史事实。Monitor 复用同一句柄会让历史队列随下一笔变化；动态数组和嵌套对象需要恰当复制。共享只读配置可以复用，但如果组件会改值，要明确所有权及生效时点。Test 不应在 Driver 仍使用对象时再次随机化它。

多个消费者订阅事务时，不假定一个消费者的修改不会影响另一个。使用不可变快照或在需要修改时复制。队列容量和阻塞要考虑真实接口速率，Monitor 不能因为下游计算暂慢就漏采样；可以缓存并诊断积压，但结束前必须处理完。

统一定义接受、完成、取消和剩余。复位时按规格保留或取消事务，清理模型和队列，停止旧驱动，必要时使用代次区分旧响应。复位撤销后等待就绪，检查首笔新事务，不能只把所有计数归零后直接继续。

结束先停止新激励，再等待依赖任务、在途事务和比较队列处理完成，最后核对错误和产物。框架结束信号只控制线程时间，业务结束由这些条件证明。watchdog 是异常退出，不能作为正常用例完成机制。

顺序模块接受 A、B、C 三笔，输出 A 后发生复位。若规格取消未完成事务，则记录接受三、完成一、取消二、剩余零；恢复后输入 D，预期仅 D。若 Scoreboard 仍保留 B、C，会把正常 D 误判错；若简单清空且不记录取消，也可能掩盖真正丢失。检查的关键是统一语义和可解释账目。

用受控的错误字节、缺失或多余响应验证失败路径，再恢复正常实现。自检证明环境会判错，不证明 DUT 已正确。最终实现由工程师结合实际接口和模型完善，不能由类结构图直接推断完成。

## 自检与常见问题

| 现象 | 优先考虑 | 有效改进 |
|---|---|---|
| 历史事务都变成最后一笔 | 共享可变句柄或动态数据 | 发布稳定快照，确认嵌套复制 |
| 第一笔或尾笔总错一拍 | 采样边沿、读模式、侧带快照 | 对齐真实事件，不能整体放宽比较 |
| 收发总数相同仍有错误 | 内容、顺序或关联未比较 | 可区分载荷及逐字段检查 |
| 数据正确但始终不结束 | 在途计数、残留和线程停止 | 明确完成消费及协调者 |
| 复位后偶尔错 | 旧线程、旧响应或队列清理不一致 | 统一取消规则并检查新业务 |
| 多接口单独通过，组合失败 | 共享资源和事务依赖 | 用真实事件协调并统一关联 |
| 检查器从不报错 | 没连接、没启动、掩码或无条件通过 | 受控错误证明失败路径有效 |

Monitor 不应丢弃无法匹配的输出；Scoreboard 不应任意调整顺序来寻找相等数据；模型不应读 DUT 输出决定预期；Driver 不应根据内部错误状态偷偷改变合法输入以避免失败。这些做法会让环境帮助实现得到正确结论。

需要容忍的协议行为必须来自规格。例如允许乱序就按合法键匹配，而非允许任何交换；允许取消就记录取消条件，而非清空所有残留。限制越明确，误报和漏报越容易控制。

在可恢复的验证副本中人为改变一个预期字节，确认比较失败进入总错误数；再制造一次缺失响应，确认有界等待能够失败。自检完成后恢复正常代码，记录自检对象和结果，不把人为错误算成 DUT 缺陷。AI 模板中的空比较函数、未接入观察逻辑和无条件通过语句必须由工程师补齐。

出口是一个正常已知例子能解释每笔输入和输出，检查器能发现受控错误，复位与结束行为清楚。若接口增多、对象关联和并发协调变得难以维护，应转用轻量级 SV，而不是在任务间继续堆叠无约束延时。

AI 根据工程师已完善的方案生成环境和用例模板，工程师补齐实际接口、模型和检查。具体要求见[环境组织与组件规则](../../02_工程规则/环境组织与组件规则.md)。没有编译运行时，如实说明只是静态实现或审查。
